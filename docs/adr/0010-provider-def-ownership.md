# ADR-0010: Provider Definition Ownership — the OCR Defs File, opencode.jsonc as a Materialization Target

## Status

Implemented — 2026-10-20 (stages: the defs store + one-shot jsonc port; the funnel swap across CRUD/boot/view; materialize-then-push sync with REPLACE semantics; the CLI hook rework). Amends the boot source in ADR-0005 §2(a). Amended 2026-10-21: the hand-written `config.yaml` `providers[]` surface is retired — the defs file is the sole connection-def truth (see §1).

## Decision

### 1. One truth per artifact class — connection defs join credentials

Provider CONNECTION definitions — id, name, npm wire package, baseURL, headers, env slots, canonical/body, node-static models — are owned by OCR in `<ocrHome>/custom-providers.json`, GLOBAL (not per-environment; same book as `credentials.json`, ADR-0007 file conventions). This is the SINGLE user-facing connection-def surface: the former hand-written `config.yaml` `providers[]` section is RETIRED (registry no longer reads it; the config parser drops it, the native-System-One passthrough limb was retired entirely (ADR-0008 amendment; a future Jev/Bailian integration arrives as an ordinary defs-file provider) and the hand-written `models[]` surface retired with it (models materialize from defs + catalog at boot; `RouterConfig.models` survives purely as the runtime carrier index.ts overwrites with `boot.models`). `opencode.jsonc` leaves the truth chain ENTIRELY: no console route, no boot path, no view may read or write it as truth. It is a MATERIALIZATION TARGET — a sync-client artifact the opencode adapter regenerates from the defs file, exactly as `opencode.db`/`auth.json` are for keys (ADR-0006). Hand-edited jsonc defs are not a source of anything; the §4 one-shot import is the only client→OCR def motion that will ever exist.

### 2. The file — a shape-preserving port of the jsonc providers node

`custom-providers.json`: `version: 1`, atomic temp+rename, shape = the CURRENT jsonc `providers` node verbatim (id → `{ name?, npm?, options: { baseURL?, headers? }, models?, env?, canonical?, body? }`). The node parser in `user-config.ts` (CURRENT shape only; `env:[VAR]` names materialize to `{env:X}` templates — boot-direct.ts:13,22 loads nodes through this one funnel) is UNCHANGED: boot-direct and the console routes swap the loader's SOURCE, not the grammar. Boundary with the catalog layer: node-static models ride the def (as today's jsonc nodes do); pulled/overlaid models stay in `catalog/custom.json` (add-only overlay, untouched — the custom-store.ts:12-14 precedence survives as-is).

### 3. Boot pool — same three sources, new (a)

ADR-0005 §2 restates as: (a) `custom-providers.json` provider nodes, (b) the boot-bound credential chain (ADR-0006), (c) the catalog. Failure doctrine unchanged: an unroutable provider is EXCLUDED and reported, never a boot abort; an unreadable defs file is a loud degraded badge (the credential-store doctrine, mirrored). The pool stays boot-scoped (ADR-0005 §1 — no pool-rebuild endpoint appears).

### 4. One-shot migration

At boot, marker-absent and jsonc `providers` non-empty ⇒ import verbatim into the defs file (idempotent: whole-node upsert by id), record the completion marker in the `credential-store.json` ledger (the standalone-import pattern, factory.ts). jsonc stays BYTE-IDENTICAL on disk (never delete an upstream artifact — cp-dataloss doctrine), so a v2 CLI keeps its pre-migration view until sync materializes fresher defs. Import failure = loud degraded state, marker withheld, retried next boot.

### 5. Sync contract — keys AND defs, write-only

The opencode v2 client's write direction materializes BOTH artifact classes: keys (existing `pushOcrIntoV2`) and defs — render the defs file into jsonc's `providers` node via the comment-preserving jsonc writer, then `POST /api/location/reload` so a running service registers the ids (the reload self-heal in `resolveIntegrationId` survives unchanged). The v2 writable gate (`declaredProviderIds`) consults the DEFS FILE, not jsonc. Read direction stays credentials-only — defs NEVER flow client→OCR. v1 client: keys only, no defs (legacy degraded face; no def-rewrite surface).

### 6. Console + UI de-opencode-ization

Provider CRUD rewrites onto the defs store (`upsertCustomProvider`/`getProviderNodeById` become defs-file operations). The connected view = defs file ∪ bound-store credentials; grid order reads defs-file sequence (jsonc order dies with the coupling). The page retitles to "Provider Management"; `opencode.jsonc` appears only inside the sync-client panel. The catalog needs no de-coupling — models.dev is fetched directly (sources/models-dev.ts), no opencode involvement. The same connected union governs the catalog aggregation (model list): each aggregated provider's `connected` ORs in bound-store credential presence (and the credentials file mtime joins the aggregation signature, so key add/remove rebuilds without a restart). The aggregation reads the defs file ONLY — the frozen auth.json snapshot feeds no view; its sole remaining readers are the credentials layer's one-shot import and v1 sync client.

### 7. Auto-pull is opt-in per provider (`catalog.autoPullPatterns`)

Amended 2026-12: the periodic model sweep (`autoPullProviderModels`, driven by the catalog repository's sync timer) and the post-create opportunistic top-up pull ONLY providers declared in `config.yaml`'s `catalog.autoPullPatterns` (providerId → glob over model ids, comma-separated alternates — same DSL as the manual pull route). A provider absent from the map — or mapped to a blank string — is never auto-pulled, and a declared provider's pull is bounded by its pattern; an undeclared aggregator gateway can no longer have its full upstream list materialized every sync period. The whitelist lives in the ROUTER config, never in the defs file — opencode v2 nodes must stay decoder-clean, and pull behavior is router behavior, not a connection def. `catalog.autoPullModels` remains the master switch. Both gates are read live (console edits are hot). Manual console pulls are unaffected — the pattern is a per-request argument there. The sweep stays ADD-ONLY: locally maintained defs are never overwritten.

## Consequences

- A client that never syncs sees nothing new BY DESIGN: the old "instantly shared through jsonc" coupling is the thing being removed. Post-migration, a v2 CLI keeps its imported (byte-identical) defs until write-sync materializes updates.
- The auto-pull opt-in (§7) is a breaking behavior flip for pre-existing installs: providers that were silently swept before now stay untouched until the operator declares a pattern. That is the intended default — full-list materialization was the bug; re-arming is one `catalog.autoPullPatterns` entry per provider.
- Truth-per-class is now uniform: `credentials.json` (keys) · `custom-providers.json` (connection defs) · `catalog/*` (models+pricing) · `opencode.jsonc` (client copy). Every "stored in X" claim on the console maps to exactly one owner file.
- Cleanup contract: `rg "upsertCustomProvider|getProviderNodeById|opencode\.jsonc" backend/src frontend/src` must reduce to the sync adapter's materialization path, the migration's read-once path, and sync-panel i18n strings. The provider-def-opencode-v2-write-routes.test.ts family rewrites onto the defs store; boot-direct tests re-seed defs files instead of jsonc.
- The `onecast-router` defs node (client hooking writes it so clients resolve `onecast-router/...` refs) is a NORMAL catalog citizen: the aggregation lists it like any defs-file provider. There are NO id-based special cases anywhere — behavior derives from what a def IS, not what it is named. The one guard that exists is self-REFERENCE detection (`utils/self-url.ts`): a baseURL on a loopback host at the gateway's own port is never a valid upstream. `buildDirectPool` excludes it loudly on the RESOLVED baseURL — after `{env:...}` expansion, the exact escape a raw-record check would miss (`self_loop` — pooling it would recurse every routed request into the gateway, ADR-0005 §2 excluded-and-reported doctrine); `pullLiveModels` and the `autoPullProviderModels` sweep refuse the self-fetch (it would re-materialize every routable model as that provider's defs); console provider-create and provider-update reject it at the door (409, the update's baseURL fallback mirroring the upsert's `body.baseURL ?? existing.options?.baseURL`). A def pointing at a DIFFERENT instance (another port/host) passes everywhere — legitimate federation upstream. The catalog store (`ocr.json`) version starts at 3 — 1 and 2 are burned by pre-history (2 was the pre-rename snapshot with `builtin` source ids) and the version is monotonic only, never reused or stepped back; it exists to invalidate every on-disk snapshot when aggregation semantics change in code, since the signature only covers defs/config mtimes + source defs + locked ids. `/v1/catalog.json` and `/v1/models` keep featuring the VIRTUAL provider built from the registry — that plane is unaffected.
