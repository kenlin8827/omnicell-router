# ADR-0010: Provider Definition Ownership — the OCR Defs File, opencode.jsonc as a Materialization Target

## Status

Implemented — 2026-10-20 (stages: the defs store + one-shot jsonc port; the funnel swap across CRUD/boot/view; materialize-then-push sync with REPLACE semantics; the CLI hook rework). Amends the boot source in ADR-0005 §2(a). Amended 2026-10-21: the hand-written `config.yaml` `providers[]` surface is retired — the defs file is the sole connection-def truth (see §1).

## Decision

### 1. One truth per artifact class — connection defs join credentials

Provider CONNECTION definitions — id, name, npm wire package, baseURL, headers, env slots, canonical/body, node-static models — are owned by OCR in `<ocrHome>/providers.json`, GLOBAL (not per-environment; same book as `credentials.json`, ADR-0007 file conventions). This is the SINGLE user-facing connection-def surface: the former hand-written `config.yaml` `providers[]` section is RETIRED (registry no longer reads it; the config parser drops it, the native-System-One passthrough limb was retired entirely (ADR-0008 amendment; a future Jev/Bailian integration arrives as an ordinary defs-file provider) and the hand-written `models[]` surface retired with it (models materialize from defs + catalog at boot; `RouterConfig.models` survives purely as the runtime carrier index.ts overwrites with `boot.models`). `opencode.jsonc` leaves the truth chain ENTIRELY: no console route, no boot path, no view may read or write it as truth. It is a MATERIALIZATION TARGET — a sync-client artifact the opencode adapter regenerates from the defs file, exactly as `opencode.db`/`auth.json` are for keys (ADR-0006). Hand-edited jsonc defs are not a source of anything; the §4 one-shot import is the only client→OCR def motion that will ever exist.

### 2. The file — a shape-preserving port of the jsonc providers node

`providers.json`: `version: 1`, atomic temp+rename, shape = the CURRENT jsonc `providers` node verbatim (id → `{ name?, npm?, options: { baseURL?, headers? }, models?, env?, canonical?, body? }`). Provider ids are lowercase slugs (`[a-z0-9]` first, then `[a-z0-9._-]`): the id is a verbatim key across the defs file, the credential store, quota (provider × keyHashPrefix) pairs, breaker state and modelRef `provider/model` strings, and every catalog/vocabulary id is lowercase — so `upsertProviderDef` refuses anything else on every def write, the console create route answers 400 with the rule restated, and the form's id field is a live input mask (lowercased, invalid characters stripped) so the user always sees exactly what will be stored. The node parser in `user-config.ts` (CURRENT shape only; `env:[VAR]` names materialize to `{env:X}` templates — boot-direct.ts:13,22 loads nodes through this one funnel) is UNCHANGED: boot-direct and the console routes swap the loader's SOURCE, not the grammar. Boundary with the catalog layer: EVERY model of a provider — node-static and pulled alike — lives in that provider's node (unification amendment; the `catalog/custom.json` overlay is retired, so there is no second landing spot and no precedence question left to state).

### 3. Boot pool — same three sources, new (a)

ADR-0005 §2 restates as: (a) `providers.json` provider nodes, (b) the boot-bound credential chain (ADR-0006), (c) the catalog. Failure doctrine unchanged: an unroutable provider is EXCLUDED and reported, never a boot abort; an unreadable defs file is a loud degraded badge (the credential-store doctrine, mirrored). The pool stays boot-scoped (ADR-0005 §1 — no pool-rebuild endpoint appears).

### 4. One-shot migration

At boot, marker-absent and jsonc `providers` non-empty ⇒ import verbatim into the defs file (idempotent: whole-node upsert by id), record the completion marker in the `credential-store.json` ledger (the standalone-import pattern, factory.ts). jsonc stays BYTE-IDENTICAL on disk (never delete an upstream artifact — cp-dataloss doctrine), so a v2 CLI keeps its pre-migration view until sync materializes fresher defs. Import failure = loud degraded state, marker withheld, retried next boot.

### 5. Sync contract — keys AND defs, write-only

The opencode v2 client's write direction materializes BOTH artifact classes: keys (existing `pushOcrIntoV2`) and defs — render the defs file into jsonc's `providers` node via the comment-preserving jsonc writer, then `POST /api/location/reload` so a running service registers the ids (the reload self-heal in `resolveIntegrationId` survives unchanged). The v2 writable gate (`declaredProviderIds`) consults the DEFS FILE, not jsonc. Read direction stays credentials-only — defs NEVER flow client→OCR. v1 client: keys only, no defs (legacy degraded face; no def-rewrite surface).

### 6. Console + UI de-opencode-ization

Provider CRUD rewrites onto the defs store (`upsertProviderDef`/`getProviderNodeById` become defs-file operations). The connected view = defs file ∪ bound-store credentials; grid order reads defs-file sequence (jsonc order dies with the coupling). The page retitles to "Provider Management"; `opencode.jsonc` appears only inside the sync-client panel. The catalog needs no de-coupling — models.dev is fetched directly (sources/models-dev.ts), no opencode involvement. The same connected union governs the catalog aggregation (model list): each aggregated provider's `connected` ORs in bound-store credential presence (and the credentials file mtime joins the aggregation signature, so key add/remove rebuilds without a restart). The aggregation reads the defs file ONLY — the frozen auth.json snapshot feeds no view; its sole remaining readers are the credentials layer's one-shot import and v1 sync client.

### 7. Auto-pull is opt-in per provider (`catalog.autoPullPatterns`)

Amended 2026-12: the periodic model sweep (`autoPullProviderModels`, driven by the catalog repository's sync timer) and the post-create opportunistic top-up pull ONLY providers declared in `config.yaml`'s `catalog.autoPullPatterns` (providerId → glob over model ids, comma-separated alternates — same DSL as the manual pull route). A provider absent from the map — or mapped to a blank string — is never auto-pulled, and a declared provider's pull is bounded by its pattern; an undeclared aggregator gateway can no longer have its full upstream list materialized every sync period. The whitelist lives in the ROUTER config, never in the defs file — opencode v2 nodes must stay decoder-clean, and pull behavior is router behavior, not a connection def. `catalog.autoPullModels` remains the master switch. Both gates are read live (console edits are hot). Manual console pulls are unaffected — the pattern is a per-request argument there. The sweep stays ADD-ONLY: locally maintained defs are never overwritten.

## Consequences

- A client that never syncs sees nothing new BY DESIGN: the old "instantly shared through jsonc" coupling is the thing being removed. Post-migration, a v2 CLI keeps its imported (byte-identical) defs until write-sync materializes updates.
- The auto-pull opt-in (§7) is a breaking behavior flip for pre-existing installs: providers that were silently swept before now stay untouched until the operator declares a pattern. That is the intended default — full-list materialization was the bug; re-arming is one `catalog.autoPullPatterns` entry per provider.
- Truth-per-class is now uniform: `credentials.json` (keys) · `providers.json` (connection defs) · `catalog/*` (models+pricing) · `opencode.jsonc` (client copy). Every "stored in X" claim on the console maps to exactly one owner file.
- Cleanup contract: `rg "upsertProviderDef|getProviderNodeById|opencode\.jsonc" backend/src frontend/src` must reduce to the sync adapter's materialization path, the migration's read-once path, and sync-panel i18n strings. The provider-def-opencode-v2-write-routes.test.ts family rewrites onto the defs store; boot-direct tests re-seed defs files instead of jsonc.
- The `onecast-router` defs node (client hooking writes it so clients resolve `onecast-router/...` refs) is a NORMAL catalog citizen: the aggregation lists it like any defs-file provider. There are NO id-based special cases anywhere — behavior derives from what a def IS, not what it is named. The one guard that exists is self-REFERENCE detection (`utils/self-url.ts`): a baseURL on a loopback host at the gateway's own port is never a valid upstream. `buildDirectPool` excludes it loudly on the RESOLVED baseURL — after `{env:...}` expansion, the exact escape a raw-record check would miss (`self_loop` — pooling it would recurse every routed request into the gateway, ADR-0005 §2 excluded-and-reported doctrine); `pullLiveModels` and the `autoPullProviderModels` sweep refuse the self-fetch (it would re-materialize every routable model as that provider's defs); console provider-create and provider-update reject it at the door (409, the update's baseURL fallback mirroring the upsert's `body.baseURL ?? existing.options?.baseURL`). A def pointing at a DIFFERENT instance (another port/host) passes everywhere — legitimate federation upstream. The catalog store (`ocr.json`) version is now 4 (see the Amendment below; 1–3 are burned by pre-history) and the version is monotonic only, never reused or stepped back; it exists to invalidate every on-disk snapshot when aggregation semantics change in code, since the signature only covers defs/config mtimes + source defs + locked ids. `/v1/catalog.json` and `/v1/models` keep featuring the VIRTUAL provider built from the registry — that plane is unaffected.

## Amendment — provider book unification (providers.json, connect-time doctrine)

A later revision collapses the provider class system entirely. Supersessions are called out inline; everything above still holds where not contradicted.

- **One book, no class system.** `<ocrHome>/providers.json` (renamed from `custom-providers.json`) is the single def truth for EVERY provider — built-in (connected from the catalog) and self-declared relay alike. The historical `catalog/custom.json` custom store is RETIRED: its credential-only landing spot existed only because built-in providers had no defs node, and that asymmetry is gone. Hard cutover — legacy books are NOT migrated; the code simply stops reading them (files stay on disk untouched). An operator upgrades by restarting (the boot bind ensures a node for every store-backed provider) and then pulling/re-connecting: an empty node is an EMPTY universe (no catalog fallback), so no model routes until the node is filled. That state is observable, not log-only: a provider card whose node has no models carries a `No models` chip that opens the model dialog (pull / add), and `/models` — a maintained-only page — renders an empty state that links to the Providers page instead of a dead end. An existing credential keeps routing nothing until the operator acts; nothing silently re-expands it.
- **The defs node IS the routing universe.** `buildDirectPool` takes `Object.keys(defs)` and nothing else — the catalog listing is a SOURCE for the node, never a fallback pool. An empty node is excluded-and-reported (reason: no models maintained — pull or add some), not silently re-expanded to the catalog. This is what makes `/models` (maintained physical models) and `/v1/models` (the same set, policy-filtered) agree.
- **Model hiding is a CLIENT-visibility flag, not a second universe.** `disabled` (overrides.json, or a def-level flag the aggregation carries over — override wins) keeps a MAINTAINED model out of the boot pool: after a restart `/v1/models` omits it and a direct call cannot be pinned to it. Console surfaces still read the aggregate, so `/models` and the catalog viewer keep listing the row with its toggle and badge (restorable). The pool is boot-scoped; there is no hot-apply for this flag. Only the override plane is written by the UI — the model form's def-level switch was retired (it read/wrote a second plane and could not be toggled back).
- **Connect-time doctrine.** A credential landing (console connect, provider create, boot bind sweep) ensures the provider owns a defs node, seeding the effective baseURL from the explicit override or the aggregated catalog record — this is what makes live `/v1/models` pull uniformly available (the credential-only class could never carry a baseURL). `ensureConnectedProviderBook` (catalog/auto-pull.ts) then auto-fills models ONCE for an empty node: live first, static catalog fallback, `enrichFromCatalog` for pricing/limits. Seeding applies to an EXISTING node too: the bind sweep creates bare nodes by design, so a node with no `options.baseURL` is seeded on the next connect/bind sweep — otherwise the documented hard-cutover recovery (re-connect without retyping the baseURL) would leave every self-declared relay permanently unable to live-pull. A node that already has models is operator-owned truth and is never re-filled. Auto-fill failure is data on the response (`modelsFilled`/`fillError`), never a connect failure. The §7 auto-pull OPT-IN for the periodic sweep is unchanged — self-declared relays still only materialize on an explicit `autoPullPatterns` entry or manual pull.
- **The custom badge is DYNAMIC, never stored.** A provider is custom iff its id is not covered by the built-in provider catalogs (`sources` ∋ `opencode` | `models-dev`, derived at aggregation time in repository.ts step 5). The old accumulated `custom: true` bookkeeping (defs views, step-1 records) is gone.
- **Model writes have ONE landing spot** (the provider's own node): modelsGet/modelAdd/modelUpdate/modelRemove/modelsClear/modelReorder lose their credential-only fallback branches; pullCatalogModels writes the node unconditionally; the periodic sweep skips node-less providers (not connected → nothing to write into, never fabricates a connection). The `modelsManageable` capability field is GONE from the wire with the gate it used to carry: with one landing spot, editability IS presence (a row that exists owns a node), and a constant-true field is dead API surface. Model ORDER is defs-file truth too: the console up/down gesture rewrites the node's `models` key order (modelReorder), because the materialization renders the node verbatim and the drift check is order-sensitive — an order change is a real def write that pushes to the client, never a console-only view preference.
- **The bind sweep checks the RAW defs file, not the normalized view.** The normalized view drops retired-shape nodes (Decision 9); a raw check is the only way to avoid "resurrecting" one as a fresh routable node. A retired node keeps its loud boot exclusion until the operator migrates it (a re-connect deliberately rebuilds it — the key just went to the store, nothing is lost).
- **`ocr.json` version 4**: 3 is burned by this amendment (the aggregation lost the `custom` source); monotonic, never reused. The `custom` CatalogSourceId is GONE with it: source tags are always the configured source's own `src.def.id`, never a hardcoded class, so the retired member had no producer left. (`catalog.sources[].type: 'custom'` is a different concept — a user-configurable model-list SOURCE type — and survives.)
- Env book-sets (ADR-0007): `catalog/custom.json` leaves the export set; the envelope whitelist keeps ACCEPTING the key (its checksum still enforced, so a tampered archive is still refused) and then DROPS it — a pre-amendment book-set imports instead of being rejected, and the retired file is never written back into the new environment.
- **Console surfaces split by plane.** `/models` = maintained physical models only (defs-backed rows, edit/test/lock); the aggregated catalog moved to a read-only tab on the model-sources page (discovery/reference, no maintenance actions). Virtual refs (auto/tier aliases, combos, variants) never appear on `/models` — they have their own pages, which keeps "maintained" unambiguous.

## Amendment — defs write-path hardening (2026-12)

Reviewed after the unification amendment; four sync-contract defects fixed. §5 still holds — this amendment states the invariants it lacked.

- **Absent ≠ empty (materialization guard).** The materializer reads the RAW defs book: a missing / unparsable / wrong-version file is NOT `providers: {}`. With a populated client slot it REFUSES loudly (`ok:false`, one `failed` entry, client file byte-identical); with an empty client slot it is a no-op. A valid-but-empty book still REPLACEs the client slot — that is def delete propagation, and it must not be conflated with the unreadable case. The pre-sync client config is copied to `<config>.bak.ocr-defs` on EVERY change (refreshed, not first-capture-only) so the wipe an operator may need to undo is always the immediately preceding state.
- **A changed render reloads.** `POST /api/location/reload` now fires from the write path itself whenever the materialized slot actually changed (`materializeDefs` returns `changed`; unchanged renders never reload, so a periodic auto-write costs nothing). The unmatched-resolve self-heal stays, but only as the fallback for a failed reload: relying on it alone made def-ONLY changes (new model, price/limit edit, provider delete) invisible to a running client, since no key push follows them and therefore no unmatched resolve ever fires. The CLI setup/teardown/profile-refresh paths reload through the same helper. Outcome carries `defsMaterialized` / `defsChanged` / `defsReloaded` (mirrored in the console wire type), so "defs did not reach the client" is visible instead of a silent success.
- **One config-path resolver.** `credentials/paths.ts` owns the candidate list (`opencodeConfigCandidates` / `resolveOpencodeConfigPath`: `<configDir>/opencode.jsonc` → `<configDir>/opencode.json` → `~/.opencode/opencode.json`, first existing wins, jsonc as the default write target). The one-shot import (read) and the materializer (write) both resolve through it; previously the import read whichever file existed while the materializer always created `<configDir>/opencode.jsonc`, so on installs living in `opencode.json` (or the legacy home path) the push landed in a file the client never reads and reported success. Candidate resolution never leaves the injected path set (`home` is optional on `CredentialPaths`), so sandboxed path sets stay hermetic. The configDir itself is `OPENCODE_CONFIG_DIR` when the operator/server sets it (the CLI's own override — `--config-dir` profiles write it), else `<XDG_CONFIG_HOME>/opencode`; the data dir is unaffected, matching the CLI. Without this the push would silently target `~/.config/opencode` while a profile-launched client reads its own tree — the very mismatch this resolver prevents.
- **v1 presence = v1 evidence, not auth.json alone.** `v1FlavorActive` is "no v2 evidence (no db, no v2 pin) AND v1 evidence", where v1 evidence is an existing `auth.json` OR a v1 version pin. The pin counts because the write direction CREATES `auth.json` on a fresh v1 install — requiring the file made that (documented) creation branch unreachable, so a clean v1 machine could never be seeded.
- **Retired-shape rationale corrected (measured, 2026-12).** opencode v2.0.0 does NOT discard a node carrying node-level `npm`/`options`: live check on a real install enumerated the models of a `npm`+`options` probe node. The exclusion is kept, but on the honest ground — the retired WIRE spelling is unproven, so the realistic failure is a provider that looks registered while its baseURL/headers are ignored (a silently wrong endpoint, strictly worse than a missing provider). The earlier "the decoder rejects the node (`kind=invalid`)" statement was never verified and is retracted (code comments + boot-direct's exclusion comment now say this).
- **Drift is visible, never inferred from a green sync.** The status view gains `defsDrift` (opencode-v2): the client's materialized `providers` slot is compared to the defs book with the SAME comparison the materializer uses, so the badge can never disagree with what a push would do; the sync table renders a `defs not pushed` badge. Auto-write ships OFF and the two directions are independent, so until now a stale client copy was indistinguishable from a working push.
- **Per-provider runs cover BOTH directions.** The `provider` narrow of a sync run now applies to the pull as well as the push (the `credential-sync/run` route accepts an optional `provider`), so a provider-scoped gesture can no longer sweep the whole book.
- **Artifact-class asymmetry (recorded, not incidental).** What the write direction REPLACEs must never be overwritten from the client: defs are materialized as an identity REPLACE of the `providers` slot, so the client→OCR def motion is ADD-ONLY (the boot import and the sync read direction; amended below — an id OCR already owns is never taken from the client). What the write direction merely ADDS to legitimately flows back: keys are pushed add/rotate-only, so a key deleted only in the OCR file is re-imported by the next pull (ADR-0006 amendment). Any future push-side key delete must ship with a pull-side tombstone, or the two directions fight each other forever.
- **Auto-write and manual sync share one core, two wrappers (recorded).** Both call the same `pullIntoOcr`/`pushFromOcr` pair and record into the same `credential-sync.json`; the differences are deliberate: SUSPECT lifts only on a manual gesture (the flag is an operator confirmation, never auto-cleared), the engine holds in-flight guards and a 1.5 s debounce + 60 s safety net, and only the manual run can be narrowed with `provider`. One consequence is fixed here: the safety net ALSO retries when `defsChanged === true && defsReloaded === false` — the keys dedup cleanly (so `ok` reads true) while the client serves a stale provider list, and nothing else would ever retry that.

## Amendment — the client→OCR provider import owns the v1/v2 spelling split (add-only, re-armed)

The one-shot jsonc→defs port is the ONE motion that reads connection defs off the client, and the adapter — not a caller — now owns the two differences a hand-editable client config exposes:

- **Two adapters, one per flavor (`provider-def-adapters.ts`).** The machine's flavor (`credentials/paths.ts`, shared with the credential sync clients) selects the adapter; the adapter owns its slot and its node shape. The slot SPELLING never leaks out of that module: callers ask for operations (`providerDefAdapter(flavor).read` for the import, `clientDefNodes` / `writeDefSlot` for the materializer and the drift badge — the write peer is always the v2 canonical slot), so no second module can grow its own opinion about where defs live — a shared `PROVIDER_SLOT`-style constant would have been exactly that drift twin, and both spellings declared side by side would erase the difference the adapters encode:
  - `opencode-v2` → the canonical **`providers`** (plural) slot, `package`/`settings` spelling, copied verbatim. The retired singular `provider` slot is NOT read — one flavor, one slot, no legacy pass (pinned by tests; rationale below).
  - `opencode-v1` → the singular **`provider`** slot only, `npm`/`options` spelling, converted; the canonical plural slot is not read either.
  Each pass reads exactly its own adapter's slot. Nothing is ever written to the client file by the read direction.
- **Measured slot behavior (2.0.29, 2026-10-23).** opencode v2 ACCEPTS BOTH spellings as input and folds the legacy one into its canonical form: a hand-written `provider` node (v1 `npm`/`options`) appears in the service's decoded config (`GET /api/config`) under `providers` with `package`/`settings` (raw npm packages get the `aisdk:` prefix). `providers` is therefore the canonical/effective spelling — what the materializer writes and what the schema declares (`@opencode/schema` 2.0.16 `Config` struct has only `providers`) — while `provider` is a compatibility INPUT, not a second truth. The v2 adapter therefore still reads ONLY the canonical slot: a v1-shaped relic keeps registering in the client through the fold, but a compatibility input is not a truth OCR imports or tracks — ownership is claimed from the canonical spelling alone.
- **Shapes.** Detected by SHAPE, never by slot: the retired v1 node shape is node-level `npm`/`options` (`legacyShapedProviderPaths`), and the v1 adapter CONVERTS it through the same def builder the console uses (`package`/`settings`, model-level `provider.npm` → `provider.package`) instead of copying it verbatim — a verbatim copy would be dropped by the OCR reader and refused by every def write. The inline credential rides through the conversion (`settings.apiKey` kept; a `{env:VAR}` value becomes `env:["VAR"]`), because a working client copy must not lose its key during a shape migration; the console renders it as inline.
- **Add-only.** An id already in the defs file is SKIPPED, never overwritten. This supersedes §4's "whole-node upsert by id, the jsonc node wins its own id": after the first port the OCR file is the truth, so a re-run may only fill gaps — a stale client copy can never reset an operator's def edit. (This matches the credential pull's add-only contract; deletes and edits travel OCR→client only.)
- **Re-arm by port version.** The marker in `credential-store.json` carries `version` (`PROVIDER_DEFS_IMPORT_VERSION`); a marker written by an older port — or none — is STALE and the pass runs again on the next boot. That is how an existing install picks up the newly-read singular slot and the shape conversion without a manual gesture or a wiped ledger. A deferred pass (unparsable client config / defs write failure) records nothing new, keeps the stale record visible, and retries next boot.
- **The retired slot is ignored, never pruned.** Neither direction touches the singular `provider` slot on a v2 machine: the import never reads it, the materializer REPLACEs only `providers` and leaves every legacy node byte-untouched, and `defsDrift` compares only the canonical slot. Recorded consequence: a stale legacy copy can keep a def alive in the client (through the fold) after OCR has deleted it, and the pull cannot see it — clearing it is a client-file edit, the same "delete on the client side too" rule as key deletions (ADR-0006).
- **Built-in ⇒ keys only; custom ⇒ config node.** The write direction renders the defs book MINUS the provider ids the CLIENT defines itself. Evidence, never a maintained id list: `GET /api/provider` returns an `integrationID` exactly for catalog-defined providers, while a node that exists only because it was written into the config (a relay like `maisuitx`) has none. Those built-ins need no config node — the client already holds their package, baseURL and model list — so only their keys travel (the key half of the push is unchanged). Everything the client does not know is written, so a connected custom provider always lands in `providers`. The id set is recorded on the write outcome (`defsSkippedBuiltIn`) because `defsDrift` must compare the same render set the push used; with no service to ask, the whole book is written — a missing def breaks routing, a redundant one never does.
- **Client-unloadable wires are substituted, not skipped — and never withheld from the operator.** The client's `package` strings are a closed set; a wire it has no package for (`systemone` / TypeSafe today: the SDK module exists but exposes only `experimental.evaluation`, and the loader knows no such segment) cannot be served by it at all. Two layers, one direction: (a) the npm vocabulary and the write-side npm→package table OFFER the native segment (`@ai-sdk/typesafe-ai` → `@opencode/ai/providers/typesafe`), so the dropdown and the defs book keep the decision wire end to end — the 2026-10-23 change that withheld the alias and downgraded the mapping is reverted (2026-10-24) as a regression, not a safeguard (no write-side path may hide a wire the read side still resolves), and (b) a def whose resolved wire the client has no package for still gets the compatible-runtime package in the CLIENT copy only (`CLIENT_PACKAGE_FALLBACK`, one entry, keyed by wire) — the book keeps the authored def, so OCR's own wire inference still resolves `systemone`. Deterministic from the book, so `defsDrift` compares the same map a push writes. No runtime probe: the client registers a model from the node's `models` map whether or not the package resolves, so probing would report success for a package that cannot serve a request. When a future client ships the segment, changing that one entry (or deleting it) switches every def back on the next push. The substitute answers only "can the client LOAD it" — whether the upstream speaks that protocol remains a vendor fact (ark does; api.typesafe.ai, whose only route is `POST /systemone`, does not).
- **The READ direction owns it too.** `pullIntoOcr` imports provider defs through the adapter of the client being synced — a manual or auto `opencode-v2` run is always the v2 adapter, an `opencode-v1` run always the v1 adapter; the version in the sync request decides, never a guess. A provider-narrowed run (`provider`) imports only that node. The outcome carries `defsImported` / `defsConverted` / `defsSkipped` / `defsFailed` (+ a `failed` entry when the import hard-fails), so the console shows it. The boot-time, marker-gated import stays as the seed for installs that never sync.
- **What is still forbidden.** No write-back of a stale client copy: defs are add-only in the read direction, and the write direction REPLACEs the canonical slot. A provider deleted in OCR but still present in the client's canonical slot is re-imported by the next pull — the same documented trade-off as a key deletion (the push that follows a delete propagates it; until then the client copy is the only evidence left). A legacy copy under the retired slot is untouched by both directions, so it is not a path the pull can re-own — see the recorded consequence above. Editing an already-imported def happens in OCR; a client-side edit of an OCR-owned def is ignored (reported as `skipped`).

Failures are per-node and never silent in the log: invalid ids (lowercase-slug rule), non-object nodes, and refused conversions are reported with their reason, and the ledger counts `imported` / `converted` / `skipped` / `failed`.
