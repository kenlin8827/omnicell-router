# ADR-0025: 客户端信封解析——分层推断，声明式提示优先

日期: 2026-11-14

> **变更纪律。** 新 harness 靠**数据**覆盖（一条 profile 记录），否则就不覆盖——
> 归一化器的规则不随客户端数量增长。标签只有在真实客户端的线上字节里实测到之后
> 才能入表，实测证据（会话 id、日期、被观测版本）须在同一提交中落盘。

## Context

每个 agent harness 都会在人类输入前面塞上自己的上下文。Cursor 的 agent 会先发一条
独立的 `<timestamp>11/8/2026, 8:53:57 PM GMT+8</timestamp>` 消息，再发一整包
`<user_info>`/`<rules>`/`<agent_skills>`/`<mcp_server_catalog>`/`<hooks_context>`
上下文，然后把真实轮次包进 `<user_query>`。Claude Code（实测于 2026-11-14，
`claude-cli/2.1.317`，抓包会话 `cc_c6a59aae…`）则是把机器注入与人类文本**混在同一条**
user 消息里：git 署名提醒 `<system-reminder>`、`/clear` 命令记录
（`<local-command-caveat>` / `<command-name>` / `<local-command-stdout>`），最后
才是人类提示；下一条 user 消息则是 SessionStart hook 的纯文本输出。

这些字节是客户端的提示，网关**必须**原样转发。但控制台会从中渲染四个**识别辅助**——
会话标题、每轮提示摘要、路由经验片段、抓包会话预览——每个都只截 120–200 字符。缺陷
正出在这里：标题只有一段 `<timestamp>`、标题以 `<user_info> OS Version: …` 开头、
标题是原始的 `<system-reminder>` 署名文本、每轮摘要引用了
`SessionStart:clear hook success: …` 却把问题本身挤没了。

早先的设计（三条规则 + 一张有证据的标签表）只覆盖**独立信封**，留下两个缺口：

1. **混合消息。** 同一条消息里既有机器块又有人类文本时，没有任何独立信封信号，
   规则 3（纯标签消息置空）不会触发，机器块靠位置赢下 200 字符的截断。
2. **纯文本约定。** hook 输出没有任何标签，结构化规则看不见它。

更根本的一点：对第三方 harness 而言，仅凭字节「永远正确」是不可能的。唯一 100%
准确的信号是发送方自己声明哪些字节属于人类。跟别人的提示格式赛跑写正则，不是设计。

## Decision

按信号强弱组成一条**阶梯**来解析显示文本。每层都能独立成立；每层更弱的层，是为了
覆盖那些不能或没有使用更强层的客户端。

### Layer 0 —— 声明式提示（权威）

知道哪些字节是人类输入的客户端，把它写在 `x-ocr-prompt-hint` 里。该值**逐字采用**
（空白压平、超长加省略号）——无推断、无词表、无 profile。这是唯一「构造即正确」的
通道，也是形状不可猜的 harness 的答案。

该头仅用于显示，且任何能发请求的人都能伪造。它在显示路径上只被读一次，其值绝不进入路由、
提示哈希、会话锚点、会话键或抓包 body；头本身与 `x-session-id` 一样原样透传到上游（模型
供应商不会赋予 `x-ocr-*` 头任何含义）。因此伪造一个头最多换来一个错标题。会话层优先级：
**出生即冻结**的标题最高（标题是出生属性，后续轮次逐字复制），其次声明值，最后才是推断。

### Layer 1 —— 结构化规则（客户端无关、零词表）

`displayPromptText` 保留原有扫描，在原三条规则旁新增规则 4：

1. 传输包装（`<user_query>`、`<session>`）即人类内容：其 body 裸取，该消息其余部分丢弃。
2. 已知元数据块无论位于何处都丢弃。
3. 一条**只有** XML 风格块、块外无文本的消息是客户端信封：置空，不管标签叫什么名字。
4. **以顶层块开头、且块外文本只出现在其后的消息，属于「前置机器」形状**：丢掉头部块串，
   只显示后面的文本。

规则 4 是承重的那一条。它命名的是**形状**而非词表——今后任何 harness 只要是「前面塞
上下文、后面放提示」，上线当天即被覆盖，无需改代码。它的护栏同样对称且结构化：第一个块
之前出现文本则规则不触发（人类写「请分析：`<data>…`」时原样保留）、包装消息仍先由规则 1
解析、未闭合标记不受影响（其逐字尾部本就是唯一的「块后文本」，两个分支结果相同）。

### Layer 2 —— harness profile（作用域化词表）

`harness-profiles.ts` 把 User-Agent 指纹（`claude-cli/` → Claude Code profile）映射到
该客户端的词表：无论位于何处都丢弃的元数据标签，以及把整条消息判为机器的锚定纯文本前缀
（`SessionStart:<matcher> hook (success|error|failure):`）。

作用域化是关键本身，不是优化。Cursor 用户把字面 `<command-name>` 块粘进问题时，显示里
仍保留它——因为该标签只对「把它当作机器来发」的客户端才算机器。表是数据；算法不随客户端
数量增长。

两个平面用同一套方式解析 profile：

- **实时**：`fastifyRequest.headers ?? clientRequest.headers ?? headers` —— 与 trace
  身份既有的优先级一致，因此 native 腿、MITM 腿与进程内调用者都能正确解析。
- **归档**：UA 与声明值从归档自己的 `requestHeaders` 读回，回放存量会话时解析结果与当初
  实时轮次完全一致。读平面绝不回查实时请求。

### 未采纳 —— Layer 3 重复抑制

「同一块内容在同一会话 ≥2 个请求里重复出现 ⇒ 机器」这条规则能用零词表覆盖每轮重注入的
上下文（例如反复重发的 `CLAUDE.md`）。暂不采纳：它需要在显示路径上持有跨请求状态、冷启动
无解，且当前没有留下任何未被 Layer 0–2 覆盖的实测缺陷。它保留为文档化的后备方案，等真实
缺陷出现再上。

### 不变量

- 仅显示用，边界不变：这里的任何结果都不进入路由、提示哈希、会话锚点、会话键、抓包或上游请求。
- 一份推导、四个界面：标题、每轮摘要、路由片段、抓包预览调用同一个归一化器，差别只在截断
  长度和是否传入 profile。
- 线性扫描，逐标签正则不做：归一化器在请求路径上处理任意客户端字节，`[\s\S]*?<\/tag>`
  这类匹配在满是未闭合标签的文档上是二次复杂度（实测 300 KB 的字面 `<a>` 约 5 秒）。

## Consequences

- **规则 4 是有意的行为变更。** 原先被测试钉死的 `<foo_state>x</foo_state> 你是谁` →
  原样输出，现在变为 `你是谁`。代价：人类把 markup 粘在问题**前面**时，≤200 字符的显示
  辅助里会丢掉这段 markup（线上字节、归档与上游请求均不受影响）。这个取舍被接受：识别行
  的是意图那句话，不是 markup。
- **实测的 Claude Code 案例在缺陷根源处被修复**：把抓包字节重放给已落地的归一化器，
  `cc_c6a59aae…` 的开启消息现在显示 `你是谁`。
- **新 harness 花的是数据，不是代码**——只要它是「前置上下文」的形状（规则 4 覆盖混合
  形状）。只有纯文本约定需要一条 profile 记录，而那是从实测抓包中添加的。
- **存量会话保留旧标题。** `firstUserSummary` 出生即冻结、后续轮次逐字复制（这样 trace
  环驱逐不会让标题消失）；修复只对新出生的会话生效，不追溯。这是「标题不会蒸发」的代价。
- **词表被作用域隔离，因此不会让别的客户端回归**；UA 按不可信输入对待：伪造指纹只会改掉
  一个标题，别的一概没有。
- **fixture 就是回归闸门。** 每条 profile 与每条结构化规则都用真实客户端采到的字节钉住，
  所以任何「又把机器注入引用回显示」的重构都会大声失败，而不是静默给会话改名。
