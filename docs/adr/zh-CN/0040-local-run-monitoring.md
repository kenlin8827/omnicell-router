# ADR-0040 — 本地运行监控：网关侧计数，而不是抓取引擎

- 状态：已接受（已实现）
- 日期：2026-12-03
- 修订：ADR-0037 §6（运行记录新增计数区块）、ADR-0038 §3（`local` provider 即计费接缝）

## 背景

本地模型控制台已经能装引擎、下载 GGUF、规划启动并运行模型（ADR-0037/0038/0039）。
它做不到的是**观察**一个正在运行的模型。

`LocalRunPage` 每两秒轮询 `/api/admin/local-models/runs`，但它只服务于启动器：它渲染**所选**
模型的 run，把所有其他活动 run 收进一条很小的「其他 run」带。运行记录本身只承载生命周期事实 ——
`status`、`ctx`、`ngl`、`pid`、`port`、`restarts`（`backend/src/local/runner.ts` 的 `LocalRun`）。
操作者真正的问题（「这个模型健康吗、谁在调用它、它答得多快」）在控制台里没有任何答案：

- **没有并发视图。** 可以同时有多个 run 处于 ready（runner 的 `live` 映射，各占一个端口），
  但没有任何页面把它们放在一起看。
- **没有吞吐与延迟。** 解码速度与 TTFT —— 判断本地模型是否可用的两个数字 —— 只存在于引擎
  自己的 stdout 里，埋在 run 日志抽屉中。
- **没有请求计数。** 没有任何东西统计某个 run 服务了多少请求、产出了多少 token。全局
  `FinOpsTracker` 按 **tier** 聚合而非按模型，而本地模型不加入任何 tier（设计如此，
  `tier: undefined`，ADR-0038 §6）—— 因此它根本不进入任何 tier 桶。
- **没有辅助 leg 健康。** `LocalRun.aux[]`（视觉 leg、helper server）只在所选模型自己的面板里可见。

诱人的修法是抓取引擎：llama.cpp 暴露 `/metrics`，一个轮询 sidecar 就能读到
`llamacpp:tokens_predicted_total` 之类。这条路被否决了 —— 见 §1。

## 决策

### 1. 网关自己计数；绝不抓取引擎

监控页上的每一个观测都来自网关在请求路径上**本来就看得见**的数据。不轮询 `/metrics`，
不搞每引擎一套健康方言，不对一个可能没在监听的 loopback 端口开第二个 HTTP 客户端。

理由是结构性的，不是风格偏好：

- **并非每个引擎都有这个面。** `/metrics` 家族是 llama.cpp 的事实。Strata（ADR-0039）是
  另一个运行时、另一套可观测性故事，第三个引擎又会不同。抓取意味着监控对所有非该引擎的
  运行时静默退化为「未知」—— 正是 ADR-0039 用一整篇记录清除掉的「按引擎分支」。
- **网关是唯一看见这个请求的一方。** 客户端被告知调用网关，绝不调用引擎端口（ADR-0038 §4：
  仅 loopback，引擎不是第二个公共面）。因此网关自己的视角不是对流量的近似 —— 它**就是**
  流量。一个引擎服务过、但网关没看见的请求，对面向操作者的控制台来说不存在。
- **计数必须能跨引擎重启存活。** `runs.json` 记录比其进程活得久（ADR-0037 启动清扫接管
  幸存者）。引擎侧计数在每次崩溃重启时归零；网关侧计数不必。

### 2. 计数接缝是 `local` provider 装饰器

`LocalDialProvider`（`backend/src/local/local-provider.ts`）已经同时坐在两条执行路径上 ——
`createCompletion` 与 `createStream` —— 并且已经解析出哪个 run 在应答
（`localBaseFor(installedId)`）。因此它是唯一在同一个栈帧里同时知道**哪个 run** 服务了请求、
以及**代价多少**的地方，不需要在 registry、orchestrator 或各个 surface 里新铺管道。

装饰器上报给 run 统计模块（`backend/src/local/run-stats.ts`）：

- **进入时** —— `beginRequest(runId)`：在途计数 +1，记录起始时间戳。
- **缓冲路径** —— 返回的 `CanonicalResponse.usage` 就是度量：`inputTokens`、`outputTokens`、
  `cachedInputTokens` 是计费事实。
- **流式路径** —— 装饰器包装返回的可迭代对象，因此终端 usage 事件在流经时被观测到。这与
  缓存完整性红线要求的纪律完全一致（「流式与缓冲是**同一条**计数平面」）：只在一侧计的字段
  就是 bug，而 Claude Code —— 本地模型最重的使用者 —— 只会流式。
- **退出时，无论成败** —— `endRequest(runId, outcome)`：在 `finally` 里刷新在途计数，失败时
  错误计数 +1。抛出的请求绝不能泄漏一个在途槽位，否则 gauge 会永远攀升，页面就在撒谎。

没走到任何 run 的请求（`local_run_inactive` 503，ADR-0038 §3）**不是**被服务的请求，永不进入
这些计数：run 已停止，没有 run 可供归属。那次拒绝已经可以在失败账本上观测到。

### 3. 速度在网关侧测量，且窗口是明示的

两个速率都源自网关时间戳，而不是引擎自报：

| 指标 | 基准 | 为什么用这个窗口 |
| --- | --- | --- |
| TTFT (ms) | 请求开始 → 首个流式 `response.output_text.delta`（缓冲 leg 则取响应完成时刻） | 操作者感知的等待。缓冲 leg 没有首 chunk 时刻，所以它的 TTFT 是「整段响应」，并被**标记**为如此 —— 绝不静默省略。 |
| 解码 (tok/s) | 输出 token ÷（首个 delta → 流结束） | 与 `frontend/src/lib/format.ts` 中 `decodeRate()` 已用于 capture 芯片的边界相同，因此本地模型的数字与云模型在同一类页面上可比较。 |

两者都保留「滚动聚合 + 最近一次采样」：run 生命周期内的平均值回答「这个模型总体上慢吗」，
最近一次采样回答「它**此刻**慢吗」。单个数字无法同时回答两者，而混淆二者正是「两小时前的
良好均值掩盖刚刚开始的抖动」的成因。

聚合自带采样数，因此页面可以说「3 次采样」，而不是把一个只有 1 次请求的均值呈现为趋势。

### 4. 监控只读一个端点；运行记录长出计数区块

`GET /api/admin/local-models/monitor` 对每个已知 run 返回 registry 的 `LocalRun` 与其计数
区块的合并结果，外加一份机器摘要（在途总数、活动 run 数、以及网关自己的端口，好让页面说明
客户端该指向哪里）。

计数活在运行记录**旁边**，而不是它的持久化 JSON 里面：

- `runs.json` 是生命周期状态 —— 启动清扫接管的东西、停止时按 pid 杀掉的东西。gauge/速率是
  派生且进程本地的；持久化它会让网关重启后一个四小时前的 TPS 看起来像实时读数，比什么都不
  显示更糟。
- 计数按 run id 键控，并与 run 一起清理（`pruneLocalRuns`，既有的历史清理路由）。

响应是增量且版本宽容的，遵循这里每个状态端点的控制台惯例：旧网关没有该路由，页面则退回
启动器自己的轮询。

### 5. 本篇不含 GPU 采样器

VRAM 占用、SM 利用率与功耗在立项时被明确排除在范围外。它们不是网关观测 —— 需要周期性外部
采样器（`nvidia-smi` / `rocm-smi`）、按厂商分叉，以及「没有独立显卡的机器显示什么」的决策。
`detect.ts` 已经在**规划**时读 `nvidia-smi` 取总/空闲 VRAM；实时时间序列是另一篇记录，本篇
刻意不夹带。

## 后果

- 本地分组新增第六个页面 `/local-monitor`（菜单名 **运行监测**），放在运行/注册表/设置页
  **之后**：它回答「正在发生什么」，而 `/local-run` 仍是「启动这个」。之所以放最后，是因为
  它观测的是上面那些行所配置并启动的东西 —— 属于工作流末尾的读数，而不是流程中的一步。
  菜单名刻意点明「运行」：本页监测的是活动的 run 及其请求计数，不是机器本身（不含 GPU/VRAM
  采样，§5）。
- 请求计数发生在 provider 装饰器内部，因此只对网关所服务的模型可达 —— 而这按构造就是**每一次**
  本地调用（ADR-0038 §4）。
- 计数是进程本地的。网关重启会在 run 继续服务（被接管）的同时把它们归零。页面明示这一集计
  窗口，而不是假装这些数字是终身统计。
- 新增第四个引擎在这里无需任何改动：计数挂在 `local` provider 上，而不挂在任何引擎的面上。

## 被否决的方案

- **抓取 `/metrics`** —— §1；退化为仅一个引擎，对其余引擎报「未知」，却自称是监控。
- **给 `FinOpsTracker` 加 per-model 维度** —— 它是一个按 tier 键控的成本追踪器，整体形状假定
  计费美元；本地模型是 `pricing: 0` 且无 tier。在那里加 per-model 维度等于在一张 tier 表上
  硬接第二根轴，而且仍会错过在途/aux 事实。
- **把计数持久化进 `runs.json`** —— §4；重启后读数陈旧。
- **用启动器既有轮询渲染监控** —— 启动器问的是单个模型的启动状态；看板需要每个 run 加聚合，
  为了同时服务两者而把轮询载荷翻倍，会把两个不同页面的成本耦合起来。
