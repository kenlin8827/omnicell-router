# ADR-0022: 出站代理——手动 URL 或托管的 Clash 核心

日期: 2026-11-13
状态: 已接受
约束: `backend/src/config/types.ts`（`ProxyConfig`）、`backend/src/utils/proxy.ts`、
`backend/src/utils/proxy-node.ts`、`backend/src/proxy/mihomo-*.ts`、
`backend/src/proxy/asset-download.ts`、`backend/src/routes/mihomo.ts`、
`frontend/src/pages/ProxyPage.tsx`、`frontend/src/pages/MihomoPage.tsx`。

## 背景

出站代理原来只有一个 URL（`proxy.url`）加上按 provider/model 的包含与排除列表。已经在用订阅客户端（Clash Meta / mihomo）的操作者只能手工把 `proxy.url` 指过去，控制台也不能切换节点。另外，`proxiedFetch` 把 `{ proxy }` 传给 `fetch`。这个选项在 Bun 上生效，在 Node 的 fetch 上被忽略，所以用 `node` 启动的网关会静默直连。

ADR-0018 的前向代理出口仍然只回答「走不走出站代理」，也仍然不看 `proxy.includes` / `proxy.excludes`。本记录只改变「出站代理」指的是哪个端点。

## 决策

### 1. `proxy.mode` 选择端点；默认是 `manual`

- `manual`（默认；`mode` 缺失或无法识别时也是它）——端点是 `proxy.url`，与从前完全一致。
- `mihomo`——端点是 `http://127.0.0.1:<proxy.mihomo.mixedPort>`（混合端口默认 7890）。此时忽略 `proxy.url`。

两种模式都按原来的顺序应用 `includes`、`excludes` 和 loopback 绕过。loopback 包含 External Controller，所以控制器调用不会再被送回混合端口。`outboundProxyUrl()`（前向代理出口，ADR-0018）使用同一个端点，仍然不看包含/排除列表。

`proxy.enabled` 仍是总开关——针对**出站流量**。sidecar 是否运行是另一条轴：由 `proxy.mihomo.autoStart` 决定这个进程该不该存在。因此核心可以在出站直连时继续运行（订阅照常刷新、节点持续探测、混合端口仍可供其它客户端使用），也可以在 `mode: mihomo` 保持不变的情况下被停止。

> **修订——运行策略拆分。** 早期版本要求 `enabled` 为真且 `mode` 为 `mihomo` 才运行 sidecar。这把两个问题混为一谈——「出站流量去哪」与「这个进程该不该存在」——导致核心无法作为独立能力使用：手动 URL 方案下没法让它保持预热，任何一次配置保存都会杀掉手工启动的实例。现在由 `autoStart` 承载意图（`true` 运行、`false` 被手动停止、缺省 = 跟随 `mode`），控制台的「启动/停止」按钮会把它写回配置；缺省时行为与旧规则完全一致，现有配置无需迁移。

> **修订 — `proxy.includes` 是白名单，没有规则就不走代理。**
> 早期版本把空的 includes 列表当作「全部走代理」：只要打开总开关并配好 URL（或 mihomo 核心），所有上游调用都会被代理，直到操作者写出例外。对网关来说这是错误的默认值——它会悄悄改变没有任何人要求代理的流量里凭据的走向，而在操作者眼里「我没配任何规则」就是「不走代理」。现在 `resolveProxyUrl` 在列表为空时返回直连（`proxy.enabled` 本身不再产生任何代理流量），excludes 仍先执行且仍强制直连。控制台把该状态显式渲染出来（代理分流页的「未配置包含规则，全部直连」提示），字段标签与配置注释统一改为白名单措辞。按主机生效的 `forwardProxy.rules` 不受影响：`outboundProxyUrl()` 不经过列表门控（ADR-0018 §4），`{ egress: proxy }` 行仍然只代理它点名的主机。原先依赖「全量走代理」的安装只需在 includes 里加 `*`（或逐 provider 的规则行），否则保持直连。
>
> **没有匹配目标的调用永远直连，加 `*` 也不会改变。** 白名单以 `{ provider, model }` 为键，不带该目标（目录同步 models.dev / OpenRouter、provider logo 拉取、更新检查）的调用因此无论 includes 写什么都直连——这是「按模型点名」的必然结果，不是第二道门控。在这些主机只能通过代理到达的网络上，这是一次**可见**的失败（目录/logo 同步会报传输错误），而不是悄悄改掉带凭据的推理流量走向——这是本修订主动选择的取舍。连通性探测（probe）不属于此类：它带 `{ provider, model }`，因此和真实推理一样受白名单约束，配了 `*` 就会走代理。

### 2. Sidecar 是生成的配置加一个本机控制器

网关把 mihomo 配置写到 `<env>/mihomo/`（`mixed-port`、`external-controller: 127.0.0.1:<controllerPort>`、`secret`、每个启用订阅一个 `proxy-provider`、一个代理分组（默认 `select`，见 `groupType`）、`MATCH` 到该组）。控制器已经健康就接管，否则执行 `mihomo -d <dir> -f <config>`。pid 文件和 `owner` 标记（`spawned` / `adopted`）记录是谁启动的。显式停止会结束本机监听。离开 mihomo 模式不再停任何进程——运行策略由 `autoStart` 决定；需要停时，也只结束本网关自己拉起的进程。启动时按同一策略无条件对账一次：进程该不该存在由 `autoStart` 决定，与配置的是哪种模式无关。每个 provider 还可以带 `proxy: <节点|分组>`（mihomo 的 provider 级 `proxy`）：下载是一条按规则匹配的 INNER 连接，留空即进入分组——在出现可用节点前就是直连；被本机网络阻断的订阅站点（TLS 握手超时、SNI 重置）需要在这里指定一个可达节点或分组。该名字按自由文本存储，不与运行中的代理表校验，因为是否存在是运行时事实；控制台提供选择器，但名字所属的 provider 消失后它仍会保留，只有该 provider 的拉取失败，不会让整份配置加载失败。

> **修订——本网关拉起的核心是它的子进程。** 核心是网关启动的基础设施，因此绑定在网关的生命周期上，而不是反过来：
>
> - 本网关拉起的核心在网关退出时被结束，控制台重启也不例外（重启监督进程会存活，这个子进程不会）。收尾在同步的 `process.on('exit')` 钩子里通过 `stopSpawnedMihomoSync` 完成，它只认得本进程亲手拉起或收编过的 pid——操作者自己的 mihomo（`adopted`）没有登记，永远不受影响。结束成功的收尾同时清掉指向该 pid 的标记，状态目录因此不会声称一个已经不存在的核心。
> - 任何阶段的启动失败（spawn 报错、立即退出、未就绪、端口占用）都会回收刚刚拉起的进程并清掉指向它的标记（回收失败则保留标记，让下一次启动的自愈还能找到幸存者），因此被拒绝的启动绝不会给下一次留下一个聋掉的监听者。核心自己的输出指名了拒绝原因（`bind:` / `address already in use`）时，失败归类为带端口的 `port-in-use`，与 `port-collision`（配置的混合端口与控制器端口相同）分开：前者要「关掉占端口的程序」，后者要「改端口数字」，两种动作不能共用一条提示。
> - 接管是有意收编：上一次网关留下的标记（`spawned` + 存活的 pid）被视为本网关形状的孤儿，从此在退出时一并结束。操作者自己启动的核心（`adopted`、无标记）跨越任何网关生命周期都保持运行；`spawned` 标记若指向的 pid 已死，则属于过期标记，改写为 `adopted`——控制器后面活着的核心不是它记录的那个。
> - 记录的 pid 存活却既没占住混合端口、也没占住控制器端口，说明它绑定失败：它不应答任何请求，却让此后的每次启动都撞端口，因此在拉起替代进程之前先被回收。
> - 被硬杀的网关（taskkill、断电）跑不了任何钩子；幸存者在下次启动时按上述规则接管——聋掉的回收，健康的收编并在之后随网关退出而结束。

二进制查找顺序是 `proxy.mihomo.binaryPath`，然后 `<ocrHome>/bin/mihomo`，然后 `PATH`。从 MetaCubeX/mihomo 的 GitHub release 下载是显式的管理操作，绝不是启动副作用。`selectedNodes` 在启动后通过控制器恢复：首次尝试是同步的（分组已加载就立即切回上次选中的节点，无需人工操作），订阅节点尚未下载完成时在后台重试 30 秒——启动绝不等待慢订阅。生成配置里的 `profile.store-selected` 让核心也能从自己的缓存恢复同一选择。
这个恢复只属于手动选择器：`url-test` / `fallback` 下选择权归核心，而 `PUT /proxies/{group}` 就是 mihomo 的 `Set`——一个在节点存活期间优先于核心自身延迟排序的钉选。因此自动分组在启动时跳过恢复，其自身的 `selectedNodes` 条目在每次保存时被清掉；其它分组的条目保留。
删除手动节点时，指向它的 `selectedNodes` 条目在同一次写入里一并清除——否则每次启动都会重放一个核心无法解析的节点名。

安装端点（`POST /api/admin/proxy/mihomo/install`）返回 NDJSON 而非单个 JSON body：release 资产下载过程中逐行推送 `progress` 事件（`downloaded` / `total` 字节，控制台据此显示百分比；宿主未返回 `Content-Length` 时退化为 MB 计数），最后恰好一个 `result` 携带安装结果。release 查询优先走 GitHub API 并带上共享的 `GITHUB_TOKEN` 请求头；匿名每小时配额返回 403/429 时回退到 release 页面重定向里的 tag，因此二进制下载不再依赖 API 配额。

核心自己的输出不再被丢弃：stdout/stderr 经管道进入一个有界、仅存在于内存的环形区（500 行，最旧的先丢），控制台的日志小节通过 `GET` / `DELETE /api/admin/proxy/mihomo/logs` 轮询与清空它；网关自己的 `core process started` / `exited` / `spawn error` 标记写进同一个环，因此即使面板里还留着上一个进程的遗言，重启也是可读的。这个环是进程生命周期证据，不是指标流：接管的核心不是这里拉起的，因此不贡献任何行；环刻意在核心崩溃后继续保留——退出前的那几行正是控制器给不出的诊断。核心的 `log-level` 仍是 `warning`，控制器密钥与订阅 URL 都不在它打印的内容里；网关在写入前剥掉 ANSI 颜色码并拼接未完成的行。

### 3. 密钥不进日志，归档默认脱敏

控制器密钥在为空时于首次启动生成，并经 `saveConfig` 写回。订阅 URL 可能内嵌令牌。两者都不写入日志。环境归档脱敏 `proxy.mihomo.controllerSecret` 和每条订阅的 `url`（扁平形状与 `upstream.proxy.mihomo.*` 都覆盖）。已登录的控制台仍然拿到 URL，因为操作者要在那里编辑。状态接口只报告 `secretConfigured`，不返回密钥本身。

### 4. Node 的 fetch 自己打开代理

在 Bun 上，`proxiedFetch` 继续使用 `fetch(url, { proxy })`。在 Node 上，HTTP 用绝对形式请求，HTTPS 用 `openViaProxy`（CONNECT）再在隧道上的 TLS 套接字上发送 HTTP/1.1。响应体是 web stream。重定向继续走代理，除非下一跳是 loopback。

### 5. 不提升 schemaVersion

新字段位于既有的 `upstream.proxy` 段内。缺失字段由 `loadConfig` 填默认值。这是值清洗，不是磁盘形状迁移（ADR-0016）。`schemaVersion` 保持 1。没有 `mode` 的文件维持 `manual`；但旧式的 `proxy.mihomo.enabled: true` 例外——这种形状早于 `mode`，仍然表示要启用核心。

## 后果

- 既有配置的代理行为不变。
- `egress: proxy` 的前向代理行使用同一个端点，因此 mihomo 模式也覆盖中转流量，不需要第二条 URL。
- 代理页按已配置的 `proxy.mode` 落在对应作用域：「代理设置」对应 `manual`，「Clash 核心」对应 `mihomo`——纯手动的安装因此不会一进来就停在「核心未运行」的卡片上。
- 管理面是 `/api/admin/proxy/mihomo/*`，以及代理页的六个小节（基本设置、订阅、节点、规则、连通性、日志）。依赖控制器的操作（选节点、测速、更新订阅）保持可点击；核心未运行时接口返回 409 `not-running`，控制台把它显示为本地化的“未运行”提示并跳转到基本设置标签的核心卡片（安装 / 启动），绝不直接显示传输层英文原文。控制器在传输层不可达（密钥已存在时）同样归为 `not-running`，而不是单独的传输错误。同一规则覆盖所有核心/安装失败码（`disabled`、`binary-missing`、`port-collision`、`port-in-use`、`spawn-failed`、`not-ready`、`spawn-exited`、`kill-failed`、`pid-unknown`、`unauthorized`、`reload-failed` 以及下载类码）：后端消息保留为日志用的英文诊断，控制台按 `code` 查 i18n 表，八种语言都有译文。核心运行期间混合端口与控制器端口输入框锁定（端口只在启动时生效，运行中修改会让控制台与进程状态静默不一致）；卡片会说明这一点，操作者停止核心后才能修改。代理页只有两级导航，绝不出现两排连续标签：页面自己的标签是「代理设置」（总开关、手动 URL、白名单与排除列表）与「Clash 核心」，Clash 的六个小节（基本设置、订阅、节点、规则、连通性、日志）是第二级里的左侧竖向菜单——切换小节是导航，因此读起来是菜单，而不是叠在页面标签下面的第二排 tab；导航条只包住自己的六行（不撑到页面底部），小节卡片撑满剩余页面高度并在内部滚动，文档本身永不滚动。基本设置里只有字段滚动：保存行是面板的 footer，钉在面板底边，操作因此永不离开屏幕（这里的字段才是高的那半，固定它是对的）；其余小节仍是整张卡片内部滚动，动作随卡片一起滚。核心操作按钮跟随核心状态：运行中「启动」禁用，未运行「停止 / 重启」禁用（各自以本地化提示作为 tooltip），核心运行期间「下载二进制」禁用（不能替换活进程的二进制），二进制已存在时按钮改称「重新下载」。操作者能读到的每个标签都写 **Clash**，不写「Mihomo」：用户认识的名字是 Clash，而 mihomo 只是核心的发布名。核心名只保留在三处——配置键 `proxy.mihomo`、`mode: mihomo` 字面量、二进制与缓存路径（`<ocrHome>/bin/mihomo`、`<env>/mihomo/`）——因为那是操作者必须亲手输入或到磁盘上找的事实，不是产品文案。ADR 正文在指核心进程本体时仍用「mihomo core」这个架构名词。节点列表按分组应答（`GET .../proxies?group=<name>`）：每行的类型与测速都从控制器实时快照解析；操作者切换分组时控制台重新拉取，而不是拿另一组的行去映射——那种映射会把新选中组的每个成员都标成「Unknown」（节点类型只有快照这一个真相）。节点表可按「测速」列排序（点表头在升序/降序之间切换，默认仍是配置顺序）；未测速不是 0 毫秒——`—` 行在升序和降序里都排在所有已测速节点之后，降序也不会把未测速的尾巴顶到最前。每条订阅都标出自动更新节奏（mihomo provider 的 `interval`）：只有核心运行期间才会按该间隔重新拉取，运行中保存订阅会重启核心使新间隔生效。每条订阅还指定自己下载时使用的代理（`proxy`）：跟随规则（进入 `MATCH` 分组）、本机直连（`DIRECT`——核心自己拨号，不读系统代理，这一点与 Geo 同步的「本机」腿不同）、策略组，或某个节点。选择器列出配置里的手动节点与核心已加载的订阅节点；已保存但当前列表给不出的名字仍以单独一行显示，而不是伪装成空值。订阅站点被本机网络阻断时，选一个可达节点即可修复。订阅面板把两个动词分开：列表上方的表单只负责新建（半填的新建表单不会再被误当成待保存的编辑），编辑某一行打开弹框，每行自带启用开关——启用/禁用是落在该行上的一次点击状态切换，不是藏在表单里的字段：停用的订阅仍留在列表里，但不会写进生成的 `proxy-providers`，也不参与自动更新；拨动开关即刻重建 sidecar。订阅时间戳按本地格式展示；从未拉取过的 provider 在客户端边界就丢掉时间戳——Go 把 `time.Time{}` 序列化成 `0001-01-01T00:00:00Z`，那是协议零值而不是远古日期，绝不能进入渲染出来的文案。 网关自己提供 PAC 文档（`GET /proxy.pac`，位于 `/api` 之外，在鉴权 preHandler 白名单里——它只是一个生成的脚本，不含任何密钥）。每次请求都按实时配置生成，因此控制台里的混合端口就是唯一真相；它携带了裸 host:port 无法携带的直连清单：回环、链路本地、私网（RFC1918、CGNAT 100.64/10）与 mDNS 名称返回 `DIRECT`，其余一律 `PROXY 127.0.0.1:<mixedPort>`，且对被代理的域名不提供 `DIRECT` 兜底——核心挂掉必须显式失败，不能悄悄绕过隧道泄漏流量。`proxy.includes` / `proxy.excludes` 不会映射进 PAC：它们匹配的是 provider/model 名，不是主机名。代理模式页的快捷添加是一个多选弹框，只来自**当前已连接**的 provider id（`<provider>/*`）；勾选只会**追加**规则行，绝不改写操作者手写的规则。不种任何预设：includes 为空等于不走代理（见下方修订），控制台绝不自造机器上不存在的厂商名。控制台（Clash面板 → 基本设置）把该 URL 放在按钮后面：点开弹框显示地址并提供复制。地址由网关按请求自身的 Host 头加网关端口拼出（`pacUrlFor`），绝不采用控制台文档的 origin：在 Vite 开发服务器下 `window.location.origin` 是 5174 的开发源，会随终端一起消失，也绝不是 OS 或浏览器该被指向的地址。因此状态载荷带上 `pacUrl`（旧网关不带该字段，按钮保持禁用），远程打开的控制台给出的仍是它被访问时的地址——URL 是参考资料而不是配置项，不该在表单里长期占一个只读输入框。

出站模式是 mihomo 自身的开关，与 `proxy.mode`（手动 vs. 核心）严格区分：`proxy.mihomo.routingMode` 取 `rule`（默认）/ `global` / `direct`。生成的配置只注入一条 `MATCH,<group>` 规则，因此当前 `rule` 与 `global` 的路由结果完全相同——仍然暴露这个选择器，是因为 `direct` 是比停止核心更轻的断流开关（控制器与订阅自动更新继续运行），且这是 mihomo 原生概念。控制台修改后既写入配置字段，也 `PATCH /configs {mode}` 热生效，无需重启；核心未应答时只保存、下次启动生效，并回 `live: false` 加提示，绝不假装已应用。读取时把保存值与核心实际报告的模式（`liveRoutingMode`）比对，不一致就显式提示，而不是让选择器谎报运行中的进程——但操作者自己的写入在途期间除外：选择器是乐观更新的，写入前的快照会被误读成偏离，于是每次切换都闪一下提示；等紧随其后的状态读取落定再恢复比对，真实偏离（核心拒绝、别的客户端改走）照样显示。字段与其他配置一样走白名单：未知字符串回落到 `rule`，绝不进入生成配置。PAC 只在客户端决定直连还是走代理，出站模式决定到达核心之后的流量怎么走——两者都存在，所以 PAC 的提示文案从不声称携带规则。

保存是**卡片页脚**，不是页头操作：按钮位于它所写入的那张卡片内、紧贴上方字段的左缘，后面跟「未保存的修改」徽标，作用域说明放在按钮旁的 InfoTip 里（页脚长段落没人看，还会和操作抢位置）——一次保存写的是整个 `proxy` 段（本卡片 + 另一个设置作用域），所以它不能被读成「保存这个字段」，也不该待在多作用域共用、但并非每个作用域都会写入的角落。

当前实际使用的节点是**所有作用域都会显示的页头微标**（运行中分组的 `now`，附协议与最近一次延迟），不是一条设置行：点它会切到 Mihomo → 节点并锚定到该行，该行在表格里带强调色竖条与「当前」徽标。因此「我现在走哪个节点」既不需要切页签，也不需要在上百行里找，筛选条件也遮不住这个答案。

节点页支持按订阅筛选与按协议类型筛选：两者都以真实值作键（provider id、协议名），且相互收窄——选了某个机场就不该再列出只属于另一个机场的协议。协议名不做翻译，`Vless` / `Hysteria2` 是用户要拿去和订阅对照的线路名，不是界面文案。某个筛选值的最后一个成员消失后，该筛选自动失效，而不是留下一个看起来空掉的分组。

节点也可以手工添加：`proxy.mihomo.manualNodes` 是白名单列表（`{ id, name, type, server, port }` 加上该协议自己的字段），渲染进生成配置的 `proxies:` 段，并与订阅节点的 `use` 一起加入策略组——不需要订阅，也不需要联网。协议白名单为 `ss` / `vmess` / `vless` / `trojan` / `hysteria2` / `http` / `socks5`；缺少该协议凭据的行在加载时被丢弃，绝不交给核心，因为一个畸形代理会让整份配置加载失败。控制台通过 `POST/PUT/DELETE /api/admin/proxy/mihomo/nodes` 增删改，每次写入都保存并重建 sidecar（与编辑订阅一致）；`GET .../proxies` 带 `manualId`，节点表只对自有行提供编辑/删除。节点名不得与内置项（`DIRECT`/`REJECT`/`PASS`/`GLOBAL`）或所选策略组同名，且手动节点之间唯一。密码与 uuid 属于凭据：环境归档脱敏，绝不写入日志。

节点行也可以直接录入 Clash 代理定义：控制台解析后把规范化映射存为 `yaml`，渲染时原样输出，因此原始映射在归档中整体脱敏。一次粘贴多个映射（或订阅文件的 `proxies:` 段）要么整批写入、要么整批拒绝；身份字段的校验与表单录入完全一致。编辑以表单为主，并且由同一张字段表（`manual-node-spec`）驱动三个方向：清洗表单草稿、把草稿渲染进映射、把已存映射反向投影回表单。`GET /api/admin/proxy/mihomo/nodes` 用这张表投影出表单字段（含 `reality-opts`、`ws-opts`、`grpc-opts`、`h2-opts`、`client-fingerprint`、`alpn`、`udp`、`tfo`、`ip-version`、ss 插件与 hysteria2 混淆/端口跳跃），所以粘贴录入的节点打开时表单是填满的；响应同时给出表单未建模的键名（`unmodeled`），控制台据此明示「这些键只在 YAML 页签编辑」，而不是悄悄藏起来。表单保存只覆盖这些键：清空的字段从映射中删除，未建模的键原样保留；白名单之外的协议只允许改名称/服务器/端口。非法输入返回 `400 {code: 'invalid-node-field', field}`，控制台把提示落到对应控件上。`GET .../nodes/catalog` 暴露协议/字段/枚举表，控制台不再手抄后端白名单；YAML 页签保留给表单未建模的键。

每个节点行还带一个 `source` 字段：`{ kind: 'subscription', id }`、`{ kind: 'manual', id }`，或 `{ kind: 'builtin' }`（mihomo 自有条目：DIRECT/REJECT/PASS，以及不对应任何已声明订阅的 provider 名）。控制台把它渲染为节点表的「来源」列，并用它构造来源筛选，因此手动节点和机场一样可筛选，不会在只有 provider 的筛选里消失。

添加节点对话框可以在写入前探测未保存的节点：此时核心还没有该节点的路由，因此对 server:port 做一次**直连 TCP**（5 秒预算；裸 socket 不读 `HTTP_PROXY`/`HTTPS_PROXY`，也不经过本网关的前向代理），只报告「可达/不可达」——不声称凭据或隧道可用。完整测速仍在节点表里对已保存的行做，那条路径才是刻意经过节点的。

失败的测速不是一次测量：mihomo 会把它报告为 `0`（history 条目、单节点测速或分组 map），客户端层把 `0` 归一为「未测量」，控制台因此显示 `—` 而不是误导性的 `0 ms`；批量测速还会清空响应里没有测到的行。整组批量测速在没有任何成员成功时回 504（`get delay: all proxies timeout`），旧构建对同一失败回 408；客户端把两者归一为同一个稳定的 `timeout` 码，控制台因此显示本地化的超时提示、把这些行结算为「超时」，而不是把控制器的原始状态码当成操作失败抛出来。
测速的路由由名字「住在哪里」决定。mihomo 的 `/proxies/{name}/delay` 只在自己那份代理表里解析——生成配置的 `proxies:` 段、策略组和内置条目；proxy-provider（订阅）成员只存在于自己的 provider 里，因此对这条路由会返回 404 `Resource not found`，哪怕节点本身完全健康。客户端因此先判定归属：配置内代理走配置作用域，provider 成员改走 `/providers/proxies/{provider}/{name}/healthcheck`（同一个 URL 测速，只是换到 provider 作用域），两边都不认识的名字报 `node-not-found`，而不是被当成「节点不可达」。

测速地址是**一个**配置项 `proxy.mihomo.testUrl`（http/https、不得内嵌账号密码，默认 gstatic 的 204 地址，即 mihomo 自身的 `DefaultTestURL`），不是列表：生成的策略组只有一个 `url`，"这次延迟是对谁测的"必须无歧义。控制台提供 Google 204 / Google / Cloudflare / OpenAI / Anthropic / Gemini 预设作为快捷方式，但输入框可自由填写；测速请求可以携带输入框里的当前值，因此未保存的修改立即生效（mihomo 的延迟测试接受任意 HTTP 状态码，带鉴权的端点同样能证明连通性）。

两种检查绝不混用：**测通**用核心的 delay 接口，经当前选中的节点去请求配置的 URL——同时证明隧道和 URL；**测速**测的是节点本身，未保存的节点只能直连 `server:port` 做 TCP 探测（不经过代理，因为核心还没有它的路由）。控制台按此区分展示，测通结果会注明经过的节点，以及核心实际请求的那个地址（输入框留空时即默认地址），因此结果永远不会描述一个操作者看不到的端点。测通失败不会另起一套「逐 URL 测速」的界面：它指向节点页的批量测速——那条路径已经回答了「这个地址是所有出口都不通，还是只有当前节点不通」。
候选端点的批量测通仍属于这**一个**字段的探路：一次动作把预设加输入框当前值经**当前**节点逐个探测并各自给出结果，结果只留在页面，选中赢家仍是一次普通的字段编辑——探测绝不改写核心健康检查所用的地址；反过来「这个地址是否所有出口都不通」仍交给节点页的批量测速，不另起测试界面。

节点表的「测速」列永远不是一个裸数字，而是五种状态之一：未测、测试中、超时、错误、已测量。mihomo 对不通的节点回的是延迟 0，若让它落进单元格就成了「0 ms」的谎话；同理，某一行正在测试时也不能继续显示上一次的数字。批量测速开始时把全部成员先置为「测试中」，结束后一起结算，因此结果陆续返回时排序不会跳动。测量值按 < 250 ms / < 400 ms / 更慢分档着色，而所有非测量状态在两个排序方向上都排在测量值之后——降序也不会把「—」顶到最前。控制台测得的读数按节点缓存 30 分钟，过期即丢弃，因为过了这个时长的数字已经不描述该节点。测速预算收敛成一个常量（`MIHOMO_DELAY_TIMEOUT_MS`，5 秒），控制器客户端的默认值与两个控制台接口共用它；接口各自接受按请求覆盖，覆盖值上限 20 秒。

选谁当节点是另一条轴：`proxy.mihomo.groupType` 取 `select`（默认，由控制台的节点选择决定）/ `url-test`（实测延迟最低者胜出）/ `fallback`（第一个可用的成员），配套 `groupInterval`（秒，30..86400，默认 60）与仅 `url-test` 使用的 `groupTolerance`（毫秒，0..5000，默认 50）。这个间隔是**故障检测窗口**而不是显示刷新：失效节点在下一轮测试前仍会继续承载流量（延迟读数也陈旧这么久），因此网关默认 60 秒而不是 mihomo 自身的 300 秒——后者意味着一个刚测完就挂掉的节点最多要等五分钟才被换掉。30 秒下限则避免「每个成员每轮一次真实请求」在大型订阅上变成对测试地址的模板攻击。生成的代理分组沿用同一类型、指向共享的测速 URL 并带上 provider 列表。自动分组刻意不含 `DIRECT` 成员：直连路由实测约 0 ms，`url-test` 会每一轮都选中它而静默绕过隧道，`fallback` 则会在某个节点失败时把全部流量交给它；手动分组保留 `DIRECT`，因为那是人主动选的。改动走配置保存（分组写在生成配置里，需要重启核心——不同于可直接 PATCH 热生效的出站模式）。节点页从代理列表响应里的 `groupType` 读取**运行中**分组的类型，自动分组下禁用手动选择并给出说明，控制台不会给出核心会忽略的点击。三个字段与其他配置一样走白名单与区间钳制，未知值回落到 `select` 与出厂默认。
手动批量测速不是第二条选择路径：它把每个成员在共享测速地址上的最新延迟写进核心，核心在下一次排序（受自身数秒级结果缓存约束，而不是等 `groupInterval`）时按同一容差重新排序；节点失效后跑一次批量测速，就是操作者缩短检测窗口的手段。

控制台还展示**正在运行的核心**实际加载的规则表（Mihomo → 规则，`GET /api/admin/proxy/mihomo/rules`，数据来自控制器的 `GET /rules`）：类型、匹配内容、出站目标都读自核心而不是网关写下的配置，因此被拒绝或丢弃的规则会显形，而不是靠假设。这也让 provider 的边界可核对：`proxy-providers` 只贡献**代理**，订阅文件自带的 `rules:` / `proxy-groups:` 一律不导入——屏幕上那张表就是网关生成的那张。核心未运行时接口回 409 `not-running`，控制台把它渲染成空表加一条本地化的「未运行」说明，绝不弹错误框。需要自己的分流时由操作者自己写：`proxy.mihomo.rules` 是一个**有序**列表（`{ type, payload, target }`），渲染在最后一条 `MATCH,<group>` 之前，先匹配先赢。目标保持符号化——`PROXY` 在渲染时才解析为当前配置的分组名，因此改分组名不会让某条规则悄悄指向一个不存在的名字。类型白名单是刻意收窄的：`DOMAIN`、`DOMAIN-SUFFIX`、`DOMAIN-KEYWORD`、`IP-CIDR`、`IP-CIDR6`、`GEOIP`、`GEOSITE`、`DST-PORT`、`SRC-PORT`、`PROCESS-NAME`、`PROCESS-PATH`。`GEOIP` / `GEOSITE` 依赖显式下载的地理数据库（见下方修正），缺库时保存与启动都会被拒绝；`RULE-SET`（加载时远程拉取）和逻辑规则直接拒收，因为求值不了的规则要么让配置加载失败，要么静默落到下一跳，而静默落空会改变出网路径。带列表分隔符的匹配内容同样丢弃。编辑器（`PUT /api/admin/proxy/mihomo/rules`）写整张列表并让核心按新配置生效，并且与上面那张只读表并存而不是取代它：可编辑的草稿和核心真正加载的内容是两个不同的事实。
订阅自带的规则可以**一次性**导入，接口是 `POST /api/admin/proxy/mihomo/rules/import`（`source: 'subscription' | 'text'`）。导入是一个**草稿**操作：解析订阅文件，把指向订阅自有 `proxy-groups` 的目标一律压平成 `PROXY`，跳过核心无法求值的内容（`RULE-SET`、逻辑规则）并计数，去重后把行返回给控制台，由控制台合并进可编辑列表——既不写盘也不下发给核心，只有操作者保存后才生效。网关不认识的出站目标默认映射为 `PROXY`（控制台提供勾选改为直接丢弃），避免机场自己的分组名变成死目标。刻意不做实时绑定：机场改一次订阅文件就会在控制台显示着另一种状态的同时悄悄改变出网路径，而规则的目标恰恰是这种意外代价最大的地方。
文档本身优先取自核心自己的 provider 缓存（`<workDir>/providers/<id>.yaml`）：那正是运行中配置实际使用的那一份，可离线工作，也能扛住订阅站点 TLS 链被本运行时拒绝的情况——而这恰好就是让联网导入不可用的那种失败（`fetch` 报 `unknown certificate verification error`，而核心早已成功接受同一个地址）。网络只作为兜底，并且控制台会明确告诉你这次用的是哪一种来源，而不是让你猜。
每条规则带一个 `source` 来源标签（`manual`、订阅名、`paste`，以及内置标签 `default` / `preset`）。它只是元数据——不写进 YAML、不参与求值——存在只为一件运维上的事：把来自同一处的规则归到一起，删掉某个订阅时可以按来源筛选后批量清理。导入是两段式的：先出可勾选、可筛选的预览，只有勾中的行才进入草稿；解析很便宜，改出网路径不便宜。规则章节一次只显示两个视图之一——「生效规则」（核心实际加载的）或「规则编辑」（草稿），绝不叠在一起：叠放时操作者判断不出哪些行真正在生效。长列表只在各自限高的容器里滚动，保存按钮固定在卡片底部，对话框本体不加滚动，因为嵌套滚动会藏行，还会让滚轮落到错误的容器上。

> **修正——界面上只叫 Clash。** 早先的版本把界面标成「Mihomo (Clash)」，让两个名字同时出现。这是错的：「mihomo」是核心的发布产物名，不是操作者认得的词，双名标签还让控制台看起来像有两个产品。所有面向操作者的文案——导航项、页面标题、模式选项、状态卡片、每条错误提示，以及写进 `config.json` 的注释——现在一律写 Clash。其余一概不动：配置键仍是 `proxy.mihomo`，`mode: mihomo` 字面量仍是 `mihomo`，管理路由仍是 `/api/admin/proxy/mihomo/*`，二进制仍用上游名，因此下载、查找与 PATH 解析都不受影响。

> **修正——局域网直连默认内置，国内分流是一键预设，地理数据是显式安装。** 规则表不靠操作者手写也有用，且没有任何规则依赖磁盘上不存在的文件：
>
> - `proxy.mihomo.rules` 缺失时 ⇒ 生成的配置带上局域网直连基线（`MIHOMO_LAN_DIRECT_RULES`，`source: 'default'`）：回环、RFC1918、CGNAT、链路本地，以及 IPv6 ULA / 链路本地网段 → `DIRECT`。这个键一旦存在（包括显式的空列表），保存的列表就是权威，基线永不回填，操作者删掉的默认行保持删除。「默认规则」对话框把操作者勾选的行（去重、只进草稿）补回来——这是它们唯一的回来方式。
> - 国内分流（`GEOIP,CN` + `GEOSITE,cn` → `DIRECT`，`MIHOMO_CN_DIRECT_RULES`，`source: 'preset'`）是**一键预设**，绝不是默认。核心规则作用于混合端口的全部客户端——包括 ADR-0018 中 `egress` 为 `proxy` 的转发代理行——因此一条默认的国内直连会让被操作者刻意走出口的国内厂商主机悄悄改走直连。预设对话框把这一后果写出来，而不是藏起来。
> - `GEOIP` / `GEOSITE` 在白名单里，但地理数据库（`geoip.metadb`、`GeoSite.dat`，共数十 MB）是向核心工作目录的**显式下载**（`POST /api/admin/proxy/mihomo/geo`，NDJSON 进度，与二进制同一个 MetaCubeX release 源，64 MB 上限；已有的非空文件保留，部分失败后重试只补缺的那个）。mihomo 自己会在解析需要它们的配置时下载这两个文件——而下载失败（离线机器、GitHub 被拦）会让核心**致命退出**，把网关自己的出网路径一起带走。因此两侧边界都在文件缺失时拒收带 geo 规则的列表：规则保存在落盘**之前**回 400 `geo-missing`（先写盘再失败会让配置和进程在之后每次启动时都对不上），sidecar 启动在 spawn 之前返回 `geo-missing` 码。生成的配置关闭 `geo-auto-update`；装好的文件离线使用、永不重复拉取。预设对话框先读 `GET /api/admin/proxy/mihomo/geo`，在行进草稿之前完成下载，代价以进度条呈现，而不是一次失败的保存。
> - 导入器把 `GEOIP` / `GEOSITE` 当作普通白名单类型（渲染时归一大小写：GEOIP 大写、GEOSITE 小写）；`RULE-SET`（加载时远程拉取）与逻辑规则既不在白名单也不在导入器里，按跳过计数。
> - 两组预设由后端提供（`GET /api/admin/proxy/mihomo/rules/presets`），与全新配置的种子读同一份声明；控制台侧再抄一份就是种子行的漂移双胞胎。

> **修正——测通有两条腿，不是一条。** 核心的 delay 接口回答「当前节点能否把这个 URL 拉回来」，回答不了「这台机器裸连通不通」；只有一个结果时，操作者无法把节点/订阅的故障和本机网络的故障分开。因此 `POST /api/admin/proxy/mihomo/test-url` 增加 `mode: 'tunnel' | 'machine'`（缺省 `tunnel`，即历史行为；任何其它值都是 400，绝不悄悄回落）。本机腿回答的是「这台机器自己的出网会怎么处理这个 URL」：系统代理启用时就走系统代理（`readOsProxyEndpoint`——WinINET 的 `ProxyEnable`+`ProxyServer`、macOS 当前启用的服务、或 GNOME 手动模式），并遵循该代理的绕过列表（`osProxyBypasses`：回环永远直连、`<local>`、WinINET 通配、CIDR、后缀域名、精确主机）；没有系统代理时裸直连。它不需要核心在跑。传输是裸 `net`/`tls` 写出的 HTTP/1.1（直连用 origin-form；经代理用 absolute-form，或 CONNECT + TLS，userinfo 转 `Proxy-Authorization`），之所以不用现成 HTTP 客户端，是因为在本运行时上 `fetch` **和** `node:http`/`node:https` 都会读环境变量里的 `HTTP_PROXY` / `HTTPS_PROXY`，而裸 socket 什么都不读（实测：死掉的环境代理会同时拦下 `fetch`、`fetch(url, { proxy: '' })` 与 node 的 HTTP 客户端），用客户端栈回答的就成了「命令行环境说什么」而不是「系统配置做什么」。环境代理被刻意忽略——它只是启动环境的产物。PAC（`AutoConfigURL`）在这里无法求值，回落为直连。响应带上 `via: 'direct' | 'system-proxy'`，走代理时还带实际使用的 `host:port`。控制台在测通页顶部放一个两态开关（经 Clash 节点 / 本机网络），结果按 (URL, 腿) 分开存，切换不丢另一侧的答案。刻意没有第三个「经 Clash 的 DIRECT 出站」模式，也不以系统代理归属设门：本机腿在任何状态下都回答一个有意义的问题。当 Clash 自己持有系统代理时，本机腿必然与节点路径重合——页面用一条琥珀色说明点破，让这一对结果读作「整机全链路对照」，而不是与节点无关的基线。

> **修正——页面叫「Clash面板」，核心仍叫「Clash 核心」。** 导航项、面包屑与页内子导航标签由「Clash 核心」改为「Clash面板」。旧名只点出一个部件，而这一页装着核心启停、订阅、节点、规则、连通性五块，且在开发语境里容易被读成网关自身的 core。不选「控制台」：它在本项目里指整个网关管理界面（登录、访问控制、所有页面都在其内），在代码语境里又指终端，Clash 生态里的「控制台」还是 yacd / metacubexd 那类实时流量看板，与这一页的表单形态不符；不选「管理」：上级分组已叫「代理管理」，叠词且语义偏空。「面板」具体，又不抢这两个词。三层语义就此定死：**控制台**＝整个网关界面，**Clash面板**＝其中一个页面，**Clash 核心**＝被管理的进程。因此状态卡片、每条错误提示以及写进 `config.json` 的注释仍称运行中的进程为「Clash 核心」。i18n 键名、`/proxy-clash` 路由、`proxy.mihomo` 配置键与二进制名一律不动。

> **修正——系统代理目标集中到一个「系统代理」页面。** Clash面板不再提供「设为系统代理」：指派 OS 指针（在入站转发代理与混合端口之间启用或切换）属于「代理」分组下专用的「系统代理」页面，页面并排呈现两个目标，通过与入站卡片**同一套**所有权模块写入（见 ADR-0018 修订——单一快照槽、切换目标不重拍 OCR 之前的快照、还原恢复原始设置）。该操作即时生效，刻意排除在任何页签的配置保存之外；启用 Clash 目标以核心运行中为前提，核心在持有系统代理期间被停止时该页面会告警。其余表面只保留状态——入站卡片及其设置向导、Clash面板、出站页显示所有者、绕过 / 环境变量文案与还原动作，并各自链到系统代理页（`/proxy-system?target=forward|clash`）做启用与切换。

> **修正——地理数据按操作者的指令同步，走操作者选定的腿。** 安装是显式的，更新同样是：两个数据库绝不自行重拉（`geo-auto-update` 保持关闭）；已安装的一对文件超过 `MIHOMO_GEO_STALE_DAYS`（30 天）后，`GET /api/admin/proxy/mihomo/geo` 报 `stale`，控制台显示「建议同步」徽标——只是提醒，永不阻止启动，数据陈旧的核心照常能起。基本设置新增 Geo 卡片（文件、大小、更新时间、陈旧徽标、一个同步按钮、本机/节点腿切换），下载不再只能作为国内预设的副作用触达。
>
> `POST /api/admin/proxy/mihomo/geo` 接受 `leg: 'machine' | 'node'`（缺省 `machine`；其它任何值都是 400，绝不悄悄回落）与 `refresh: boolean`。本机腿是默认，因为它总能作答：系统代理启用时就走系统代理（与测通本机腿同一对 `readOsProxyEndpoint` + `osProxyBypasses`，按 URL 逐一判断，重定向到 `objects.githubusercontent.com` 时按它自己的主机判断绕过），否则直连——核心没跑也能用。节点腿走混合端口，因此只要真的会发生下载就要求核心**正在运行**（`getMihomoStatus`，而不是仅凭配置了控制器）；核心没跑时路由在发出任何下载请求之前就返回 `not-running`。有一个取舍直说而不藏：本运行时上的直连下载仍然会遵循环境变量里的 `HTTP_PROXY` / `HTTPS_PROXY`，与本进程里其它 `fetch` 完全一致。系统代理才是这条腿的定义，环境变量只是启动残留。
>
> 「同步」意味着**替换**：`refresh: true` 时即使文件已在也重下两个文件，各自先写临时文件再改名覆盖，刷新失败保留可用的旧文件——操作者的同步绝不拿可用的数据库换一个坏的。不带 `refresh` 时，已存在的非空文件被跳过；这正是国内预设走的方式（只补缺的，不重拉已有的）。

> **修正——下载中断可以续传，字节要被校验。** 两处下载都是从 GitHub 拉数十 MB，而这条链路上中途 503、连接重置是常态；从前失败即整段作废：下一次点击从零重拉，发起它的那个控制台页签还在后台继续下载，因为没有任何东西观察到操作者已经离开。规则还各写各的——二进制用 `.download` 暂存且完全不校验，地理数据库只有上限与改名。
>
> `proxy/asset-download.ts`（`assetPartPaths`、`downloadAssetToFile`、`cleanupAssetPart`、`withAssetLock`、`parseAssetDigest`、`AssetSidecar`）把一个资源的传输收在一处，规则只说一遍。暂存文件是 `<target>.part`，旁边的 sidecar `<target>.part.json` 记 `{ url, etag, lastModified, sha256?, size, savedAt }`——分段与让它得以安全续传的验证符同行，绝不单独留下其一。只有在 sidecar 未超过分段保留期（24 小时）、指向同一个 URL、且至少带一个响应原样回送的实体验证符时，才发出 `Range: bytes=<size>-`；刻意不用 `If-Range`，比较在代码里明写。206 的 `Content-Range` 总长与记录值不符 ⇒ 分段作废、从零重来；总数一致的 416 是主机在说「你已经有了」⇒ 从磁盘重走校验。字节进度按 `size + written` 计，续传条从操作者离开的位置开始走。
>
> 校验锚在发布方，绝不是拿同一份响应自证一致。mihomo 的 release API 为了定版本本来就要回资源清单，每项自带 `digest`，因此校验二进制不多花一次请求；meta-rules-dat 在数据库旁边发布 `geoip.metadb.sha256sum`，地理侧尽力取那个同目录兄弟文件。主机不给摘要时退化为实体验证符，绝不停下下载；摘要对不上时分段销毁并回 `checksum-failed`——重试救不了，所以控制台说出是哪个文件、什么原因，而不是一句「安装失败」。
>
> 失败保留分段，因为下一次点击会接着传。例外——超出体积上限、写盘失败、校验不符、sidecar 过期或不匹配、显式重新同步、以及一个字节都没落盘的取消——各自删除分段，坏分段绝不让调用方陷入死循环；下载校验都过却解不开包的资源由调用方同样销毁。`installMihomoBinary` 因此先写入校验通过的压缩字节，再在 `withAssetLock(<part>)` **之内**解包，两段一起串行：从前两个页签会交错写同一个目标，并把撕坏的文件改名就位。
>
> 取消是穿透的，而且是**显式**的。`signal` 沿 `api.installMihomo` / `api.downloadMihomoGeo` → NDJSON 路由 → `installMihomoBinary` / `downloadMihomoGeoAssets` → `downloadAssetToFile`。做不到的是察觉操作者离开：在 Bun 1.3.14 加 Fastify 5 上实测，客户端丢下一个被 hijack 的 NDJSON 响应不管怎么表现——不关 socket、reader 被后台页签冻住、只隐藏不卸载——请求、响应、socket 三者的 `close` 在响应自然结束之前一个都不会触发，排在已接受但没人读的 body 后面的 `write()` 回调同样永不执行。于是只被隐藏的页签留下一段下载在无人接收地继续跑，下一次点击也接不上它的位。路由把在途的 controller 记在按腿命名的登记表里（`liveTransfers`，键为 `core`、`geo:machine`、`geo:node`，传输开始登记、handler 结束销账），并暴露 `POST /api/admin/proxy/mihomo/transfers/cancel { leg }`：一次调用只 abort 那一条腿，腿不在跑就回 `cancelled: false`——键写错或者早已过期，是无操作，不是报错。MihomoPage 在操作者按取消、以及页面卸载时调用它，卸载那一次带 `keepalive: true`，因为后台页签的 reader 会被冻结，页面自己的流 promise 就不是可靠的离开信号。同一条腿上的第二次点击会先等这次 cancel 被确认、再交出新 signal——等待是有上限的，确认悬住只是让同一个资源锁短暂重叠，不至于把按钮卡死；卸载那一次是发了就不管，因为组件已经不在了。`raw.on('close')` 保留，作为真会上报断开运行的兜底：它必须跳过正常结束（`writableEnded`——干净的 `raw.end()` 同样触发 `close`），并且带原因 abort。
>
> 停下来的字节必须活下来，否则续传就是假话。传输被中途切断时写盘队列是 flush（`end()`）而不是丢弃：实测带着缓冲字节 destroy 一个写流，只留下 0 字节的 `.part`，取消后重新点击反而整段重拉。一个字节都没落盘的分段不留 sidecar——孤零零的验证符会让从零重来看起来像续传。

> 取消是**结果**，不是失败，而且只属于一条腿。每个 `abort()` 都带原因：路由以 `client disconnected` abort，页面说出自己的原因（`<leg> download cancelled by the operator`、`page closed during the <leg> download`）；页面按腿各持一个 controller（`useTransferAbort`），所以点 Geo 同步再也打不断正在跑的核心安装。不带原因的 `abort()` 正是那句引擎原文 "signal is aborted without reason" 被包成笼统"操作失败"的来源。两条 abort 路径都回 `download-aborted`，控制台按"传输已中断、下次点击接着传"渲染；路由的 catch 把 `signal.aborted` 映射到同一个 code 而不是 `install-failed`；流 promise 以 abort 拒绝时什么都不弹。
>
> 新代码沿用既有结果形状：`download-incomplete`、`download-aborted`、`checksum-failed`（两腿同一个码——字节栽在同一条检验上），安装结果另加 `resumedFrom` / `verified`。

`.download` 作为**传输暂存名**退役：再没有东西往它里面下载，地理腿直接把校验过的 `.part` 改名就位，数据库因此不再回读进内存。它在另一处换了含义继续存在——安装路径把**解开后**的可执行文件写到那里再做最后一次改名，因为那些字节与 `.part` 里装的压缩包本就不是同一样东西。地理腿旧文里「各自先写临时文件再改名覆盖」的说法由这句替换：`refresh: true` 依然不会拿可用的数据库换一个坏的。
