# ADR-0037 — 本地模型运行时：下载完整性、分层规划、运行所有权

- 状态：已接受（已实现）
- 日期：2026-11-26

## 背景

本地模型控制台此前已经能安装引擎、下载或导入 GGUF 文件，但闭环到此为止：没有任何东西能**运行**模型，而已存在的部分底下还埋着三个缺陷。

- **Gated 模型下载静默失败。** 运营者在「本地设置」里保存的 HuggingFace token 从未到达下载路径，因此无论配置什么，gated 仓库都回 401。下载也没有任何完整性校验——一个被截断的文件看起来已安装，直到有人真的去读它。
- **一个引擎只有一份安装。** llama.cpp 按加速器分别发布构建（CPU / Vulkan / CUDA），而存储层每个引擎 id 只保留一条记录，装 Vulkan 构建会挤掉 CPU 构建。运行页要求运营者在启动时选择引擎，但当同一时间只能存在一份构建时，这个选择毫无意义。
- **没有人知道一个文件是什么。** 注册表只存名字/大小/仓库，因此分层规划、引擎支持徽标、上下文阶梯全都无从谈起——llama.cpp 需要的参数（`-ngl`、`-c`）只能靠猜。

本记录把闭环补上（下载 → 导入 → 规划 → 运行），并修掉底下的三个缺陷。

## 决策

### 1. 下载经 settings 链认证并校验完整性

每一个 HuggingFace 请求——搜索、文件列举、模型下载本身——都通过 `resolveHfToken()`（控制台设置 → 环境变量 → 无）解析 token，与设置页测试所用的是同一条链。因此 gated 仓库恰好在运营者保存了有效 token 时可用；不存在第二个凭据面。

下载路由从调用方接收 `size` + `sha256`（校验 hex-64）——模型市场页传入 HF API 为该文件声明的值——并在注册模型之前校验暂存字节。校验失败则传输失败、残缺文件不进注册表；本地文件导入与字节无关，跳过校验（运营者自己就是来源）。

### 2. 一个引擎、多份构建 target——状态键是 `engine:target`

引擎安装状态以 `engineInstallKey(engineId, target)` 为键，安装目录为 `engines/<id>/<version>-<target>`，因此 llama.cpp 的 CPU 与 Vulkan 构建可以共存、独立卸载（DELETE 必须携带 `?target=`）。传输 leg 为 `engine:<id>:<target|auto>`——`auto` 只在解析器尚未选出具体 target 时出现。遗留的单 target 记录在**读取时**归一化（从目录布局推断其 target）；没有任何写路径再产生旧形状。

运行页的引擎选择器为每个已安装的 `(engine, target)` 对列一行——运行时选引擎选的是这个对，永远不是裸引擎 id。

某个发布**实际**提供哪些目标是运行时事实，不是目录知识：`GET /engines/availability` 解析每个引擎的当前发布（缓存 10 分钟），通过与安装器同一个 `matchAssets` 回答每个目标的可用性，因此发布没有携带某目标资产时，控制台直接禁用对应 chip，而不是等安装点击才失败。探测失败是软失败——离线机器保持所有 chip 可用。（Strata 的 CUDA 尾部 `cuda-<variant>` 就在这里：资产 `…-cuda-cuda13.tar.gz` 对应目标 `cuda13`；hip/sycl/metal 的尾部等于目标 id。）

llama.cpp 的发布遍历只把携带 `llama-<tag>-bin-*` 资产的发布算作有效：稳定版 `v*` tag 只带一个 `nightly-tag.txt` 指针文件，且发布当天排在发布列表**最前**，若按“有任意资产即算数”就会解析到这个指针发布，把所有构建目标报为不可用（2026-11-26 的 v1.1.0 事件）。`listTags` 应用同一过滤，版本选择器永远不会给出任何目标都无法安装的 tag。

### 2a. 更新即重装，升级会回收被替换的版本

没有单独的更新端点，也没有需要移动的版本锁：**更新就是对已存在的 `(engine, target)` 发起同一次安装调用**，由它解析当前发布并解包进按版本命名的目录。

由此，升级发现退化为比较控制台本来就拿到的两个值——安装记录上的版本，与当前发布**会给这个目标装**的版本（`availability.targets[target].version`，缺失时回退到发布 tag）。比较必须读每目标版本，不能只看 tag：llama.cpp 两者相同，但 Strata 的 tag（`v0.2.22`）与从资产名解析出的引擎版本（`0.1.69`）是两个不同的串，拿记录去比 tag 会让每一次 Strata 安装永远显示为过旧。更新按**每个安装**给出，而不是按卡片——同一引擎的一份目标可能已最新，另一份还落后。

由于状态键是 `engine:target`，这条记录是版本目录的唯一指针：覆盖它就让被替换的目录变得不可达。因此 `installEngine` 报告 `supersededDir`（仅当目录仍存在时才带）由安装**路由**删除——在新记录落盘之后，且仅当没有运行仍钉住其中的二进制时（`runs.json` 记录二进制绝对路径；运行中引擎的二进制不能从它脚下消失）。安装器本身仍然对 run 一无所知；因活跃运行而保留下来的目录只是浪费磁盘，绝不构成损坏的安装，因为记录已指向新构建。回收在安装结果发出**之前**完成，因此该结果触发的刷新永远不会渲染出一条已消失版本的行。

### 3. 模型身份即 GGUF 头，缓存到注册表行

`readGgufMeta`（`backend/src/local/gguf.ts`）最多扫描文件头部 16 MB，只收集标量元数据 kv 对（数组跳过、值绝不物化），并在遇到第一个 `tokenizer.*` 键时提前停止——规划器需要的一切都在它之前。v2 与 v3 头都能解析。

`listInstalledModels` 对每个未标注的文件懒扫描一次，并把结果回写到注册表行（`InstalledModelMeta`：arch / layers / maxCtx / experts / heads / kvHeads / headDim / embedding）。`engineSupportFor` 从 arch 推出控制台渲染的两个徽标轴：

- `runnable`——能运行该文件的引擎（GGUF → `['llamacpp']`）。
- 信息性的 `moe` / `strataFamily`——MoE 架构，以及其中 Strata 自带控制面所服务的精选家族（见 §6）。

徽标是对文件的**读取**，绝不是从文件名猜测。

### 4. 分层规划即启动真值

`planPlacement`（`backend/src/local/plan.ts`）同时被 `/plan` 预览路由和 `startLocalRun` 调用——控制台展示的数字就是运行器传入的数字，因为它们来自同一次调用：

- 运行选项中的 `ctx 0` 解析为 `autoCtx`（在内存预算内不减速的最大阶梯值，8K–131072）；
- `ngl -1` 解析为 `nglForPlan`——规划放得下显存时为全部层（llama.cpp 的 `999` 写法），否则为规划器给出的层数。

分层执行**就是** llama.cpp 的 `-ngl N`：N 层放显存，其余由内存承载，超出内存预算的部分从磁盘流式读取（mmap）。规划器按检测到总量的 92% 预算显存并预留 400 MB 运行时开销，为系统保留 4 GB 内存，并从 GGUF 头估算 KV 缓存几何（`heads`/`kvHeads`/`headDim`，F16 = 2 字节/元素，Q8_0 = 1.125）。速度预估是带宽模型（显存 ≈ 250、内存 ≈ 110、磁盘 ≈ 50 GB/s）——只是展示数字，绝不做门槛。

同一次 `/plan` 响应还带一份机器快照（GPU 名称、显存总量与空闲、内存总量与空闲），供运行页的「这台电脑」卡片使用。它走 60 秒探测缓存（§7），不进入 `planPlacement`。空闲低于估算时，启动按钮旁给警告，绝不因此重算 `-ngl` 或 `ctx`。

### 5. 运行所有权沿用 mihomo sidecar 原则（ADR-0022）

一次 RUN 是一个已启动的 `llama-server` 进程，通过其 OpenAI 兼容 API 服务一个注册模型。运行记录持久化为 `<ocrHome>/engines/runs.json`，重启绝不丢失对存活服务器的追踪：

- 由**本网关派生**的运行绑定网关生命周期——`stopSpawnedLocalRunsSync` 在 `process.on('exit')` 时杀掉它，与 `stopSpawnedMihomoSync` 同一原则。
- 启动时 `restoreLocalRuns` **收养** pid 仍应答健康端点的幸存者（记录继续服务；其日志环从空开始），并关闭进程已消失的所有记录。
- `starting` → `ready` 在首次健康轮询时迁移（`/health`，503 = 仍在加载，`/v1/models` 兜底）；超过 `LOCAL_RUN_READY_TIMEOUT_MS`（10 分钟）仍在加载的运行被杀掉并标记失败——卡死的加载不是服务器。
- 崩溃自动重启有界（`LOCAL_RUN_MAX_RESTARTS` = 每 `LOCAL_RUN_RESTART_WINDOW_MS` = 5 分钟 3 次，稳定服务后计数重置），且只在运行自己要求时发生。

端口从 `DEFAULT_LOCAL_RUN_PORT`（4800）起通过 `net.createServer` 探测分配——绝不固定，也绝不随机到控制台无法预测。进程输出进入每 run 的内存日志环（`MIHOMO_LOG_RING_CAPACITY`），由「运行日志」抽屉轮询；**任何东西都不落盘**。启动统一带 `-lv 4`：近期 llama.cpp 构建只在这个详细级别打印设备枚举与按设备的显存明细，而日志抽屉正是靠这些行来证明各层确实落到了规划所选的那块 GPU 上。

### 6. llama.cpp 是无条件的唯一运行目标；Strata 需要 profile

> **由 ADR-0038 §4 修订。** 下面的规则对“仅凭文件即可推导启动规格”的引擎原样保留。Strata 的启动输入（pack / PLE 表 / MTP draft 头 / expert profile）无法从 GGUF 头推导，因此当运营者能以模型记录上的 profile 提供它们时，Strata 就成了真正的运行目标。逐字保留的不变量是：**徽标永远不是启动路径** —— 仅有 `strataFamily` 仍然什么都不启动，缺 profile 时 `engine-cannot-serve` 仍然拒绝，并点名缺的正是它。

Strata 的控制面只服务它自己的精选 MoE 家族——它无法加载任意 GGUF——因此对 `strata` 引擎 `startLocalRun` 最初返回 `engine-cannot-serve` 并附上解释，控制台也把它从引擎选择器中灰掉。Strata 保持可安装（运营者可能要用那个应用本身），信息性的 `strataFamily` 徽标告诉运营者某个已下载的 MoE 模型**也**适合 Strata 应用。徽标永远不是启动路径。

### 7. 探测有缓存；规划绝不重复探测硬件

`/plan` 路由把依赖探测报告（GPU/显存枚举）缓存 60 秒——面板在每次选项变化时重新请求，而每次防抖都去探一次 PCIe 是浪费。`startLocalRun` 则重新探测：启动那一刻数字必须为真。

## 影响

- 闭环成立：市场下载（含 gated）/ 文件导入 → 徽标 → 自动分层规划预览 → 启动 → 端点 → 日志，全部针对同一个注册表。
- 纯 CPU 与 GPU 构建共存，运营者按启动选择构建——同一模型无需重装即可在任一者上运行。
- 已安装的构建不会悄悄过期：控制台拿它与当前发布给同一目标所提供的版本作比较并就地给出更新；接受更新会回收被替换的版本，不留不可达的目录。
- 运营者读到的规划**就是**启动配置；预览与进程参数出现偏差即定义上的 bug。
- 网关重启既不会遗弃自己启动的服务器，也不会杀掉仅仅收养的服务器。
- Strata 永远不会半吊子工作：要么是 Strata 应用服务它自己的家族，要么它就不是运行目标。

## 修订 — 2026-11-26：资源档位与机器面板

- 规划器新增一个输入 `headroom`（默认 true）：运行页的「电脑资源」开关
  （留出空间 / 全部性能）在两组预算常量之间切换，常量只在 `plan.ts` 声明一次
  （显存比例 0.92/0.97，内存预留 4/2 GiB）。启动路径传递同一个值，预览条与
  实际 `-ngl` 永不分叉。引擎自管放置忽略它——控制台在那里不提供资源开关。
- plan 响应同时携带「这台电脑」卡片读取的机器事实（`gpus`、`vramFreeMb`、
  `ramFreeBytes`）、ctx 选择器渲染的后端权威 `ctxLadder`（前端不再有镜像副本），
  以及规划结果的 `ramReserveBytes`，任何文案都不再硬编码预留数字。
