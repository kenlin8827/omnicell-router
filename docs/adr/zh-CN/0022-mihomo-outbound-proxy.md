# ADR-0022: 出站代理——手动 URL 或托管的 Mihomo 核心

日期: 2026-11-13
状态: 已接受
约束: `backend/src/config/types.ts`（`ProxyConfig`）、`backend/src/utils/proxy.ts`、
`backend/src/utils/proxy-node.ts`、`backend/src/proxy/mihomo-*.ts`、
`backend/src/routes/mihomo.ts`、`frontend/src/pages/ProxyPage.tsx`。

## 背景

出站代理原来只有一个 URL（`proxy.url`）加上按 provider/model 的包含与排除列表。已经在用订阅客户端（Clash Meta / mihomo）的操作者只能手工把 `proxy.url` 指过去，控制台也不能切换节点。另外，`proxiedFetch` 把 `{ proxy }` 传给 `fetch`。这个选项在 Bun 上生效，在 Node 的 fetch 上被忽略，所以用 `node` 启动的网关会静默直连。

ADR-0018 的前向代理出口仍然只回答「走不走出站代理」，也仍然不看 `proxy.includes` / `proxy.excludes`。本记录只改变「出站代理」指的是哪个端点。

## 决策

### 1. `proxy.mode` 选择端点；默认是 `manual`

- `manual`（默认；`mode` 缺失或无法识别时也是它）——端点是 `proxy.url`，与从前完全一致。
- `mihomo`——端点是 `http://127.0.0.1:<proxy.mihomo.mixedPort>`（混合端口默认 7890）。此时忽略 `proxy.url`。

两种模式都按原来的顺序应用 `includes`、`excludes` 和 loopback 绕过。loopback 包含 External Controller，所以控制器调用不会再被送回混合端口。`outboundProxyUrl()`（前向代理出口，ADR-0018）使用同一个端点，仍然不看包含/排除列表。

`proxy.enabled` 仍是总开关。sidecar 只在 `enabled` 为真且 `mode` 为 `mihomo` 时运行。

### 2. Sidecar 是生成的配置加一个本机控制器

网关把 mihomo 配置写到 `<env>/mihomo/`（`mixed-port`、`external-controller: 127.0.0.1:<controllerPort>`、`secret`、每个启用订阅一个 `proxy-provider`、一个代理分组（默认 `select`，见 `groupType`）、`MATCH` 到该组）。控制器已经健康就接管，否则执行 `mihomo -d <dir> -f <config>`。pid 文件和 `owner` 标记（`spawned` / `adopted`）记录是谁启动的。显式停止会结束本机监听。离开 mihomo 模式时，只停止本网关自己拉起的进程。

二进制查找顺序是 `proxy.mihomo.binaryPath`，然后 `<ocrHome>/bin/mihomo`，然后 `PATH`。从 MetaCubeX/mihomo 的 GitHub release 下载是显式的管理操作，绝不是启动副作用。`selectedNodes` 在启动后通过控制器恢复：首次尝试是同步的（分组已加载就立即切回上次选中的节点，无需人工操作），订阅节点尚未下载完成时在后台重试 30 秒——启动绝不等待慢订阅。生成配置里的 `profile.store-selected` 让核心也能从自己的缓存恢复同一选择。
这个恢复只属于手动选择器：`url-test` / `fallback` 下选择权归核心，而 `PUT /proxies/{group}` 就是 mihomo 的 `Set`——一个在节点存活期间优先于核心自身延迟排序的钉选。因此自动分组在启动时跳过恢复，其自身的 `selectedNodes` 条目在每次保存时被清掉；其它分组的条目保留。
删除手动节点时，指向它的 `selectedNodes` 条目在同一次写入里一并清除——否则每次启动都会重放一个核心无法解析的节点名。

安装端点（`POST /api/admin/proxy/mihomo/install`）返回 NDJSON 而非单个 JSON body：release 资产下载过程中逐行推送 `progress` 事件（`downloaded` / `total` 字节，控制台据此显示百分比；宿主未返回 `Content-Length` 时退化为 MB 计数），最后恰好一个 `result` 携带安装结果。release 查询优先走 GitHub API 并带上共享的 `GITHUB_TOKEN` 请求头；匿名每小时配额返回 403/429 时回退到 release 页面重定向里的 tag，因此二进制下载不再依赖 API 配额。

### 3. 密钥不进日志，归档默认脱敏

控制器密钥在为空时于首次启动生成，并经 `saveConfig` 写回。订阅 URL 可能内嵌令牌。两者都不写入日志。环境归档脱敏 `proxy.mihomo.controllerSecret` 和每条订阅的 `url`（扁平形状与 `upstream.proxy.mihomo.*` 都覆盖）。已登录的控制台仍然拿到 URL，因为操作者要在那里编辑。状态接口只报告 `secretConfigured`，不返回密钥本身。

### 4. Node 的 fetch 自己打开代理

在 Bun 上，`proxiedFetch` 继续使用 `fetch(url, { proxy })`。在 Node 上，HTTP 用绝对形式请求，HTTPS 用 `openViaProxy`（CONNECT）再在隧道上的 TLS 套接字上发送 HTTP/1.1。响应体是 web stream。重定向继续走代理，除非下一跳是 loopback。

### 5. 不提升 schemaVersion

新字段位于既有的 `upstream.proxy` 段内。缺失字段由 `loadConfig` 填默认值。这是值清洗，不是磁盘形状迁移（ADR-0016）。`schemaVersion` 保持 1。没有 `mode` 的文件维持 `manual`；但旧式的 `proxy.mihomo.enabled: true` 例外——这种形状早于 `mode`，仍然表示要启用核心。

## 后果

- 既有配置的代理行为不变。
- `egress: proxy` 的前向代理行使用同一个端点，因此 mihomo 模式也覆盖中转流量，不需要第二条 URL。
- 代理页按已配置的 `proxy.mode` 落在对应作用域：「代理设置」对应 `manual`，「Mihomo (Clash)」对应 `mihomo`——纯手动的安装因此不会一进来就停在「核心未运行」的卡片上。
- 管理面是 `/api/admin/proxy/mihomo/*`，以及代理页的五个小节（基本设置、订阅、节点、规则、连通性）。依赖控制器的操作（选节点、测速、更新订阅）保持可点击；核心未运行时接口返回 409 `not-running`，控制台把它显示为本地化的“未运行”提示并跳转到基本设置标签的核心卡片（安装 / 启动），绝不直接显示传输层英文原文。控制器在传输层不可达（密钥已存在时）同样归为 `not-running`，而不是单独的传输错误。同一规则覆盖所有核心/安装失败码（`disabled`、`binary-missing`、`port-collision`、`spawn-failed`、`not-ready`、`spawn-exited`、`kill-failed`、`pid-unknown`、`unauthorized`、`reload-failed` 以及下载类码）：后端消息保留为日志用的英文诊断，控制台按 `code` 查 i18n 表，八种语言都有译文。核心运行期间混合端口与控制器端口输入框锁定（端口只在启动时生效，运行中修改会让控制台与进程状态静默不一致）；卡片会说明这一点，操作者停止核心后才能修改。代理页只有两级导航，绝不出现两排连续标签：页面自己的标签是「代理设置」（总开关、手动 URL、包含/排除列表）与「Mihomo (Clash)」，Mihomo 的五个小节（基本设置、订阅、节点、规则、连通性）是第二级里的左侧竖向菜单——切换小节是导航，因此读起来是菜单，而不是叠在页面标签下面的第二排 tab；导航条只包住自己的五行（不撑到页面底部），小节卡片撑满剩余页面高度并在内部滚动，文档本身永不滚动。基本设置里只有字段滚动：保存行是面板的 footer，钉在面板底边，操作因此永不离开屏幕（这里的字段才是高的那半，固定它是对的）；其余小节仍是整张卡片内部滚动，动作随卡片一起滚。核心操作按钮跟随核心状态：运行中「启动」禁用，未运行「停止 / 重启」禁用（各自以本地化提示作为 tooltip），核心运行期间「下载二进制」禁用（不能替换活进程的二进制），二进制已存在时按钮改称「重新下载」。控制台把 sidecar 命名为 **Mihomo (Clash)**：Mihomo 是 Clash.Meta 的后继内核，操作者仍习惯旧名，模式选项因此显示「内置 Mihomo (Clash)」；ADR 正文继续使用「mihomo core」这个架构名词。节点列表按分组应答（`GET .../proxies?group=<name>`）：每行的类型与测速都从控制器实时快照解析；操作者切换分组时控制台重新拉取，而不是拿另一组的行去映射——那种映射会把新选中组的每个成员都标成「Unknown」（节点类型只有快照这一个真相）。节点表可按「测速」列排序（点表头在升序/降序之间切换，默认仍是配置顺序）；未测速不是 0 毫秒——`—` 行在升序和降序里都排在所有已测速节点之后，降序也不会把未测速的尾巴顶到最前。每条订阅都标出自动更新节奏（mihomo provider 的 `interval`）：只有核心运行期间才会按该间隔重新拉取，运行中保存订阅会重启核心使新间隔生效。订阅面板把两个动词分开：列表上方的表单只负责新建（半填的新建表单不会再被误当成待保存的编辑），编辑某一行打开弹框，每行自带启用开关——启用/禁用是落在该行上的一次点击状态切换，不是藏在表单里的字段：停用的订阅仍留在列表里，但不会写进生成的 `proxy-providers`，也不参与自动更新；拨动开关即刻重建 sidecar。订阅时间戳按本地格式展示；从未拉取过的 provider 在客户端边界就丢掉时间戳——Go 把 `time.Time{}` 序列化成 `0001-01-01T00:00:00Z`，那是协议零值而不是远古日期，绝不能进入渲染出来的文案。 网关自己提供 PAC 文档（`GET /proxy.pac`，位于 `/api` 之外，在鉴权 preHandler 白名单里——它只是一个生成的脚本，不含任何密钥）。每次请求都按实时配置生成，因此控制台里的混合端口就是唯一真相；它携带了裸 host:port 无法携带的直连清单：回环、链路本地、私网（RFC1918、CGNAT 100.64/10）与 mDNS 名称返回 `DIRECT`，其余一律 `PROXY 127.0.0.1:<mixedPort>`，且对被代理的域名不提供 `DIRECT` 兜底——核心挂掉必须显式失败，不能悄悄绕过隧道泄漏流量。`proxy.includes` / `proxy.excludes` 不会映射进 PAC：它们匹配的是 provider/model 名，不是主机名。控制台（Mihomo → 基础设置）把该 URL 放在按钮后面：点开弹框显示地址并提供复制，地址按控制台自身的 origin 拼出，远程打开的控制台依然给出可用的地址——URL 是参考资料而不是配置项，不该在表单里长期占一个只读输入框。

出站模式是 mihomo 自身的开关，与 `proxy.mode`（手动 vs. 核心）严格区分：`proxy.mihomo.routingMode` 取 `rule`（默认）/ `global` / `direct`。生成的配置只注入一条 `MATCH,<group>` 规则，因此当前 `rule` 与 `global` 的路由结果完全相同——仍然暴露这个选择器，是因为 `direct` 是比停止核心更轻的断流开关（控制器与订阅自动更新继续运行），且这是 mihomo 原生概念。控制台修改后既写入配置字段，也 `PATCH /configs {mode}` 热生效，无需重启；核心未应答时只保存、下次启动生效，并回 `live: false` 加提示，绝不假装已应用。读取时把保存值与核心实际报告的模式（`liveRoutingMode`）比对，不一致就显式提示，而不是让选择器谎报运行中的进程——但操作者自己的写入在途期间除外：选择器是乐观更新的，写入前的快照会被误读成偏离，于是每次切换都闪一下提示；等紧随其后的状态读取落定再恢复比对，真实偏离（核心拒绝、别的客户端改走）照样显示。字段与其他配置一样走白名单：未知字符串回落到 `rule`，绝不进入生成配置。PAC 只在客户端决定直连还是走代理，出站模式决定到达核心之后的流量怎么走——两者都存在，所以 PAC 的提示文案从不声称携带规则。

保存是**卡片页脚**，不是页头操作：按钮位于它所写入的那张卡片内、紧贴上方字段的左缘，后面跟「未保存的修改」徽标，作用域说明放在按钮旁的 InfoTip 里（页脚长段落没人看，还会和操作抢位置）——一次保存写的是整个 `proxy` 段（本卡片 + 另一个设置作用域），所以它不能被读成「保存这个字段」，也不该待在多作用域共用、但并非每个作用域都会写入的角落。

当前实际使用的节点是**所有作用域都会显示的页头微标**（运行中分组的 `now`，附协议与最近一次延迟），不是一条设置行：点它会切到 Mihomo → 节点并锚定到该行，该行在表格里带强调色竖条与「当前」徽标。因此「我现在走哪个节点」既不需要切页签，也不需要在上百行里找，筛选条件也遮不住这个答案。

节点页支持按订阅筛选与按协议类型筛选：两者都以真实值作键（provider id、协议名），且相互收窄——选了某个机场就不该再列出只属于另一个机场的协议。协议名不做翻译，`Vless` / `Hysteria2` 是用户要拿去和订阅对照的线路名，不是界面文案。某个筛选值的最后一个成员消失后，该筛选自动失效，而不是留下一个看起来空掉的分组。

节点也可以手工添加：`proxy.mihomo.manualNodes` 是白名单列表（`{ id, name, type, server, port }` 加上该协议自己的字段），渲染进生成配置的 `proxies:` 段，并与订阅节点的 `use` 一起加入策略组——不需要订阅，也不需要联网。协议白名单为 `ss` / `vmess` / `vless` / `trojan` / `hysteria2` / `http` / `socks5`；缺少该协议凭据的行在加载时被丢弃，绝不交给核心，因为一个畸形代理会让整份配置加载失败。控制台通过 `POST/PUT/DELETE /api/admin/proxy/mihomo/nodes` 增删改，每次写入都保存并重建 sidecar（与编辑订阅一致）；`GET .../proxies` 带 `manualId`，节点表只对自有行提供编辑/删除。节点名不得与内置项（`DIRECT`/`REJECT`/`PASS`/`GLOBAL`）或所选策略组同名，且手动节点之间唯一。密码与 uuid 属于凭据：环境归档脱敏，绝不写入日志。

节点行也可以直接录入 Clash 代理定义：控制台解析后把规范化映射存为 `yaml`，渲染时原样输出，因此原始映射在归档中整体脱敏。一次粘贴多个映射（或订阅文件的 `proxies:` 段）要么整批写入、要么整批拒绝；身份字段的校验与表单录入完全一致。编辑以表单为主，并且由同一张字段表（`manual-node-spec`）驱动三个方向：清洗表单草稿、把草稿渲染进映射、把已存映射反向投影回表单。`GET /api/admin/proxy/mihomo/nodes` 用这张表投影出表单字段（含 `reality-opts`、`ws-opts`、`grpc-opts`、`h2-opts`、`client-fingerprint`、`alpn`、`udp`、`tfo`、`ip-version`、ss 插件与 hysteria2 混淆/端口跳跃），所以粘贴录入的节点打开时表单是填满的；响应同时给出表单未建模的键名（`unmodeled`），控制台据此明示「这些键只在 YAML 页签编辑」，而不是悄悄藏起来。表单保存只覆盖这些键：清空的字段从映射中删除，未建模的键原样保留；白名单之外的协议只允许改名称/服务器/端口。非法输入返回 `400 {code: 'invalid-node-field', field}`，控制台把提示落到对应控件上。`GET .../nodes/catalog` 暴露协议/字段/枚举表，控制台不再手抄后端白名单；YAML 页签保留给表单未建模的键。

每个节点行还带一个 `source` 字段：`{ kind: 'subscription', id }`、`{ kind: 'manual', id }`，或 `{ kind: 'builtin' }`（mihomo 自有条目：DIRECT/REJECT/PASS，以及不对应任何已声明订阅的 provider 名）。控制台把它渲染为节点表的「来源」列，并用它构造来源筛选，因此手动节点和机场一样可筛选，不会在只有 provider 的筛选里消失。

添加节点对话框可以在写入前探测未保存的节点：此时核心还没有该节点的路由，因此对 server:port 做一次**直连 TCP**（5 秒预算；裸 socket 不读 `HTTP_PROXY`/`HTTPS_PROXY`，也不经过本网关的前向代理），只报告「可达/不可达」——不声称凭据或隧道可用。完整测速仍在节点表里对已保存的行做，那条路径才是刻意经过节点的。

失败的测速不是一次测量：mihomo 会把它报告为 `0`（history 条目、单节点测速或分组 map），客户端层把 `0` 归一为「未测量」，控制台因此显示 `—` 而不是误导性的 `0 ms`；批量测速还会清空响应里没有测到的行。
测速的路由由名字「住在哪里」决定。mihomo 的 `/proxies/{name}/delay` 只在自己那份代理表里解析——生成配置的 `proxies:` 段、策略组和内置条目；proxy-provider（订阅）成员只存在于自己的 provider 里，因此对这条路由会返回 404 `Resource not found`，哪怕节点本身完全健康。客户端因此先判定归属：配置内代理走配置作用域，provider 成员改走 `/providers/proxies/{provider}/{name}/healthcheck`（同一个 URL 测速，只是换到 provider 作用域），两边都不认识的名字报 `node-not-found`，而不是被当成「节点不可达」。

测速地址是**一个**配置项 `proxy.mihomo.testUrl`（http/https、不得内嵌账号密码，默认 gstatic 的 204 地址，即 mihomo 自身的 `DefaultTestURL`），不是列表：生成的策略组只有一个 `url`，"这次延迟是对谁测的"必须无歧义。控制台提供 Google 204 / Google / Cloudflare / OpenAI / Anthropic / Gemini 预设作为快捷方式，但输入框可自由填写；测速请求可以携带输入框里的当前值，因此未保存的修改立即生效（mihomo 的延迟测试接受任意 HTTP 状态码，带鉴权的端点同样能证明连通性）。

两种检查绝不混用：**测通**用核心的 delay 接口，经当前选中的节点去请求配置的 URL——同时证明隧道和 URL；**测速**测的是节点本身，未保存的节点只能直连 `server:port` 做 TCP 探测（不经过代理，因为核心还没有它的路由）。控制台按此区分展示，测通结果会注明经过的节点，以及核心实际请求的那个地址（输入框留空时即默认地址），因此结果永远不会描述一个操作者看不到的端点。测通失败不会另起一套「逐 URL 测速」的界面：它指向节点页的批量测速——那条路径已经回答了「这个地址是所有出口都不通，还是只有当前节点不通」。
候选端点的批量测通仍属于这**一个**字段的探路：一次动作把预设加输入框当前值经**当前**节点逐个探测并各自给出结果，结果只留在页面，选中赢家仍是一次普通的字段编辑——探测绝不改写核心健康检查所用的地址；反过来「这个地址是否所有出口都不通」仍交给节点页的批量测速，不另起测试界面。

节点表的「测速」列永远不是一个裸数字，而是五种状态之一：未测、测试中、超时、错误、已测量。mihomo 对不通的节点回的是延迟 0，若让它落进单元格就成了「0 ms」的谎话；同理，某一行正在测试时也不能继续显示上一次的数字。批量测速开始时把全部成员先置为「测试中」，结束后一起结算，因此结果陆续返回时排序不会跳动。测量值按 < 250 ms / < 400 ms / 更慢分档着色，而所有非测量状态在两个排序方向上都排在测量值之后——降序也不会把「—」顶到最前。控制台测得的读数按节点缓存 30 分钟，过期即丢弃，因为过了这个时长的数字已经不描述该节点。测速预算收敛成一个常量（`MIHOMO_DELAY_TIMEOUT_MS`，5 秒），控制器客户端的默认值与两个控制台接口共用它；接口各自接受按请求覆盖，覆盖值上限 20 秒。

选谁当节点是另一条轴：`proxy.mihomo.groupType` 取 `select`（默认，由控制台的节点选择决定）/ `url-test`（实测延迟最低者胜出）/ `fallback`（第一个可用的成员），配套 `groupInterval`（秒，30..86400，默认 60）与仅 `url-test` 使用的 `groupTolerance`（毫秒，0..5000，默认 50）。这个间隔是**故障检测窗口**而不是显示刷新：失效节点在下一轮测试前仍会继续承载流量（延迟读数也陈旧这么久），因此网关默认 60 秒而不是 mihomo 自身的 300 秒——后者意味着一个刚测完就挂掉的节点最多要等五分钟才被换掉。30 秒下限则避免「每个成员每轮一次真实请求」在大型订阅上变成对测试地址的模板攻击。生成的代理分组沿用同一类型、指向共享的测速 URL 并带上 provider 列表。自动分组刻意不含 `DIRECT` 成员：直连路由实测约 0 ms，`url-test` 会每一轮都选中它而静默绕过隧道，`fallback` 则会在某个节点失败时把全部流量交给它；手动分组保留 `DIRECT`，因为那是人主动选的。改动走配置保存（分组写在生成配置里，需要重启核心——不同于可直接 PATCH 热生效的出站模式）。节点页从代理列表响应里的 `groupType` 读取**运行中**分组的类型，自动分组下禁用手动选择并给出说明，控制台不会给出核心会忽略的点击。三个字段与其他配置一样走白名单与区间钳制，未知值回落到 `select` 与出厂默认。
手动批量测速不是第二条选择路径：它把每个成员在共享测速地址上的最新延迟写进核心，核心在下一次排序（受自身数秒级结果缓存约束，而不是等 `groupInterval`）时按同一容差重新排序；节点失效后跑一次批量测速，就是操作者缩短检测窗口的手段。

控制台还展示**正在运行的核心**实际加载的规则表（Mihomo → 规则，`GET /api/admin/proxy/mihomo/rules`，数据来自控制器的 `GET /rules`）：类型、匹配内容、出站目标都读自核心而不是网关写下的配置，因此被拒绝或丢弃的规则会显形，而不是靠假设。这也让 provider 的边界可核对：`proxy-providers` 只贡献**代理**，订阅文件自带的 `rules:` / `proxy-groups:` 一律不导入——屏幕上那张表就是网关生成的那张。核心未运行时接口回 409 `not-running`，控制台把它渲染成空表加一条本地化的「未运行」说明，绝不弹错误框。需要自己的分流时由操作者自己写：`proxy.mihomo.rules` 是一个**有序**列表（`{ type, payload, target }`），渲染在最后一条 `MATCH,<group>` 之前，先匹配先赢。目标保持符号化——`PROXY` 在渲染时才解析为当前配置的分组名，因此改分组名不会让某条规则悄悄指向一个不存在的名字。类型白名单是刻意收窄的：`DOMAIN`、`DOMAIN-SUFFIX`、`DOMAIN-KEYWORD`、`IP-CIDR`、`IP-CIDR6`、`DST-PORT`、`SRC-PORT`、`PROCESS-NAME`、`PROCESS-PATH`，即核心不需要地理数据库或外部规则集就能求值的类型。`GEOIP`、`GEOSITE`、`RULE-SET` 在加载时就丢弃而不是照发，因为求值不了的规则要么让配置加载失败，要么静默落到下一跳，而静默落空会改变出网路径。带列表分隔符的匹配内容同样丢弃。编辑器（`PUT /api/admin/proxy/mihomo/rules`）写整张列表并让核心按新配置生效，并且与上面那张只读表并存而不是取代它：可编辑的草稿和核心真正加载的内容是两个不同的事实。
订阅自带的规则可以**一次性**导入，接口是 `POST /api/admin/proxy/mihomo/rules/import`（`source: 'subscription' | 'text'`）。导入是一个**草稿**操作：解析订阅文件，把指向订阅自有 `proxy-groups` 的目标一律压平成 `PROXY`，跳过本网关无法求值的内容（`GEOIP`/`GEOSITE`/`RULE-SET`/逻辑规则）并计数，去重后把行返回给控制台，由控制台合并进可编辑列表——既不写盘也不下发给核心，只有操作者保存后才生效。网关不认识的出站目标默认映射为 `PROXY`（控制台提供勾选改为直接丢弃），避免机场自己的分组名变成死目标。刻意不做实时绑定：机场改一次订阅文件就会在控制台显示着另一种状态的同时悄悄改变出网路径，而规则的目标恰恰是这种意外代价最大的地方。
文档本身优先取自核心自己的 provider 缓存（`<workDir>/providers/<id>.yaml`）：那正是运行中配置实际使用的那一份，可离线工作，也能扛住订阅站点 TLS 链被本运行时拒绝的情况——而这恰好就是让联网导入不可用的那种失败（`fetch` 报 `unknown certificate verification error`，而核心早已成功接受同一个地址）。网络只作为兜底，并且控制台会明确告诉你这次用的是哪一种来源，而不是让你猜。
每条规则带一个 `source` 来源标签（`manual`、订阅名、`paste`）。它只是元数据——不写进 YAML、不参与求值——存在只为一件运维上的事：把来自同一处的规则归到一起，删掉某个订阅时可以按来源筛选后批量清理。导入是两段式的：先出可勾选、可筛选的预览，只有勾中的行才进入草稿；解析很便宜，改出网路径不便宜。规则章节一次只显示两个视图之一——「生效规则」（核心实际加载的）或「规则编辑」（草稿），绝不叠在一起：叠放时操作者判断不出哪些行真正在生效。长列表只在各自限高的容器里滚动，保存按钮固定在卡片底部，对话框本体不加滚动，因为嵌套滚动会藏行，还会让滚轮落到错误的容器上。
