# ADR-0008: 协议接入面与捕获——双传输一张派发表、交换事件而非轮快照、两腿全链 opt-in

## 状态

已实现 — 2026-10-15（事实面语料重写）。2026-12 修订：MITM 腿自己中继 `Upgrade:`/WebSocket 握手（运行时自身的 upgrade 事件不可用——见 §3）；每 host 的 TLS 终结器与签发叶证书都做了 LRU 上限；`forwardProxy.accessLog.bodyBytes` 获得有限默认值（1 MiB），超限体溢写到裸 body 文件而不是撑爆堆。2026-10-21 修订：原生 System One 上游支路（`systemoneUpstreams[]`、厂商直通）**退役**——该面仅经 chat 模型协议转换服务；未来 Jev/Bailian 集成以普通 provider 形式经定义文件接入（ADR-0010）。2026-10-24 修订：写侧 `@ai-sdk/typesafe-ai` → package 映射保留原生 `typesafe` 段，该别名继续留在 npm 词表中——2026-10-23 的降级（改用兼容运行时 + 从下拉框隐藏别名）是回归，现予撤回。客户端可加载性仍是独立一层：客户端没有该段时，写给客户端的那一份由 `CLIENT_PACKAGE_FALLBACK` 替换（ADR-0010 修订案）。2026-10-22 修订：原生 decision 支路**以 wire 驱动方式复职**——解析出的 npm 为 `@ai-sdk/typesafe-ai`（或 opencode v2 segment `typesafe`）的 provider 定义解析到 wire `systemone`，在决策面上以**原生直通调用**服务（§7）；所有 chat wire 模型仍走转换。范围：入站协议面（原生路由 + MITM 代理）、共享派发接缝、System One 决策网关、请求捕获平面。trace/捕获持久化分界 = ADR-0005；数据集采样（**不是**捕获）= ADR-0001；决策面的寻址 = ADR-0003。

## 决策

### 1. 一张表、两种传输、一个接缝

`SURFACES`（`surfaces/table.ts:8-23`）是唯一注册表：每个入站面一行——`routePath / detectSuffix / exec / capture / encodeStream`。同一张表同时驱动 Fastify 路由注册（`server.ts:1044-1056`）与 MITM 路径探测（`detectSurface` 后缀匹配）——限流路由表也由它派生（`INFERENCE_ROUTE_PATHS = SURFACES.map`）。`dispatchSurface` 只按 `exec` 分叉：`chat-pipeline` | `decision-pipeline`。两种传输各自构造 `TransportContext`（`surfaces/types.ts:58-79`）：`method/url/headers/clientIp` + 访问闸（判别联合：Fastify 侧 `kind:'key'`——已验 bearer/x-api-key + 按 key 模型访问，拒绝已由 guard 写成 403；MITM 侧 `kind:'exempt'`——客户端是**穿过**我们连出去的，信任在 CONNECT/TLS 层 + bypass 名单；无网关 key，故捕获事件不带 apiKey 归属，上游调用一律用注册 provider 自己的凭证）+ `captureProcessContext()`（捕获关时答 `{}`）+ 终发（`sendJson` / `beginSse`+`writeSseChunk`+`endSse`）+ `isClientGone()` + `logError`。终发纪律：每请求恰一次终发；parse/gate 失败**零捕获事件**（两腿都在 dispatch 之前）。

### 2. 入站线型别名——恰四个；Gemini 是上游 wire

`/v1/chat/completions`（OpenAI-compatible）、`/v1/messages`（Anthropic-compatible）、`/v1/responses`（OpenAI Responses）、`/v1/systemone`（决策网关）。别名表封闭——其余一律 404。（2026-11-05 修订，ADR-0017：封闭表约束的是直连 `/v1` 面；client-gateway 插件可在 MITM 腿之后按整台 SNI 主机接管，其路由按主机作用域、永不成为表行。）Gemini `:generateContent` 是**出站** provider wire（出站集 `openai|anthropic|google|responses|opencode-proxy`），不是入站别名。systemone 的 `detectSuffix '/systemone'` 刻意**宽于**其 routePath——让 MITM 腿认领途经的 typesafe.ai / bailian 同形决策流量。

### 3. MITM 转发代理——全捕获就是要点

默认姿态：每个 HTTPS CONNECT 都 MITM，除 loopback 或规则另有规定（`forwardProxy.rules`，ADR-0018）：SNI peek → `startMitm` → 解密流 splice 进内层 `http.Server`（h1）或先验 h2c `http2` 兼容服务器（h2，由连接 preface 判定，绝不只看 ALPN）；命中 surface 表且 POST ⇒ dispatch；否则透明转发——h1 裸字节中继（`relay.ts` 带背压；跳逐头集合——connection/keep-alive/TE/trailer/transfer-encoding/upgrade/proxy-*——双向剥离），或 h2 腿上的忠实 h2 重发上游（ADR-0017 §3：trailer、双向流、保留 `te: trailers`；上游拒绝 h2 时回落 h1）。请求体 32 MB 上限（413）与非法 JSON（400）都发生在捕获/dispatch **之前**——零事件。裸名消歧走 `upstreamHost` = 被拦截请求的 host（`orchestrator.ts:106-124`；原生腿刻意不信 Host——防伪冒，ADR-0003 §1.5）。

**Upgrade / WebSocket 中继。** `Upgrade:` 握手（含 WebSocket）在**解密流**上、进入内层服务器之前就被捕获，逐字节中继——请求头（以及客户端已提前发出的后续字节）→ 源站 socket，随后裸字节双向 splice（`relayUpgrade`）。它不能走运行时自带的 `node:http` upgrade 事件：在 Bun 1.3.14 上，交给该处理器的 socket 会吞掉每一次 write，而解析器继续运行、对客户端随后发送的字节回 505，于是 `wss://` 连接会在握手处直接死掉。握手内容一律不重序列化（子协议、扩展、cookie——任何 upgrade 协议皆然），因为 upgrade 只有一跳。它也不能走普通转发器：`connection` 与 `upgrade` 是跳逐头，`filterHeaders` 恰好会剥掉这两个**构成握手本身**的头。上游 TLS 对 IP 字面量源站**不发** `servername`（`egress.ts` `upstreamServernameOption`）：RFC 6066 禁止 SNI 出现 IP，Node/Bun 会直接抛异常——抛在 socket 的 `data` 监听器里就是未捕获异常、连接静默死亡，所以 IP 判定收在一处，TLS 参数抛错或连不上时向客户端回 502 而不是任其逃逸。客户端网关插件可以**拥有**它声明主机上的握手（`handleUpgrade`，ADR-0017）：返回 `true` 即整条解密 socket 移交——101 由插件自己写、流由插件驱动；返回 `false`（或没有该钩子）则落到下面的透明中继。三个边界是**设计使然**的开放项，不是日后要“修”的 bug：明文代理端口上的非 TLS `ws://`（该腿从不解密，且同一个运行时缺口也卡住它的 upgrade 事件）、HTTP/3/QUIC（根本不代理）、以及需要上游客户端证书（mTLS）的目标（终结器没有客户端证书，源站的 CertificateRequest 无从应答）。

**有上限的每 host 终结器。** 每个被 MITM 的 host 都会得到一个监听中的 `tls.Server` 加一张签发的叶证书。full capture 会看到客户端访问的每一个 host，所以两个缓存都加了 LRU 上限——256 个终结器（`server.ts` `MAX_HOST_TERMINATORS`）与 512 张证书（`ca.ts` `MAX_CACHED_CERTS`）——淘汰终结器只关监听：已建立的连接保留自己的 socket，下一次 CONNECT 用同一个 CA 重签即可。这里不设上限等于按访问过的 host 数泄漏文件描述符，也就是说，故障只会在代理已经“好用了一阵子”之后才现形。

**解密范围与入站上限。** 接管范围由规则表的 `ingress` 列决定（ADR-0018）：`intercept` 解密、`passthrough` 纯隧道透传，未命中兜底为 `intercept`——即本 ADR 描述的默认姿态。`passthrough` 行照样代理字节，只是永不解密，所以这是**解密范围**而不是访问控制（访问控制是代理认证——OCR API Key 作为 Basic 密码，ADR-0017）。两条腿——CONNECT/MITM 准入与明文 absolute-URI 的拦截判定——共用同一个解析器，因此不可能各说各话；CONNECT 账本会带上该决策，所以「这个 host 为什么没被捕获」能直接从账本回答。`forwardProxy.maxConnections`（默认 512，区间 16..8192，保存即生效）限制的是**并发代理会话**——一个被隧道或被 MITM 的 socket 占两个 fd（接受的 socket 加它解密后的 loopback 对端）——并在**准入点**（CONNECT 或明文 HTTP 请求）执行，而不是 accept 时：Bun 的 `node:http` 没有任何 accept 侧钩子（`http.Server` 不发 `'connection'` 事件，`server.maxConnections` 与 `server.timeout` 全部无效——均在 1.3.14 验证），所以一个从不发字节的 socket 只能由 listen backlog 兜底。槽位在 `end`、`close` **或** `error` 时释放，因为同一个运行时对交给 CONNECT 处理器的 socket 不发 `close`。代理认证**只接受 API Key**——**谁**可以用这个代理：每个 CONNECT 与明文请求都必须带 `Proxy-Authorization: Basic <base64 用户名:keySecret>`（用户名忽略；密钥按 live 配置恒定时间比较），否则回 407 并带 `Proxy-Authenticate` 挑战；loopback 且没有可用 key 时保持关闭认证（历史姿态），除非开启 `forwardProxy.requireCredential`。引入 API Key 之前的 `forwardProxy.authToken` **已退役**——与所有退役键一样在加载时丢弃（ADR-0018 §6）且永不翻译，因此曾用它给 loopback 代理做认证的安装会回到**认证关闭**的状态，直到它创建一把 key 并开启 `requireCredential`。绑非回环地址却没有任何启用中的 key 会在启动时**直接拒绝**（`forward-proxy/index.ts` `assertForwardProxyBindSafety`；它刻意不复用 `isLoopbackHost`——后者为 MITM 环路安全把 `0.0.0.0` 也算作 loopback，与绑定门禁的要求正好相反）——一个对局域网可达、无认证、全量解密的代理是最坏的默认值。严格模式对 loopback 是可选项，原因只有一个：网关插件绑定的 key（`accountKeyId`，ADR-0017）是给无法携带代理凭据的 GUI 客户端准备的服务端回退，绝不能把该身份借给同一台机器上未认证的进程——开启后 loopback 与局域网执行同一套凭据要求，且没有任何启用中的 key 时启动直接拒绝，而不是退化为开放。

**严格模式还会回收已打开的隧道。** 准入是连接级的，所以运行中开启 `forwardProxy.requireCredential` 时会关闭所有“无凭据准入”的隧道（对已登记 socket 做 1 秒一次的巡检）——否则该开关会留下一条无认证的全量解密隧道，直到客户端自己断开。网关 seam 也会独立停止为该隧道承认绑定 key，因此在 socket 被关闭之前也无法借用身份。

**CONNECT 携带身份（ADR-0017）。** 代理**唯一**的凭据是把 OCR API Key 作为 Basic 密码（`Proxy-Authorization: Basic <任意>:<keySecret>`，用户名忽略——key 名不唯一），按 live 配置恒定时间匹配并在派发前复查。这样认证的隧道只记住 `{keyId, name}`；同连接的解密请求继承它，于是路由到 OCR 的补全按该 key 计量，vendor 原生中继不受影响。终结器按 key 分区，两个身份绝不共享同一条解密连接；非回环绑定要求至少一把启用中的 key，运行期删光 key 会 fail-closed（407），而不是打开监听。

**CA 路径只有一处拼写——且 CA 是本机共享的。** MITM CA 目录经 `forward-proxy/ca.ts` `resolveCaDir(forwardProxy.caDir)` 解析；默认是**每用户共享数据根 + `forward-proxy`**（即桌面 shell 的默认 `OCR_HOME`），而不是某个 book-set 的 `<ocrHome>`。信任锚是**机器级**状态：第二个安装必须沿用操作者已导入的 CA，而不是再铸一张同 CN 的孪生证书让客户端验错链（`CERT_SIGNATURE_FAILURE`）。book-set 隔离仍然覆盖访问日志与系统代理快照——它们留在 `<ocrHome>/forward-proxy/`。首次解析时，共享目录会把旧的 per-home `<ocrHome>/forward-proxy` CA **复制过来沿用**（绝不重新生成，已导入的根必须在迁移中存活）；`OCR_CA_DIR` 为沙箱测试固定默认值。代理自身、控制台的 PEM 下载、CA 卡片（`GET /api/admin/proxy/ca/meta` 回显路径 / SHA-256 指纹 / 主体 / 有效期，绝不外带私钥）以及系统代理状态里的信任提示共用这同一处拼写。另加两道身份闸：同一个目录里已存在的 CA 若 CN 与请求不符，`ensureCa` 直接报错；每个 CA 的主体按密钥派生一个 `OU`，使多个同 CN 的根不会共享同一 DN。Windows 的信任探测比对**证书指纹本身**（不再只比 CN），过期同 CN 根再也不会被报成 trusted。

**信任状态只报告，决不臆测。** 控制台的 Proxy Access 配置卡与设置向导展示 `GET /api/admin/proxy/ca/trust`：针对代理实际签发所用的**同一张证书**给出三态答案（`trusted` / `not trusted` / `unknown`——探测本身跑不起来时**绝不**压扁成"未信任"）。`forward-proxy/ca-trust.ts` 只探测网关能读到的平台存储——Windows 机器 + 当前用户 Root 存储按指纹匹配，macOS 用 `security verify-cert` 走真实 SSL 信任策略，Linux 的 anchor 文件 / 合并 bundle / NSS 数据库按**证书内容体**比对——应用私有根库（Firefox profile、Java keystore）明确不在范围内。探测会 spawn 平台工具，因此结论缓存 60 秒；`?force=1` 绕过 TTL，保证安装后立刻重查不会回放安装前的旧答案。检测永不代替安装：导入根证书始终是操作者的显式动作（提权 / OS 确认）。

### 4. 请求身份

身份由 **ADR-0021** 定义：无前缀的 id 属于本服务（`requestId` 命名单次请求，是 trace 记录的主键；`sessionId` 命名会话），外部命名空间加前缀（`clientRequestId`、`upstreamRequestId`）——客户端自铸的**会话**别名不设独立字段，由路由溯源携带（`request.clientRef`，ADR-0002），`exchangeId` 配对单次 HTTP 交换。共享边界适配器（`observability/request-identity.ts`）按 `traceparent` > `x-request-id` > `x-trace-id`/`x-correlation-id`/`request-id` 的优先级把入站值解析为 `clientRequestId`（W3C 验而后用，绝不铸造、绝不回显）；MITM 读**原始** clientRequest 头。出站注入 traceparent **未实现**（builder 仅测试用）。捕获的 `clientHeaders` 是安全子集 `{userAgent, acceptLanguage, clientRequestId}`；authorization/api-key/cookies 在结构上就进不了 trace 记录。`X-OCR-Session-ID` 命名网关会话；`X-OCR-Trace-ID` 已移除。

### 5. requestCapture——HTTP 交换事件

命名空间：`requestCapture:`——退役的顶层 `capture:`（更名残留）、`classifier.layer2.decisionCapture`、键级 `role`、以及退役的 `requestCapture.systemone` 双闸子树加载即剥离、保存永不写回；两条控制台保存路径热应用（`routes/console.ts`）。一个命名空间一个含义：**请求/HTTP 交换日志**（训练数据采样是另一个 concern，ADR-0001 §5）。

模型：`CaptureEvent`——每方向每腿一条；一个请求产生 2–4 条共享同一 `requestId` 的事件（请求与响应按 `exchangeId` 配对）：client-request / client-response / upstream-request / upstream-response。每行盖章 `schema: 2`（`CAPTURE_SCHEMA`），并携带其请求的**写时** turn 身份——`turnIndex`（无提示请求取一等值 null）、`isPromptStart`、`turnDecision`——外加 `attempt`（`(requestId, leg)` 内 1 起；客户端腿恒为 1）。边界由准入闸口以结构化方式判定（`capture/turn-boundary.ts`，ADR-0024 §4），读取方只复制；没有任何读取方从提示文本、消息数或重发启发式推导边界。每条事件另带 `conversationKey`（ADR-0002 §1：sha256(apiKey 身份 + 首条用户消息)，内容寻址，无法解析时省略），档案可凭它跨易变 sessionId 重组会话。头部现行制度：**名保留**，凭证形**值** `[REDACTED]`（子串拒单：authorization/api-key/cookie/token/secret/bearer/…-key/key/auth；query 里的 auth 参同遮）；`requestCapture.redactSecrets`（默认 true）是运营者**退出脱敏**的开关——置 false 后命中拒单的头与 query 值原样落盘（含上游 provider 真实密钥），由 `CaptureRecorder` 统一下发，构造与热应用一致。主闸 `enabled:false` 默认——OFF 是**字节同一的零事件姿态**（测试钉死），开是自觉 opt-in（`/api/admin/*` 免鉴权提醒适用）。落盘：`capture/<YYYY-MM-DD>/<sanitized-sessionId>.jsonl`——schema-2 行的**活归档根**；版本挂在数据上（每行 `schema: 2`），不挂在根名上。Schema 演进：活根通过注册的迁移链（`capture/migrate/`：每一跳一个 `V{N}ToV{N+1}Migrate` 类、每类一文件于 `migrate/steps/`、注册于 `migrate/registry.ts`；引擎按 `(from, to)` 解析这一跳，**每个文件现建实例**，故某个 step 的 `begin()` 规划状态永不共享；`begin()` **每跳调一次**，喂给它的是**该跳即将重写的形状**（后面的跳绝不会拿前一跳已替换掉的磁盘形状做规划），且走链不许缺步、不许跳步——与 `traces.db` 的 `DB_VERSION` 同一的一次性阶梯）**原地**前进：boot 与热启用两趟处理**每一个**文件（升级后的历史当场可见），每小时 sweep 只碰静置满十分钟的文件；每次重写都是全文件原子的（同目录临时文件 + rename），且在换上去之前**再校验一次原文件**——迁移途中若有追加落盘，该文件这趟让开而不是丢掉新字节；某行的迁移步未注册、跨版或无法表示为该 schema 的形状时，整个文件保持原样留给下一趟、读取方继续拒绝——绝不出现半迁移档案。而不可解析 JSON 的行也不构成放弃整文件的理由：原字节保留（并在趟汇总里计为 `unreadable`），一行腐烂绝不能让读者丢掉旁边的千行好数据。schema 1 是**无标记基线**（整行没有 `schema` 字段），而 `V1ToV2Migrate` 是真实的一步、不是墓碑，覆盖**两种历史形态**：已带网关 id 的行原样采用（`attempt` 重建为同一 `(requestId, leg)` 内每个不同 `exchangeId` 的序号）；没有网关 id 的旧行——只有 `traceId` + `spanId`——的请求边界从事件序列**读出来**，因为 `traceId` 是**连接**级关联（一条 trace 内可有多个先后请求）而 `spanId` 才是 exchange 身份：`client request` 开启一个请求，它引发的 `upstream` span 归属该请求，配对的 `client response` 收口，requestId 由 `(sessionId, spanId, ts)` 确定性铸造，故重跑铸出同一个 id（幂等）。无法收口的序列一律**修**成最接近真相的形状，既不猜测也不搁置：落在任何 client 请求之外的 upstream 交换成为独立的**孤儿请求**（`turnIndex: null`、`NO_TURN`——可见且如实标注“不属于任何提示”，绝不折进相邻轮次）；前一个请求未收口又开来一个 client 请求时，直接开启下一个请求（被弃置的那个保留其交换与轮次，只缺响应半边）；匹配不上任何请求的响应挂到其 span 在文件更早处开启的请求上，或自成孤儿；文件在请求中途结束则保留该请求。因此该 step **从不拒绝**引擎交给它的行：凡能解析的行，必定以目标 schema 的可读形状出来。两种形态的 turn 身份都来自准入闸口所用的同一套结构化规则（`classifyTurnBoundary`），对归档**已记录的原 body** 按文件顺序重放、按会话串接上一请求的消息数（body 已不可读时改由旧写入端记下的 `promptMessageCount` / `promptLastUserIdx` 对照驱动）。退役词汇被丢弃：`spanId` 成为 `exchangeId`、`traceId` 由请求身份取代、`promptMessageCount` / `promptLastUserIdx` → 无。引擎对每条重写行盖 `migratedFrom: 1`，因此重建的 turn 身份**绝不会**被误认为准入闸口印章。没有封存、没有隔离区、没有暂存地：**任何东西**都不会被搬出活根——把旧捕捉停放到运行时不读的目录里，等于让升级吃掉它本该保住的历史。活根是唯一副本，趟结束后其中每一行仍然可查看。（`_backup-20261114-1229/` 是切换时运营者手工做的一次性副本，不属于机制的一部分，也没有任何代码路径会再生成这种东西。）保留 7 天 / 池 2048 MB / 单体上限 16 MB（按“一份满载的 2M-token 上下文能完整落盘”定标） / 单会话封顶 512 MB——触及封顶的会话档案停止追加，并落一条终态 `archive-overflow` 行；该行是元数据，读取侧不得将其计作一个请求。封顶的因由：agent 循环在工具循环的每个请求里重发全量历史（单个 turn 内 O(n²) 增长），一个失控会话不得吃掉共享配额；预算为软上限（并发追加最多多出一行）。控制台尾读窗口随单体上限缩放（8 MB 下限 / 48 MB 封顶），完整历史恒可经导出取得（导出不封顶）。读取面（控制台）：`readEvents` 改为**异步**——fs.promises 窗口读 + 让出事件循环的批量解析——档案读取不再阻塞网关事件循环；`bodies=none`（控制台元数据优先默认）剥离解析后事件的 wire body，并在读取时给每条响应事件盖上派生的 `completionTokens`（响应体内最后一次 usage 计数），每请求的 tok/s 速率章在无 body 时照常渲染；完整 body 经 `GET /api/admin/capture/:date/:file/request?id=<requestId>` 按请求取回（`evt_…` 事件 id 亦可，两者都能唯一命名它），或以 `bodies=full` 重读。请求列表在该窗口内**向后翻页**：`page=1` 是最新的一页，越早的页码往上数，且每页都在请求起点处切分，绝不渲染半个请求（响应带回 `page`/`totalPages`/`hasOlder`/`hasNewer`；越界页码会被钳制，因此分页条能自愈）。由于读取窗口有界，标题里的精确分母与全归档轮次索引来自 `GET /api/admin/capture/:date/:file/summary`：它只流式扫描 client-request 元数据（定向字节行扫描，绝不对 MB 级 body 整体 `JSON.parse`），统计请求数，并直接读取每行的**写时** `turnIndex` 构建轮次索引（`CaptureTurnIndexEntry`，按 `turnIndex` 作键，按文件 stat 缓存；拼接会话各分片相加）。分页条从最新端往回按**请求**计数，其读取窗口按需增长至一个硬上限——越过上限时响应会钳制页码（分页条自愈），更深的历史仍只能导出，因此一次点击永远无法分配出封顶大小的缓冲区。分页条是详情面板**固定在底部的页脚**（只有请求列表滚动），默认每页 50 个请求；对话回放视图例外——它自己逐页走完全部轮次。轮次导航复用同一份写时元数据：`isPromptStart` 标出开启一轮的请求，其**仅显示**的 `promptSummary` 印章（捕获时写入、绝不派生）为选择器条目命名，控制台无需解析任何报文体就能把已加载页分成轮次并把视图收窄到某一轮。跨零点会话由读取侧拼接：事件窗口与按请求端点均支持 `stitched=1`，把同一会话跨日期的分片合并（`readEventsStitched`/`readRequestStitched`；分片发现经 `listSessionsWithSpans`，限定为缓存的 ≤64 KB 头部读取，会话行带 `spanDates`）；前端把跨日跨度渲染为徽章加逐日分隔线。会话行另带 `protocol`——由首条 client-request 事件的请求行派生的入站面（`/v1/chat/completions` → chat、`/v1/messages` → anthropic、`/v1/responses` → responses、`/v1/systemone` → systemone；无请求行的归档保持 undefined = 无徽标）——且预览/轮提示提取器把 System One 请求体的 `state`（字符串或结构化 JSON，封顶）视为用户文本，决策面会话由此获得内容标题而非裸 sessionId。boot + 逐小时清扫，I/O 全 fail-open。客户端响应体 stash 上限 1 MB；客户端断连经传输适配器终结（合成 499）——hang/cancel 也留痕。流式上游腿记录该 exchange 的原始 `text/event-stream` 体（内存累积在 recorder 自身按字段截断前封顶 256 KB，含 `[DONE]`），所以 `upstream/response` 回答“哪些帧真正过线”，截断的流以截断态可见；出站客户端腿在 1 MB 上限内按分片 stash SSE 帧。流式不产生额外事件种类——仍是同一对请求/响应，只是 body 形状不同。流式响应事件另带 `firstByteTs`（首个 body 分片的 epoch ms，在 wire 上盖章：上游 SSE 读循环 / 客户端 SSE 写；缓冲式单发回复不带），`groupEventsIntoRequests` 由此派生每腿 `ttftMs`/`genMs`——捕获平面与 trace 平面使用同一套 TTFT / 解码 TPS 词汇（ADR-0005 §8），绝不用全时延合成的速率。`/v1/systemone` 面本身永不捕获 FinOps 或 trace 行——捕获只有交换事件。

词汇（ADR-0024，权威）：`session ⊃ turn ⊃ request ⊃ exchange ⊃ event`。控制台渲染的请求投影是 `CaptureRequestSummary`，带按 `(leg, attempt)` 分桶的 `exchanges[]`——failover 的每一跳与 Layer-2 决策对都保持可见，每个 exchange 阶段各占一个抽屉标签页；契约前的六个固定槽位与 `round*` 读平面符号（`roundNumber`、`totalRounds`、`CaptureRoundIndexEntry`）已删除。`requestNumber` 是读取窗口内 1 起的请求序号（分页器的单位）；turn 归属是不可变的写时 `turnIndex`，绝不折叠进它、绝不被重编号。`promptSummary` 仅在写时盖章于开启一轮的 client-request 事件（仅显示用；续接请求永远没有）——退役的读时新鲜度去重（`promptMessageCount`/`promptLastUserIdx`）已移除。recorder 不跨请求持有状态（捕获 fail-open、重启无感）；turn 高水位放在 session-manager 快照（`v: 3`）里，不在 recorder。

### 6. System One 面——单总闸捕获

退役的双闸树（`requestCapture.systemone.{enabled, l2DecisionEnabled}`——面闸默认 ON，外加决策调用子闸默认 ON）加载即剥离、保存永不写回：两闸默认值都是 TRUE，只会收窄一个本已显式的隐私 opt-in，代价是让捕捉卡片读起来像 System One 面配置（面向操作者的混淆，2026-12 退役）。单一 `requestCapture.enabled` 总闸（默认 OFF）现在门控每条腿——`/v1/systemone` 客户端一对、该面自己的上游一对（按解析 wire 的原生直通或合成转换调用，无 purpose 标签）、以及 Layer-2 决策层的内部调用腿（挂外层被路由请求，upstream 方向，`purpose:'l2-decision'`，唯一的 ExchangePurpose 值；总闸不开时编排器根本不向决策层传捕获 ctx）。发射严格晚于全部 400/403/404/503 闸。OFF 的隐私姿态：`captureProcessContext()` 答 `{}`，该面路径与无捕获构建字节同一（专测钉住）。

### 7. 决策网关（/v1/systemone）——wire 驱动，诚实写进措辞

该面的模型语义：点名模型 = 所点即所得；auto 梯队别名按**纯池投影**解析到访问过滤后池的首位模型——404 未知/无池、403 被禁、503 解析不出，**绝不**静默回退；裸 `auto`/省略 → `systemone.defaultModel`；决策线限流计数但永不本地拒绝（决策层是请求下腿）。响应头恰三个（冻结契约）：`X-OCR-Model / X-OCR-Systemone-Upstream / X-OCR-Latency-MS`。**同一执行器**同时服务 HTTP 面与 Layer-2 路由决策层——一个实现，两个调用方。控制台的智能分配决策模型（`POST /api/admin/client/:client/smart-assign`，以及只读的 `GET /api/admin/decider/resolve` 探针——它回答一次选择实际落在哪个物理模型上）是**第三个调用方**，复用**同一条**别名级联：物理 id、combo 主成员、档位别名→决策面池首位、裸 `auto` → `systemone.defaultModel`——同一个名字在控制台里只有一个含义；控制台调用不带 API key，访问过滤在此为空操作；解析不出的选择直接 400 拒绝，绝不静默替换。

两条执行支路，由解析出的模型 wire 选择（永不由配置表选择）：

- **原生直通（wire `systemone`）**——2026-10-22 修订。解析 npm 为 `@ai-sdk/typesafe-ai`（opencode v1 字符串，或直接写进 defs 文件的 opencode v2 segment `typesafe`）的 provider 定义经共享 `wireFor()` 解析到 wire `systemone`；模型以 `wire: 'systemone'` 进入启动池，决策执行器**直接调用**厂商决策端点：`POST {baseUrl}/systemone`，Bearer 鉴权取自 provider 凭证链，请求体 = 客户端 `{model, state, questions, …}` 形状、model id 改写为 `upstreamModel`，响应 answers **原样透传**（未知 answer 类型如 `box` 不做二次猜测）。chat 池**永不见**这些模型（`getCandidateModelsForTier` 默认排除 `wire === 'systemone'`，仅决策面显式传入时包含）——decision 协议无法应答 chat，把 chat 路由到其上只会把网关自身的错配归咎于上游。厂商 npm 契约由 `@ai-sdk/typesafe-ai` SDK 本体钉死（v3）：`languageModel` 直接 throw `NoSuchModelError`；只有 decision 模型存在，端点 `POST {baseURL}/systemone`，`{model, state, questions}` + Bearer `TYPESAFE_AI_API_KEY`。
- **协议转换（其余所有 chat wire）**——一条 JSON 受限的 chat completion 携全部问题；由此产生的概率是"自报估计、未经校准"（措辞长在协议类型与 reasonCode 分叉里，ADR-0001 §4）。

`X-OCR-Systemone-Upstream` 携带实际采取的支路（`native` / `converted`）——让两条路径在线上可分辨的诚实标记。2026-10-21 退役的 `systemoneUpstreams[]` 配置支路保持退役：原生支路以**数据**（defs 文件的 npm，ADR-0010）回归，而非配置节。

### 8. Responses 续接状态（`responses.persist`）

`/v1/responses` 链存储以内存 L1 Map 为权威；`responses.persist: false` 默认 = 逐字节的纯内存姿态；ON 时向 append-only JSONL 镜像（`<env dataDir>/responses-chain.jsonl`，0600），启动重放（TTL 24h 过滤 → createdAt 序 → 封顶清扫 → 原子压实；边界 20k 节点 / 256KB 单节点 / 64MB 文件 / 每 1000 append 压实一次）。persist 把**重启失忆**缩到"最后一条未刷盘的轮"——链用型客户端若存储滚了，得到的是有文档的显式失败 400（全量重发降级，提示词保住）；磁盘故障只告警、永不拖垮请求；persist-OFF 的链用客户端每进程恰一条告警讲清这层暴露。

## 后果

- 新增一个入站面 = 表里加一行；两种传输自动继承派发、头、捕获、限流行为——逐腿漂移结构性不可能（头模块的注释把旧漂移立为它存在的理由）。
- 捕获答"什么经过了线路"，trace 答"什么被决定并执行"，数据集答"模型该学什么"——三个平面、三个命名空间、任何一把键都不蕴含另一个。
- 隐私姿态默认关/字节同一且有测试钉；opt-in 是两级闸且对暴露范围诚实。
