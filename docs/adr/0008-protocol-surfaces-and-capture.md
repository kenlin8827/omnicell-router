## Decision

### 1. One table, two transports, one seam

`SURFACES` (`surfaces/table.ts:8-23`) is the single registry: one entry per inbound face with `routePath / detectSuffix / exec / capture / encodeStream` (and `encodeChunk` where the client protocol is chunk-shaped end to end). The SAME table drives Fastify route registration (`server.ts:1044-1056`) and MITM path detection (`detectSurface` suffix match) — and the rate-limit route table derives from it too (`INFERENCE_ROUTE_PATHS = SURFACES.map`). `dispatchSurface` branches only on `exec`: `chat-pipeline` | `decision-pipeline`. Both transports build a `TransportContext` (`surfaces/types.ts:58-79`): `method/url/headers/clientIp` + the access gate (discriminated: `kind:'key'` on Fastify — validated bearer/x-api-key + per-key modelAccess, guard already wrote the 403; `kind:'exempt'` on MITM — the client connects THROUGH us, trust lives at the CONNECT/TLS layer + bypass list; no gateway key, so captured events carry no apiKey attribution and upstream calls use the registered provider's own credentials) + `captureProcessContext()` (answers `{}` when capture off) + terminal sends (`sendJson` / `beginSse`+`writeSseChunk`+`endSse`) + `isClientGone()` + `logError`. Terminal-send discipline: exactly one terminal send per request, and parse/gate failures emit ZERO capture events (all pre-dispatch on both legs).

**Streamed turns take the same discipline, with one committed exception.** A turn streams only when every precondition holds: client `stream === true` (C-3 normalization unchanged), the surface has `encodeChunk` and NO `afterResult` hook (that hook must run before the first byte), the serving wire has a streaming executor (today: OpenAI `chat/completions` only — anthropic/google/responses upstreams stay buffered), the serving attempt is not the schema-assertion cascade's LITE lead (its verdict needs the full content and may re-ask the whole turn on a higher tier — the cascade's escalation leg, whose response is final and never re-asserted, streams like the direct path), mock mode off, and `streaming.enabled` not false. Then the relay forwards upstream frames DURING `orchestrator.process`, and the turn can only end two ways: frames → `: ocr-summary` → `data: [DONE]` → `endSse`, or frames → `endSse` **without `[DONE]`** when the upstream broke after the first byte (post-commit: no JSON body is possible, no retry is legal — ADR-0004 §2). If the relay is never fed, nothing was written and the buffered `encodeStream`/`encodeJson` path runs byte-identically to before, which is why the fallback is safe rather than a second code path. `streaming.enabled:false` is a rollback lever, not a tuning knob.

The X-OCR header set is therefore split by WHEN it is knowable, not by wire: routing facts (`Tier/Layer/Model/Session-*/Request-ID/Thinking-Requested/Variant`) flush with the first byte via `buildChatOcrRoutingHeaders`, while completion facts (`Failover*`, `InPlace-Retries`, `Breaker-State`, `Latency-MS`, `TTFT-MS`/`Gen-MS` — the gateway-measured split whose pairing is the output-speed denominator (ADR-0005), absent on buffered turns — `Thinking-Actual/Degraded`) ride the trailing `: ocr-summary` comment frame (`buildChatOcrCompletionFacts`) — a 200 stream must not assert facts of a turn that has not finished, and HTTP trailers are unreadable to `fetch` clients. The buffered legs keep sending the whole set as headers; the SET is uniform, the transport differs. A client that disconnects mid-stream does NOT cancel the upstream call: the gateway drains to the usage frame and credentials the turn normally, because an abort that erases metering would let a caller dodge token rate limits by cancelling repeatedly — the turn is still recorded as its real outcome (synthesized 499 on the client leg, ADR-0008 §5).

### 2. Inbound wire aliases — exactly four; Gemini is an upstream wire

`/v1/chat/completions` (OpenAI-compatible), `/v1/messages` (Anthropic-compatible), `/v1/responses` (OpenAI Responses), `/v1/systemone` (decision gateway). The wire alias table is closed — anything else 404s. (Amended 2026-11-05, ADR-0017: the closed table governs DIRECT `/v1` faces; client-gateway plugins may claim whole SNI hosts BEHIND the MITM leg, where their routes are host-scoped and never become table rows.) Gemini `:generateContent` is OUTBOUND provider wire (`providers/google.ts`; outbound wire set `openai|anthropic|google|responses|systemone|opencode-proxy`), never an inbound alias. The systemone `detectSuffix '/systemone'` is intentionally WIDER than its routePath so the MITM leg claims upstream native decision traffic (typesafe.ai / bailian) passing through the proxy.

### 3. MITM forward proxy — full capture is the point

Default posture: EVERY HTTPS CONNECT MITMs unless loopback or a rule says otherwise (`forwardProxy.rules`, ADR-0018): SNI peek → `startMitm` → decrypted stream spliced into an inner `http.Server` (h1) or a prior-knowledge h2c `http2` compat server (h2, chosen by the connection preface, never by ALPN alone); surface match + POST ⇒ dispatch; otherwise transparent forward — an h1 byte splice (`relay.ts` with backpressure; hop-by-hop header set — connection/keep-alive/TE/trailer/transfer-encoding/upgrade/proxy-* — stripped both directions) or, on the h2 leg, a faithful h2 re-origination upstream (ADR-0017 §3: trailers, bidi, `te: trailers` preserved; h1 fallback when the upstream refuses h2). Request body cap 32 MB (413) and malformed JSON (400) both fail BEFORE capture/dispatch — zero events. Bare-name disambiguation rides `upstreamHost` = the intercepted request's host (`orchestrator.ts:106-124`; the native leg deliberately does NOT trust Host — anti-spoofing, ADR-0003 §1.5).

**Upgrade / WebSocket relay.** An `Upgrade:` handshake (WebSocket included) is caught on the DECRYPTED stream before the inner server and relayed byte-verbatim — request head (plus any bytes already pipelined behind it) → origin socket, then a raw bidirectional splice (`relayUpgrade`). It cannot ride the runtime's own `node:http` upgrade event: on Bun 1.3.14 the socket handed to that handler swallows every write while the parser keeps running and answers 505 to whatever the client sends next, so a `wss://` connection would die at the handshake. Nothing about the handshake is re-serialized (subprotocols, extensions, cookies — any upgrade protocol), because an upgrade is a single hop. It also cannot ride the ordinary forwarder: `connection` and `upgrade` are hop-by-hop, so `filterHeaders` strips exactly the two headers that ARE the handshake. Upstream TLS omits `servername` for an IP-literal origin (`egress.ts` `upstreamServernameOption`): RFC 6066 forbids an IP in SNI and Node/Bun throw on it, and a synchronous throw raised inside a socket `data` listener used to kill the connection silently — the IP decision therefore lives in one helper, and a refused/failed TLS setup answers the client with a 502 instead of escaping. A client-gateway plugin may OWN a handshake on a host it claims (`handleUpgrade`, ADR-0017): returning `true` transfers the decrypted socket wholesale — the gateway writes the `101` itself and drives the stream — while `false` (or no hook) falls through to the transparent relay. Three boundaries stay open BY CONSTRUCTION and are not bugs to "fix" later: non-TLS `ws://` through the plain proxy port (that leg never decrypts, and the same runtime gap blocks its upgrade event), HTTP/3/QUIC (never proxied at all), and upstream client-certificate (mTLS) targets (the terminator holds no client cert, so the origin's CertificateRequest cannot be answered).

**Bounded per-host terminators.** Every MITM'd host gets one listening `tls.Server` plus one minted leaf cert. Full capture sees every host a client visits, so both caches are LRU-bounded — 256 terminators (`server.ts` `MAX_HOST_TERMINATORS`) and 512 certs (`ca.ts` `MAX_CACHED_CERTS`) — and an evicted terminator is closed listener-only: established connections keep their sockets, and the next CONNECT re-mints from the same CA. Unbounded maps here leak file descriptors in proportion to hosts visited, i.e. the failure appears only after the proxy has been useful for a while.

**Decryption scope and the inbound cap.** Interception scope is the rule table's `ingress` column (ADR-0018): `intercept` decrypts, `passthrough` blind-tunnels, and the unmatched fallback is `intercept` — the posture this ADR describes. A passthrough row still proxies the bytes, they are simply never intercepted, which makes it a DECRYPTION SCOPE and not access control (that axis is proxy auth — an OCR API key as the Basic password, ADR-0017). One resolver answers both legs — the CONNECT/MITM admission and the plain-HTTP absolute-URI intercept step — so they cannot disagree, and the CONNECT ledger note carries the decision, so "why was this host not captured" is answerable from the ledger itself. `forwardProxy.maxConnections` (default 512, clamp 16..8192, hot-applies) caps concurrent PROXIED EXCHANGES — one tunneled or MITM'd socket costs two fds (the accepted socket plus its decrypted loopback peer) — enforced at ADMISSION (CONNECT or a plain-HTTP request) rather than at accept time: Bun's `node:http` exposes no accept-side hook (no `'connection'` event on `http.Server`, and both `server.maxConnections` and `server.timeout` are inert — verified on 1.3.14), so a socket that never sends a byte is bounded only by the listen backlog. A slot releases on `end`, `close` OR `error` because the same runtime emits no `close` on the socket it hands a CONNECT handler. `forwardProxy` auth is API-KEY ONLY — WHO may use the proxy: every CONNECT and plain request presents `Proxy-Authorization: Basic <base64 anyuser:keySecret>` (username ignored; the secret is compared in constant time against the live key list) or it is answered 407 with the `Proxy-Authenticate` challenge; loopback with no usable key keeps auth off (the historical posture) unless `forwardProxy.requireCredential` is on. The pre-API-key `forwardProxy.authToken` is RETIRED — dropped on load like every retired key (ADR-0018 §6) and never translated, so an install that authenticated its loopback proxy with a shared token comes back with proxy auth OFF until it creates a key and turns on `requireCredential`. A non-loopback bind without at least one enabled key is REFUSED at start (`forward-proxy/index.ts` `assertForwardProxyBindSafety`, which deliberately does not reuse `isLoopbackHost`: that helper counts `0.0.0.0` as loopback for MITM cycle-safety, the opposite of what a bind gate needs) — an unauthenticated full-capture proxy reachable from the LAN is the worst available default. Strict mode is opt-in for loopback for exactly one reason: a gateway plugin's bound key (`accountKeyId`, ADR-0017) is a server-side fallback for GUI clients that cannot present a proxy credential, and it must never lend that identity to an unauthenticated process on the same machine — with strict mode on, loopback enforces the same credential as the LAN, and a start with no enabled key is refused instead of degrading to open.

**Strict mode also retires OPEN tunnels.** Admission is per-connection, so enabling `forwardProxy.requireCredential` at runtime closes every tunnel that was admitted without a credential (a 1 s sweep over the tracked sockets) — otherwise the toggle would leave an unauthenticated full-capture tunnel alive until the client hung up. The gateway seam independently stops honouring the bound key for such a tunnel, so identity cannot be borrowed even before the socket dies.

**CONNECT carries identity (ADR-0017).** The ONLY proxy credential is an OCR API key as the Basic password (`Proxy-Authorization: Basic <any>:<keySecret>`, username ignored — key names are not unique), resolved against the live key list in constant time and re-checked at dispatch. A tunnel authenticated that way remembers only `{keyId, name}`; the decrypted requests inherit it, so gateway-routed completions are metered as that key while vendor-native relays remain untouched. Terminators are partitioned per key so two identities never share a decrypted connection; a non-loopback bind requires at least one enabled key, and deleting every key at runtime fails closed (407) rather than opening the listener.

Access log for the non-intercepted remainder (`forward-proxy/access-log.ts`, §4 of the observation ledgers): every NON-intercepted HTTP exchange (plus each CONNECT decision — bypassed / mitm / blind-tunnel) lands in a 300-event memory ring, viewable on the Proxy Access page via `GET /api/admin/proxy-log`. Unlike the other three ledgers the ring IS durably mirrored: events append to daily JSONL files under `<ocrHome>/forward-proxy/access-log/` (`forwardProxy.accessLog.persist`, default true) and replay oldest-first into the ring on startup (the ring's trim evicts earliest-appended rows, so chronological replay keeps the most recent history); day files older than `persistDays` (default 7, clamp 1..365) are swept at startup and daily. Binary bodies persist as raw files under `bodies/<day>/` and are fetched through the ONE neutral body endpoint `GET /api/admin/traffic-body/:token` shared with the plugin traffic feeds (ADR-0017 §5): the row carries an opaque token, the resolved ref is grammar-whitelisted and containment-checked, so no traversal and no storage layout on the wire. The forwarders tee both wire sides into an `AccessTap` while piping; bodies are capped per side at `forwardProxy.accessLog.bodyBytes` (default `DEFAULT_PROXY_ACCESS_LOG_BODY_BYTES` = 1 MiB; 0 = headers-only, never marked truncated) — a body that outgrows the cap SPILLS to a raw body file when persistence is on (the whole body: buffered prefix + the tail streamed straight to disk), so the default costs no captured bytes while the heap stays bounded; with persistence off the tail is dropped and the row is marked truncated. Inflate (`gzip`/`br`/`deflate`) carries its own output ceiling — a capped wire body is not a capped allocation. Headers pass the shared credential deny-list, and `forwardProxy.accessLog.enabled` hot-applies per request (default true). LLM-protocol traffic is never duplicated here — it keeps its richer http-exchange capture in the /traces archive.

OS system-proxy ownership (`forward-proxy/system-proxy.ts`, same Proxy Access page): `POST /api/admin/system-proxy/enable` snapshots the CURRENT OS proxy settings (whatever they point at — including a user's clash/v2ray) to `<ocrHome>/forward-proxy/system-proxy.json`, then points the OS proxy at `127.0.0.1:<forwardProxy.port>` with a loopback + literal-`egress: direct` rule-host override list (win32 registry / darwin networksetup per enabled service / GNOME gsettings; anything else reports `unsupported`). Re-enable is idempotent — an existing snapshot is never overwritten, so the user's original settings cannot be clobbered by a second call. `disable` restores the snapshot verbatim and deletes it; with NO snapshot it is a deliberate no-op (never blind-offs a proxy OCR did not set). The snapshot file doubles as crash detection: present while the OS no longer points at us, the status reads `stale` and the console offers one-click restore.

**The CA path has exactly one spelling — and the CA is machine-wide.** The MITM CA dir resolves through `forward-proxy/ca.ts` `resolveCaDir(forwardProxy.caDir)`; the default is the per-user shared data root + `forward-proxy` (the desktop shell's default `OCR_HOME`), NOT an individual book-set's `<ocrHome>`. A trust anchor is MACHINE state: a second install adopts the CA the operator already imported instead of minting a same-CN twin that clients can select by mistake (`CERT_SIGNATURE_FAILURE`). Book-set isolation still covers the access log and the system-proxy snapshot, which stay under `<ocrHome>/forward-proxy/`. On first resolve the shared dir ADOPTS a legacy per-home `<ocrHome>/forward-proxy` CA by copying it (never regenerating — the imported root must survive the move); `OCR_CA_DIR` pins the default for sandboxed test runs. The same single spelling is shared by the proxy itself, the console PEM download, the CA card (`GET /api/admin/proxy/ca/meta` echoes path / SHA-256 fingerprint / subject / validity, never key material) and the system-proxy trust hint. Two guards ride with it: an existing bundle whose CN differs from the requested one makes `ensureCa` THROW instead of silently returning a different identity, and every CA subject carries a key-derived `OU` so several same-CN roots never share one DN. The Windows CA-trust probe compares the EXACT certificate thumbprint (not the CN), so a stale same-CN root can never be reported as "trusted".

**Trust is reported, never assumed.** The console's Proxy Access card and setup wizard show `GET /api/admin/proxy/ca/trust`: a tri-state answer (`trusted` / `not trusted` / `unknown` — a probe that could not run is NEVER flattened into "not trusted") for the EXACT certificate the proxy signs with. `forward-proxy/ca-trust.ts` probes the platform stores the gateway can read — Windows machine + current-user Root store by thumbprint, macOS `security verify-cert` for the real SSL trust policy, Linux anchor files / merged bundles / NSS databases by certificate BODY — and deliberately does not cover application-private roots (Firefox profiles, Java keystores). The verdict is cached 60 s because the probe spawns platform tools; `?force=1` bypasses the TTL so a re-check immediately after an install cannot replay the pre-install answer. Detection never installs anything: importing the root stays an explicit operator action (elevation / OS consent).

### 4. Request identity

Identity is defined by **ADR-0021**: unqualified ids are the gateway's (`requestId` names one request and is the trace record key; `sessionId` names the conversation), foreign namespaces carry a prefix (`clientRequestId`, `upstreamRequestId`) — a client-minted SESSION alias has no field of its own, it is carried by the routing provenance (`request.clientRef`, ADR-0002), and `exchangeId` pairs one HTTP exchange. The shared boundary adapter (`observability/request-identity.ts`) parses inbound `traceparent` > `x-request-id` > `x-trace-id`/`x-correlation-id`/`request-id` into `clientRequestId` (W3C-validate, never mint, never echo); MITM reads the ORIGINAL client request headers. Outbound traceparent injection is NOT implemented (builder exists for tests only). Captured `clientHeaders` are the safe subset `{userAgent, acceptLanguage, clientRequestId}`; authorization/api-key/cookies are structurally never in the trace record. `X-OCR-Session-ID` names the gateway session; `X-OCR-Trace-ID` no longer exists.

### 5. requestCapture — HTTP-exchange events

Namespace: `requestCapture:` — the retired top-level `capture:` section (rename residue), `classifier.layer2.decisionCapture`, key-level `role`, and the retired `requestCapture.systemone` two-gate subtree are load-STRIPPED and never rewritten back on save; both console save paths hot-apply (`routes/console.ts`). One namespace, one meaning: **request/HTTP exchange logging** (training-data sampling is a different concern, ADR-0001 §5).

Model: `CaptureEvent` — one event per direction per leg; a request produces 2–4 events sharing one `requestId` (each request event pairs with its response via `exchangeId`): client-request / client-response / upstream-request / upstream-response. Every line is stamped `schema: 2` (`CAPTURE_SCHEMA`) and carries the WRITE-TIME turn identity of its request — `turnIndex` (null is a first-class value for prompt-less requests), `isPromptStart`, `turnDecision` — plus `attempt` (1-based within `(requestId, leg)`; the client leg is always 1). The boundary is decided structurally at the admission gate (`capture/turn-boundary.ts`, ADR-0024 §4) and every reader copies it; no reader derives a boundary from prompt text, message counts or resend heuristics. Every event additionally carries `conversationKey` (ADR-0002 §1: sha256(apiKey identity + first user message), content-addressed, absent when unresolvable) so the archive can regroup a conversation across volatile session ids. Header regime (current code): NAMES preserved, credential-shaped VALUES `[REDACTED]` via substring deny-list (authorization/api-key/cookie/token/secret/bearer/…-key/key/auth), query-string auth params redacted too; `requestCapture.redactSecrets` (default true) is the operator opt-OUT — when false, header and query values matching the deny-list persist VERBATIM (raw provider keys reach the archive on disk), set from `CaptureRecorder` so constructor and hot-apply agree. Master `enabled:false` default — OFF is a BYTE-IDENTICAL zero-event posture (pinned by tests), on is conscious opt-in (the `/api/admin/*` auth-exempt reminder applies). Sink: `capture/<YYYY-MM-DD>/<sanitized-sessionId>.jsonl` — the live archive root for schema-2 lines; the version rides on the data (`schema: 2` per line), never on the root name. Schema evolution: the live root moves forward IN PLACE by a registered migrator chain (`capture/migrate/`: one `V{N}ToV{N+1}Migrate` class per hop, one file per class under `migrate/steps/`, registered in `migrate/registry.ts`; the engine resolves a hop by `(from, to)`, builds a fresh instance per file so a step's `begin()` planning state is never shared, calls `begin()` once PER HOP over the shape that hop is about to rewrite (a later hop never plans against the disk shape an earlier hop already replaced), and walks the chain with no gap and no skip — the same one-shot ladder `traces.db` follows with `DB_VERSION`). The boot and hot-apply-enable passes process EVERY file — an upgrading installation shows its history immediately — while the hourly sweep touches only files quiet for ten minutes; each rewrite is whole-file atomic (temp file + rename in the same directory) and re-checks the original right before the swap, so an append that lands mid-pass makes that file back off instead of dropping the new bytes, and a line whose hop is unregistered, skipping or unrepresentable leaves the whole file exactly as it was for the next pass while readers keep rejecting it — never a partially migrated archive. A line that is not parseable JSON is not a reason to abandon the file either: it is carried over byte-for-byte (and counted as `unreadable` in the pass summary) so one rotten row can never cost a reader the thousand good ones beside it. Schema 1 is the unmarked baseline (no `schema` field at all) and `V1ToV2Migrate` is a real step, not a tombstone, covering BOTH historical shapes: lines that already carry the gateway ids are taken as-is (`attempt` rebuilt as the ordinal of each distinct `exchangeId` within `(requestId, leg)`), and lines that predate them — `traceId` + `spanId` only — have the request boundary read off the event sequence, because `traceId` is CONNECTION scope (one trace can hold several sequential client requests) while `spanId` is the exchange identity: a `client request` opens a request, the `upstream` spans it causes belong to it, the matching `client response` closes it, and the requestId is minted deterministically from `(sessionId, spanId, ts)` so a re-run mints the same id (idempotent). A sequence that cannot be closed is repaired into the nearest truth-bearing shape rather than guessed at or set aside: an upstream exchange with no open client request becomes a prompt-less ORPHAN REQUEST of its own (`turnIndex: null`, `NO_TURN` — visible and honestly marked, never folded into a neighbouring turn), a second client request opening over an unfinished one simply becomes the next request (the abandoned one keeps its exchanges and turn, minus a response half), a response matching nothing is attached to the request its span opened earlier in the file or stands as an orphan, and a file that ends mid-request keeps its request. The step therefore never refuses a line the engine hands it: every parseable line comes out readable at the target schema. Turn identity in both shapes comes from the SAME structural rule the admission gate uses (`classifyTurnBoundary`), replayed over the bodies the archive already recorded, in file order with the previous request's message count threaded per session (the recorded `promptMessageCount` / `promptLastUserIdx` pair drives it when the body is no longer readable). The retired vocabulary is dropped: `spanId` becomes the `exchangeId`, `traceId` is superseded by the request identity, `promptMessageCount` / `promptLastUserIdx` → nothing. The engine stamps `migratedFrom: 1` on every line it rewrites, so a reconstructed turn identity is never mistaken for an admission-gate stamp. There is no seal, no quarantine and no parking lot: NOTHING is ever moved out of the live root — an upgrade that parked old captures in a directory the runtime never reads would cost the operator the very history the migration exists to preserve. The live root is the only copy, and every line it holds stays viewable after the pass. (`_backup-20261114-1229/` was a one-off operator copy taken at the cutover; it is not part of the mechanism and no code path produces one.) Retention 7 d / 2048 MB pool / body cap 16 MB (sized so one fully-loaded 2M-token context archives untruncated) / per-session seal 512 MB — an archive that reaches its seal stops appending and gets ONE terminal `archive-overflow` line; that line is metadata, so readers MUST NOT count it as a request. The seal exists because agent loops resend full history on every tool-loop request (O(n²) growth within one turn) and one runaway session must not starve the shared pool; the budget is soft (concurrent appends can overshoot by about one line). The console tail-read window scales with the body cap (8 MB floor / 48 MB ceiling); full history is always available via export, which is uncapped. Read plane (console): `readEvents` is ASYNC — fs.promises window read + yield-paced batched JSON.parse — so an archive read never stalls the gateway event loop; `bodies=none` (the metadata-first console default) strips wire bodies from the parsed events and stamps each response event with a read-time-derived `completionTokens` (last usage occurrence in the body) so per-request tok/s chips survive without the bodies; full bodies return per request via `GET /api/admin/capture/:date/:file/request?id=<requestId>` (an `evt_…` event id is accepted too, since either names it) or a `bodies=full` re-read. The request list pages BACKWARDS within that window: `page=1` is the newest slice, older pages count up from there, and each page is cut at a request start so no page renders a half request (`page`/`totalPages`/`hasOlder`/`hasNewer` come back on the response; out-of-range pages clamp, so the pager self-heals). Because the read window is bounded, the header's exact denominator and the whole-archive turn index come from `GET /api/admin/capture/:date/:file/summary`: it streams client-request metadata only (targeted byte-line scans, never `JSON.parse` on multi-MB bodies), counts requests, and reads the WRITE-TIME `turnIndex` off each line to build the turn index (`CaptureTurnIndexEntry`, keyed by `turnIndex`, cached by file stat; stitched shards sum). The pager counts REQUESTS back from the newest end and its read window GROWS on demand up to a hard ceiling — past that the response clamps the page (the pager self-heals) and deeper history stays export-only, so one click can never allocate a seal-sized buffer. The pager is a FIXED footer of the detail pane (only the request list scrolls), 50 requests per page by default; the conversation lens is exempt — it walks every page itself to reconstruct every turn. Turn navigation rides the same write-time metadata: `isPromptStart` marks the request that opened a turn, and its display-only `promptSummary` stamp (written at capture time, never derived) labels the selector entry, so the console can group the loaded page into turns and narrow the view to one turn without any wire-body parse. Cross-midnight conversations are stitched read-side: `stitched=1` on the events window and the request endpoint merges the per-date shards of one conversation (`readEventsStitched`/`readRequestStitched`; shard discovery via `listSessionsWithSpans` is bounded to cached ≤64 KB head reads and session rows carry `spanDates`); the frontend renders the span as a badge plus per-day dividers. Session rows also carry `protocol` — the inbound surface derived from the FIRST client-request event's request line (`/v1/chat/completions` → chat, `/v1/messages` → anthropic, `/v1/responses` → responses, `/v1/systemone` → systemone; archives without request lines stay undefined = unbadged) — and the preview/prompt extractors treat a System One body's `state` (string or structured JSON, capped) as the user text, so decision-surface sessions get a content title instead of the raw session id. boot + hourly sweeps, ALL I/O fail-open. Client-response body stash capped 1 MB; client disconnects finalize through the transports (synthesized 499) — hang/cancel still leaves a record. A STREAMED upstream leg records the raw `text/event-stream` body of that exchange (in-memory accumulation capped at 256 KB before the recorder's own per-field truncation, `[DONE]` included), so `upstream/response` answers "which frames actually crossed the wire" and a truncated stream is visible AS truncated; the outbound client leg keeps stashing SSE frames per chunk under the 1 MB cap. Streaming emits no extra event kinds — the same request/response pair, with a different body shape. A STREAMED response event additionally carries `firstByteTs` (epoch ms of the first body chunk, stamped at the wire: upstream SSE reader loop / client SSE write; buffered single-shot replies stay stamp-less), and `groupEventsIntoRequests` derives per-leg `ttftMs`/`genMs` from it — the capture plane reports the SAME TTFT/decode-TPS vocabulary as the trace plane (ADR-0005 §8), never a rate synthesized from full latency. The `/v1/systemone` surface itself never captures FinOps or trace rows — capture is exchange events only.

Vocabulary (ADR-0024, authoritative): `session ⊃ turn ⊃ request ⊃ exchange ⊃ event`. The request projection the console renders is `CaptureRequestSummary` with an `exchanges[]` list bucketed by `(leg, attempt)` — every failover hop and the Layer-2 decision pair stay visible, one drawer tab per exchange phase; the pre-contract six fixed slots and the `round*` read-plane symbols (`roundNumber`, `totalRounds`, `CaptureRoundIndexEntry`) are deleted. `requestNumber` is the 1-based request ordinal inside the read window (the pager's unit); turn membership is the immutable write-time `turnIndex`, never folded into it and never renumbered. `promptSummary` is stamped at write time on the prompt-start client-request event only (display-only; a continuation never gets one) — the retired read-plane staleness dedupe (`promptMessageCount`/`promptLastUserIdx`) is gone. The recorder stays cross-request stateless (capture is fail-open and restart-transparent); the turn high-water lives in the session-manager snapshot (`v: 3`), not in the recorder.

### 6. System One surface — single-master capture

The retired two-gate tree (`requestCapture.systemone.{enabled, l2DecisionEnabled}` — a surface gate default ON plus a decision-call sub-switch default ON) is load-STRIPPED and never rewritten back on save: both gates defaulted TRUE, so they only ever NARROWED an already-explicit privacy opt-in, at the cost of making the capture card read like System One surface configuration (operator-facing confusion, retired 2026-12). The single `requestCapture.enabled` master (default OFF) now gates every leg — the `/v1/systemone` client pair, the surface's own upstream pair (the native passthrough or the synthesized conversion call, per the resolved wire; no purpose tag), and the Layer-2 decision layer's internal call leg (attached to the OUTER routed request as upstream direction, `purpose:'l2-decision'`, the sole `ExchangePurpose` value; the orchestrator only hands the decision layer a capture ctx while the master is on). Emission is strictly AFTER all 400/403/404/503 gates. Privacy posture when off: `captureProcessContext()` returns `{}`, the surface path is byte-identical to a build without capture.

### 7. The decision gateway (/v1/systemone) — wire-driven, honesty by wording

Model semantics on this surface: named model = that model; tier aliases resolve by PURE POOL PROJECTION to the leading model of the access-filtered pool — 404 unknown/no-pool, 403 denied, 503 unresolvable, NEVER a silent fallback; bare/`auto`/omitted → `systemone.defaultModel`; decision-line rate accounting counts but never locally rejects (the decision layer is a below-request leg). Exactly three response headers (frozen contract): `X-OCR-Model / X-OCR-Systemone-Upstream / X-OCR-Latency-MS`. The SAME executor backs the Layer-2 router decision layer — one implementation, two callers. The console's smart-assign decider (`POST /api/admin/client/:client/smart-assign`, plus the free `GET /api/admin/decider/resolve` probe that shows what a pick resolves to) is a THIRD caller and reuses the SAME alias cascade — physical id, combo leader, tier-alias decision-surface pool leader, bare `auto` → `systemone.defaultModel` — so a name means one thing console-wide; console calls carry no API key, so the access filter is a no-op there, and an unresolvable pick is refused (400) rather than silently substituted.

Two execution limbs, selected by the resolved model's wire (never by config tables):

- **Native passthrough (wire `systemone`)** — the 2026-10-22 amendment. A provider def whose resolved npm is `@ai-sdk/typesafe-ai` (opencode v1 string, or the opencode v2 segment `typesafe` written directly into the defs file) resolves through the shared `wireFor()` to wire `systemone`; the model enters the boot pool with `wire: 'systemone'` and the decision executor calls the vendor's decision endpoint DIRECTLY: `POST {baseUrl}/systemone`, Bearer auth from the provider's credential chain, body = the client's `{model, state, questions, …}` shape with the model id rewritten to `upstreamModel`, response answers passed through verbatim (unknown answer types such as `box` are NOT second-guessed). The chat pool NEVER sees these models (`getCandidateModelsForTier` excludes `wire === 'systemone'` unless the decision-surface opt-in is passed) — a decision protocol cannot answer chat, and routing chat at one would only blame the upstream for the gateway's own mismatch. The vendor npm contract is pinned by the `@ai-sdk/typesafe-ai` SDK itself (v3): `languageModel` throws `NoSuchModelError`; only the decision model exists, on `POST {baseURL}/systemone` with `{model, state, questions}` and Bearer `TYPESAFE_AI_API_KEY`.
- **Protocol conversion (every chat wire)** — one JSON-constrained chat completion carrying all questions; the response's probabilities are then "self-reported estimates, NOT calibrated" (wording lives in the protocol types + reasonCode split, ADR-0001 §4).

`X-OCR-Systemone-Upstream` carries the limb actually taken (`native` / `converted`) — the honesty marker that keeps the two paths distinguishable on the wire. The retired 2026-10-21 `systemoneUpstreams[]` config limb stays retired: the native limb returns as DATA (the defs-file npm, ADR-0010), not as a config section.

### 8. Responses continuation state (`responses.persist`)

The `/v1/responses` chain store is authoritative in-memory (L1 Map); `responses.persist: false` default = byte-for-byte in-memory posture; ON mirrors an append-only JSONL (`<env dataDir>/responses-chain.jsonl`, 0600) replayed at boot (TTL filter 24 h → createdAt order → cap sweep → atomic compaction; boundaries 20 k nodes / 256 KB node / 64 MB file / compact per 1000 appends). Persist turns RESTART AMNESIA into "lost the last unflushed turn" — a chain-using client whose store rolled gets the documented fail-visible 400 (full-resend degradation, prompt preserved); disk failure only ever warns, never fails a request; persist-OFF chain users get a one-per-process warn explaining the exposure.

## Consequences

- Adding an inbound face = one table row; both transports inherit dispatch, header, capture and rate-limit behavior — per-leg drift is structurally impossible (the header module's comment records the old drift as the reason it exists).
- Capture answers "what crossed the wire", traces answer "what decided and executed", datasets answer "what should the models learn" — three planes, three namespaces, no key implies another.
- Privacy postures are default-off/byte-identical and test-pinned, opt-in is two-level and honest about exposure.
