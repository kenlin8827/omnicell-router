# ADR-0008: Protocol Surfaces and Capture — One Dispatch Table for Both Transports, Exchange Events Not Turn Snapshots, Opt-in Full-Chain

## Status

Implemented — 2026-10-15 (facts-side corpus rewrite). Amended 2026-12: the MITM leg relays `Upgrade:`/WebSocket handshakes itself — the runtime's own upgrade event is unusable (§3) — per-host TLS terminators and minted leaf certs are LRU-bounded, and `forwardProxy.accessLog.bodyBytes` gained a finite default (1 MiB) whose overflow spills to a raw body file instead of growing the heap. Amended 2026-11-05: client-gateway plugins (ADR-0017) claim whole SNI hosts behind the MITM leg — the surface table stays closed for direct `/v1` faces, gateway routes are host-scoped and never become rows. Amended 2026-10-21: the native System One upstream limb (`systemoneUpstreams[]`, vendor passthrough) is RETIRED — the surface serves exclusively via chat-model conversion; a future Jev/Bailian integration arrives as an ordinary provider through the defs file (ADR-0010). Amended 2026-10-24: the write-side `@ai-sdk/typesafe-ai` → package mapping keeps the native `typesafe` segment and the alias stays in the npm vocabulary — the 2026-10-23 downgrade (compatible runtime + alias withheld from the dropdown) is reverted as a regression. Client loadability remains a separate layer: the client copy is substituted by `CLIENT_PACKAGE_FALLBACK` when the client ships no such segment (ADR-0010 amendment). Amended 2026-10-22: the native decision limb is REINSTATED, wire-driven — a provider def whose resolved npm is `@ai-sdk/typesafe-ai` (or the opencode v2 segment `typesafe`) resolves to wire `systemone` and serves the decision surface as a NATIVE passthrough call (§7); conversion remains the path for every chat-wire model. Scope: the inbound protocol faces (native routes + MITM proxy), their shared dispatch seam, the System One decision gateway, and the request-capture plane. Trace persistence/observability split = ADR-0005; dataset sampling (NOT capture) = ADR-0001; addressing on the decision surface = ADR-0003.

## Decision

### 1. One table, two transports, one seam

`SURFACES` (`surfaces/table.ts:8-23`) is the single registry: one entry per inbound face with `routePath / detectSuffix / exec / capture / encodeStream` (and `encodeChunk` where the client protocol is chunk-shaped end to end). The SAME table drives Fastify route registration (`server.ts:1044-1056`) and MITM path detection (`detectSurface` suffix match) — and the rate-limit route table derives from it too (`INFERENCE_ROUTE_PATHS = SURFACES.map`). `dispatchSurface` branches only on `exec`: `chat-pipeline` | `decision-pipeline`. Both transports build a `TransportContext` (`surfaces/types.ts:58-79`): `method/url/headers/clientIp` + the access gate (discriminated: `kind:'key'` on Fastify — validated bearer/x-api-key + per-key modelAccess, guard already wrote the 403; `kind:'exempt'` on MITM — the client connects THROUGH us, trust lives at the CONNECT/TLS layer + bypass list; no gateway key, so captured events carry no apiKey attribution and upstream calls use the registered provider's own credentials) + `captureProcessContext()` (answers `{}` when capture off) + terminal sends (`sendJson` / `beginSse`+`writeSseChunk`+`endSse`) + `isClientGone()` + `logError`. Terminal-send discipline: exactly one terminal send per request, and parse/gate failures emit ZERO capture events (all pre-dispatch on both legs).

**Streamed turns take the same discipline, with one committed exception.** A turn streams only when every precondition holds: client `stream === true` (C-3 normalization unchanged), the surface has `encodeChunk` and NO `afterResult` hook (that hook must run before the first byte), the serving wire has a streaming executor (today: OpenAI `chat/completions` only — anthropic/google/responses upstreams stay buffered), the serving attempt is not the schema-assertion cascade's LITE lead (its verdict needs the full content and may re-ask the whole turn on a higher tier — the cascade's escalation leg, whose response is final and never re-asserted, streams like the direct path), mock mode off, and `streaming.enabled` not false. Then the relay forwards upstream frames DURING `orchestrator.process`, and the turn can only end two ways: frames → `: ocr-summary` → `data: [DONE]` → `endSse`, or frames → `endSse` **without `[DONE]`** when the upstream broke after the first byte (post-commit: no JSON body is possible, no retry is legal — ADR-0004 §2). If the relay is never fed, nothing was written and the buffered `encodeStream`/`encodeJson` path runs byte-identically to before, which is why the fallback is safe rather than a second code path. `streaming.enabled:false` is a rollback lever, not a tuning knob.

The X-OCR header set is therefore split by WHEN it is knowable, not by wire: routing facts (`Tier/Layer/Model/Session-*/Trace-ID/Thinking-Requested/Variant`) flush with the first byte via `buildChatOcrRoutingHeaders`, while completion facts (`Failover*`, `InPlace-Retries`, `Breaker-State`, `Latency-MS`, `Thinking-Actual/Degraded`) ride the trailing `: ocr-summary` comment frame (`buildChatOcrCompletionFacts`) — a 200 stream must not assert facts of a turn that has not finished, and HTTP trailers are unreadable to `fetch` clients. The buffered legs keep sending the whole set as headers; the SET is uniform, the transport differs. A client that disconnects mid-stream does NOT cancel the upstream call: the gateway drains to the usage frame and credentials the turn normally, because an abort that erases metering would let a caller dodge token rate limits by cancelling repeatedly — the turn is still recorded as its real outcome (synthesized 499 on the client leg, ADR-0008 §5).

### 2. Inbound wire aliases — exactly four; Gemini is an upstream wire

`/v1/chat/completions` (OpenAI-compatible), `/v1/messages` (Anthropic-compatible), `/v1/responses` (OpenAI Responses), `/v1/systemone` (decision gateway). The wire alias table is closed — anything else 404s. (Amended 2026-11-05, ADR-0017: the closed table governs DIRECT `/v1` faces; client-gateway plugins may claim whole SNI hosts BEHIND the MITM leg, where their routes are host-scoped and never become table rows.) Gemini `:generateContent` is OUTBOUND provider wire (`providers/google.ts`; outbound wire set `openai|anthropic|google|responses|systemone|opencode-proxy`), never an inbound alias. The systemone `detectSuffix '/systemone'` is intentionally WIDER than its routePath so the MITM leg claims upstream native decision traffic (typesafe.ai / bailian) passing through the proxy.

### 3. MITM forward proxy — full capture is the point

Default posture: EVERY HTTPS CONNECT MITMs unless loopback or a rule says otherwise (`forwardProxy.rules`, ADR-0018): SNI peek → `startMitm` → decrypted stream spliced into an inner `http.Server` (h1) or a prior-knowledge h2c `http2` compat server (h2, chosen by the connection preface, never by ALPN alone); surface match + POST ⇒ dispatch; otherwise transparent forward — an h1 byte splice (`relay.ts` with backpressure; hop-by-hop header set — connection/keep-alive/TE/trailer/transfer-encoding/upgrade/proxy-* — stripped both directions) or, on the h2 leg, a faithful h2 re-origination upstream (ADR-0017 §3: trailers, bidi, `te: trailers` preserved; h1 fallback when the upstream refuses h2). Request body cap 32 MB (413) and malformed JSON (400) both fail BEFORE capture/dispatch — zero events. Bare-name disambiguation rides `upstreamHost` = the intercepted request's host (`orchestrator.ts:106-124`; the native leg deliberately does NOT trust Host — anti-spoofing, ADR-0003 §1.5).

**Upgrade / WebSocket relay.** An `Upgrade:` handshake (WebSocket included) is caught on the DECRYPTED stream before the inner server and relayed byte-verbatim — request head (plus any bytes already pipelined behind it) → origin socket, then a raw bidirectional splice (`relayUpgrade`). It cannot ride the runtime's own `node:http` upgrade event: on Bun 1.3.14 the socket handed to that handler swallows every write while the parser keeps running and answers 505 to whatever the client sends next, so a `wss://` connection would die at the handshake. Nothing about the handshake is re-serialized (subprotocols, extensions, cookies — any upgrade protocol), because an upgrade is a single hop. It also cannot ride the ordinary forwarder: `connection` and `upgrade` are hop-by-hop, so `filterHeaders` strips exactly the two headers that ARE the handshake. Upstream TLS omits `servername` for an IP-literal origin (`egress.ts` `upstreamServernameOption`): RFC 6066 forbids an IP in SNI and Node/Bun throw on it, and a synchronous throw raised inside a socket `data` listener used to kill the connection silently — the IP decision therefore lives in one helper, and a refused/failed TLS setup answers the client with a 502 instead of escaping. A client-gateway plugin may OWN a handshake on a host it claims (`handleUpgrade`, ADR-0017): returning `true` transfers the decrypted socket wholesale — the gateway writes the `101` itself and drives the stream — while `false` (or no hook) falls through to the transparent relay. Three boundaries stay open BY CONSTRUCTION and are not bugs to "fix" later: non-TLS `ws://` through the plain proxy port (that leg never decrypts, and the same runtime gap blocks its upgrade event), HTTP/3/QUIC (never proxied at all), and upstream client-certificate (mTLS) targets (the terminator holds no client cert, so the origin's CertificateRequest cannot be answered).

**Bounded per-host terminators.** Every MITM'd host gets one listening `tls.Server` plus one minted leaf cert. Full capture sees every host a client visits, so both caches are LRU-bounded — 256 terminators (`server.ts` `MAX_HOST_TERMINATORS`) and 512 certs (`ca.ts` `MAX_CACHED_CERTS`) — and an evicted terminator is closed listener-only: established connections keep their sockets, and the next CONNECT re-mints from the same CA. Unbounded maps here leak file descriptors in proportion to hosts visited, i.e. the failure appears only after the proxy has been useful for a while.

**Decryption scope and the inbound cap.** Interception scope is the rule table's `ingress` column (ADR-0018): `intercept` decrypts, `passthrough` blind-tunnels, and the unmatched fallback is `intercept` — the posture this ADR describes. A passthrough row still proxies the bytes, they are simply never intercepted, which makes it a DECRYPTION SCOPE and not access control (that axis is proxy auth, still absent). One resolver answers both legs — the CONNECT/MITM admission and the plain-HTTP absolute-URI intercept step — so they cannot disagree, and the CONNECT ledger note carries the decision, so "why was this host not captured" is answerable from the ledger itself. `forwardProxy.maxConnections` (default 512, clamp 16..8192, hot-applies) caps concurrent PROXIED EXCHANGES — one tunneled or MITM'd socket costs two fds (the accepted socket plus its decrypted loopback peer) — enforced at ADMISSION (CONNECT or a plain-HTTP request) rather than at accept time: Bun's `node:http` exposes no accept-side hook (no `'connection'` event on `http.Server`, and both `server.maxConnections` and `server.timeout` are inert — verified on 1.3.14), so a socket that never sends a byte is bounded only by the listen backlog. A slot releases on `end`, `close` OR `error` because the same runtime emits no `close` on the socket it hands a CONNECT handler. `forwardProxy.authToken` closes the other axis — WHO may use the proxy: set = every CONNECT and plain request must present `Proxy-Authorization: Basic <base64 anyuser:token>` (the token is the secret, compared in constant time) or it is answered 407 with the `Proxy-Authenticate` challenge; unset = auth off, which is legal ONLY on a loopback bind. Any other bind without a token is REFUSED at start (`forward-proxy/index.ts` `assertForwardProxyBindSafety`, which deliberately does not reuse `isLoopbackHost`: that helper counts `0.0.0.0` as loopback for MITM cycle-safety, the opposite of what a bind gate needs) — an unauthenticated full-capture proxy reachable from the LAN is the worst available default.

Access log for the non-intercepted remainder (`forward-proxy/access-log.ts`, §4 of the observation ledgers): every NON-intercepted HTTP exchange (plus each CONNECT decision — bypassed / mitm / blind-tunnel) lands in a 300-event memory ring, viewable on the Proxy Access page via `GET /api/admin/proxy-log`. Unlike the other three ledgers the ring IS durably mirrored: events append to daily JSONL files under `<ocrHome>/forward-proxy/access-log/` (`forwardProxy.accessLog.persist`, default true) and replay oldest-first into the ring on startup (the ring's trim evicts earliest-appended rows, so chronological replay keeps the most recent history); day files older than `persistDays` (default 7, clamp 1..365) are swept at startup and daily. Binary bodies persist as raw files under `bodies/<day>/` and are fetched through the ONE neutral body endpoint `GET /api/admin/traffic-body/:token` shared with the plugin traffic feeds (ADR-0017 §5): the row carries an opaque token, the resolved ref is grammar-whitelisted and containment-checked, so no traversal and no storage layout on the wire. The forwarders tee both wire sides into an `AccessTap` while piping; bodies are capped per side at `forwardProxy.accessLog.bodyBytes` (default `DEFAULT_PROXY_ACCESS_LOG_BODY_BYTES` = 1 MiB; 0 = headers-only, never marked truncated) — a body that outgrows the cap SPILLS to a raw body file when persistence is on (the whole body: buffered prefix + the tail streamed straight to disk), so the default costs no captured bytes while the heap stays bounded; with persistence off the tail is dropped and the row is marked truncated. Inflate (`gzip`/`br`/`deflate`) carries its own output ceiling — a capped wire body is not a capped allocation. Headers pass the shared credential deny-list, and `forwardProxy.accessLog.enabled` hot-applies per request (default true). LLM-protocol traffic is never duplicated here — it keeps its richer http-exchange capture in the /traces archive.

OS system-proxy ownership (`forward-proxy/system-proxy.ts`, same Proxy Access page): `POST /api/admin/system-proxy/enable` snapshots the CURRENT OS proxy settings (whatever they point at — including a user's clash/v2ray) to `<ocrHome>/forward-proxy/system-proxy.json`, then points the OS proxy at `127.0.0.1:<forwardProxy.port>` with a loopback + literal-`egress: direct` rule-host override list (win32 registry / darwin networksetup per enabled service / GNOME gsettings; anything else reports `unsupported`). Re-enable is idempotent — an existing snapshot is never overwritten, so the user's original settings cannot be clobbered by a second call. `disable` restores the snapshot verbatim and deletes it; with NO snapshot it is a deliberate no-op (never blind-offs a proxy OCR did not set). The snapshot file doubles as crash detection: present while the OS no longer points at us, the status reads `stale` and the console offers one-click restore.

### 4. Trace identity, both legs identical

One shared extractor (`observability/trace-id.ts`): inbound precedence `traceparent` > `x-request-id` > `x-trace-id`/`x-correlation-id`/`request-id` > mint 32-hex (W3C-validate-or-mint, never echo malformed); MITM reads the ORIGINAL client request headers. Outbound traceparent injection is NOT implemented (builder exists for tests only). Captured `clientHeaders` are the safe subset `{userAgent, acceptLanguage, requestId}`; authorization/api-key/cookies are structurally never in the trace record.

### 5. requestCapture — HTTP-exchange events, not turn snapshots

Namespace: `requestCapture:` — the retired top-level `capture:` section (rename residue), `classifier.layer2.decisionCapture`, key-level `role`, and the retired `requestCapture.systemone` two-gate subtree are load-STRIPPED and never rewritten back on save; both console save paths hot-apply (`routes/console.ts:1074,1098`). One namespace, one meaning: **request/HTTP exchange logging** (training-data sampling is a different concern, ADR-0001 §5).

Model: `HttpExchangeEvent` — one event per direction per leg; an inference turn produces 2–4 events sharing one `traceId`: client-request / gateway-response / upstream-request / upstream-response (the older turn-shaped `CaptureRecord` is @deprecated). Every event additionally carries `conversationKey` (ADR-0002 §1: sha256(apiKey identity + first user message), content-addressed, absent when unresolvable) so the archive can regroup a conversation across volatile session ids. Header regime (current code): NAMES preserved, credential-shaped VALUES `[REDACTED]` via substring deny-list (authorization/api-key/cookie/token/secret/bearer/…-key/key/auth), query-string auth params redacted too; `requestCapture.redactSecrets` (default true) is the operator opt-OUT — when false, header and query values matching the deny-list persist VERBATIM (raw provider keys reach the archive on disk), set from `CaptureRecorder` so constructor and hot-apply agree. Master `enabled:false` default — OFF is a BYTE-IDENTICAL zero-event posture (pinned by tests), on is conscious opt-in (the `/api/admin/*` auth-exempt reminder applies). Sink: `<capture>/<YYYY-MM-DD>/<sanitized-sessionId>.jsonl`, retention 7 d / 2048 MB pool / body cap 16 MB (sized so one fully-loaded 2M-token context archives untruncated) / per-session seal 512 MB — an archive that reaches its seal stops appending and gets ONE terminal `archive-overflow` line; that line is metadata, so readers MUST NOT count it as a turn. The seal exists because agent loops resend full history every turn (O(turns²) growth) and one runaway session must not starve the shared pool; the budget is soft (concurrent appends can overshoot by about one line). The console tail-read window scales with the body cap (8 MB floor / 48 MB ceiling); full history is always available via export, which is uncapped. Read plane (console): `readEvents` is ASYNC — fs.promises window read + yield-paced batched JSON.parse — so an archive read never stalls the gateway event loop; `bodies=none` (the metadata-first console default) strips wire bodies from the parsed events and stamps each response event with a read-time-derived `completionTokens` (last usage occurrence in the body) so per-turn tok/s chips survive without the bodies; full bodies return per turn via `GET /api/admin/capture/:date/:file/turn?id=<client-request event id>` or a `bodies=full` re-read. Cross-midnight conversations are stitched read-side: `stitched=1` on the events window and the turn endpoint merges the per-date shards of one conversation (`readEventsStitched`/`readTurnStitched`; shard discovery via `listSessionsWithSpans` is bounded to cached ≤64 KB head reads and session rows carry `spanDates`); the frontend renders the span as a badge plus per-day dividers. Session rows also carry `protocol` — the inbound surface derived from the FIRST client-request event's request line (`/v1/chat/completions` → chat, `/v1/messages` → anthropic, `/v1/responses` → responses, `/v1/systemone` → systemone; legacy archives without request lines stay undefined = unbadged) — and the preview/prompt extractors treat a System One body's `state` (string or structured JSON, capped) as the user text, so decision-surface sessions get a content title instead of the raw session id. boot + hourly sweeps, ALL I/O fail-open. Gateway-response body stash capped 1 MB; client disconnects finalize through the transports (synthesized 499) — hang/cancel still leaves a record. A STREAMED upstream leg records the raw `text/event-stream` body of that exchange (in-memory accumulation capped at 256 KB before the recorder's own per-field truncation, `[DONE]` included), so `upstream/response` answers "which frames actually crossed the wire" and a truncated stream is visible AS truncated; the outbound client leg keeps stashing SSE frames per chunk under the 1 MB gateway cap. Streaming emits no extra event kinds — the same request/response pair, with a different body shape. A STREAMED response event additionally carries `firstByteTs` (epoch ms of the first body chunk, stamped at the wire: upstream SSE reader loop / gateway SSE write; buffered single-shot replies stay stamp-less), and `groupEventsIntoTurns` derives per-leg `ttftMs`/`genMs` from it — the capture plane reports the SAME TTFT/decode-TPS vocabulary as the trace plane (ADR-0005 §8), never a rate synthesized from full latency. The `/v1/systemone` surface itself never captures FinOps or trace rows — capture is exchange events only.

### 6. System One surface — single-master capture

The retired two-gate tree (`requestCapture.systemone.{enabled, l2DecisionEnabled}` — a surface gate default ON plus a decision-call sub-switch default ON) is load-STRIPPED and never rewritten back on save: both gates defaulted TRUE, so they only ever NARROWED an already-explicit privacy opt-in, at the cost of making the capture card read like System One surface configuration (operator-facing confusion, retired 2026-12). The single `requestCapture.enabled` master (default OFF) now gates every leg — the `/v1/systemone` client pair, the surface's own upstream pair (the native passthrough or the synthesized conversion call, per the resolved wire; no purpose tag), and the Layer-2 decision layer's internal call leg (attached to the OUTER routed request as upstream direction, `purpose:'l2-decision'`, the sole `ExchangePurpose` value; the orchestrator only hands the decision layer a capture ctx while the master is on). Emission is strictly AFTER all 400/403/404/503 gates. Privacy posture when off: `captureProcessContext()` returns `{}`, the surface path is byte-identical to a build without capture.

### 7. The decision gateway (/v1/systemone) — wire-driven, honesty by wording

Model semantics on this surface: named model = that model; tier aliases resolve by PURE POOL PROJECTION to the chain head of the access-filtered pool — 404 unknown/no-pool, 403 denied, 503 unresolvable, NEVER a silent fallback; bare/`auto`/omitted → `systemone.defaultModel`; decision-line rate accounting counts but never locally rejects (the decision layer is a below-request leg). Exactly three response headers (frozen contract): `X-OCR-Model / X-OCR-Systemone-Upstream / X-OCR-Latency-MS`. The SAME executor backs the Layer-2 router decision layer — one implementation, two callers. The console's smart-assign decider (`POST /api/admin/client/:client/smart-assign`, plus the free `GET /api/admin/decider/resolve` probe that shows what a pick resolves to) is a THIRD caller and reuses the SAME alias cascade — physical id, combo leader, tier-alias decision-surface pool head, bare `auto` → `systemone.defaultModel` — so a name means one thing console-wide; console calls carry no API key, so the access filter is a no-op there, and an unresolvable pick is refused (400) rather than silently substituted.

Two execution limbs, selected by the resolved model's wire (never by config tables):

- **Native passthrough (wire `systemone`)** — the 2026-10-22 amendment. A provider def whose resolved npm is `@ai-sdk/typesafe-ai` (opencode v1 string, or the opencode v2 segment `typesafe` written directly into the defs file) resolves through the shared `wireFor()` to wire `systemone`; the model enters the boot pool with `wire: 'systemone'` and the decision executor calls the vendor's decision endpoint DIRECTLY: `POST {baseUrl}/systemone`, Bearer auth from the provider's credential chain, body = the client's `{model, state, questions, …}` shape with the model id rewritten to `upstreamModel`, response answers passed through verbatim (unknown answer types such as `box` are NOT second-guessed). The chat pool NEVER sees these models (`getCandidateModelsForTier` excludes `wire === 'systemone'` unless the decision-surface opt-in is passed) — a decision protocol cannot answer chat, and routing chat at one would only blame the upstream for the gateway's own mismatch. The vendor npm contract is pinned by the `@ai-sdk/typesafe-ai` SDK itself (v3): `languageModel` throws `NoSuchModelError`; only the decision model exists, on `POST {baseURL}/systemone` with `{model, state, questions}` and Bearer `TYPESAFE_AI_API_KEY`.
- **Protocol conversion (every chat wire)** — one JSON-constrained chat completion carrying all questions; the response's probabilities are then "self-reported estimates, NOT calibrated" (wording lives in the protocol types + reasonCode split, ADR-0001 §4).

`X-OCR-Systemone-Upstream` carries the limb actually taken (`native` / `converted`) — the honesty marker that keeps the two paths distinguishable on the wire. The retired 2026-10-21 `systemoneUpstreams[]` config limb stays retired: the native limb returns as DATA (the defs-file npm, ADR-0010), not as a config section.

### 8. Responses continuation state (`responses.persist`)

The `/v1/responses` chain store is authoritative in-memory (L1 Map); `responses.persist: false` default = byte-for-byte in-memory posture; ON mirrors an append-only JSONL (`<env dataDir>/responses-chain.jsonl`, 0600) replayed at boot (TTL filter 24 h → createdAt order → cap sweep → atomic compaction; boundaries 20 k nodes / 256 KB node / 64 MB file / compact per 1000 appends). Persist turns RESTART AMNESIA into "lost the last unflushed turn" — a chain-using client whose store rolled gets the documented fail-visible 400 (full-resend degradation, prompt preserved); disk failure only ever warns, never fails a request; persist-OFF chain users get a one-per-process warn explaining the exposure.

## Consequences

- Adding an inbound face = one table row; both transports inherit dispatch, header, capture and rate-limit behavior — per-leg drift is structurally impossible (the header module's comment records the old drift as the reason it exists).
- Capture answers "what crossed the wire", traces answer "what decided and executed", datasets answer "what should the models learn" — three planes, three namespaces, no key implies another.
- Privacy postures are default-off/byte-identical and test-pinned, opt-in is two-level and honest about exposure.
