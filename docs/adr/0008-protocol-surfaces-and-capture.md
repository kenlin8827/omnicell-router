(b): an inbound `Expect: 100-continue` is settled from the headers alone on BOTH legs by `settleContinuationExpectation` — a final 413/415 with `connection: close` and NO `100` when the declared length passes the cap or the media type / content coding is already refused, else the continue is written and the caller dispatches; the listener exists because Node otherwise writes `100` before any policy runs, and a continuation answered inside a pre-dispatch handler is a protocol violation Node answers with `ECONNRESET`. (c): refusals carry the negotiation field their cause owns (RFC 9110 §15.5.16 / §12.5.3) — `Accept-Encoding` on a coding 415, `Accept` on a media-type 415, NEITHER on a 413, and no `Retry-After` (a standing cap is not a temporary condition); the Anthropic surface types a 413 `request_too_large`, and an unframeable `Content-Length` (duplicated, non-numeric, or not matching the delivered bytes) is `invalid_content_length` (400). (d): a body that crosses the ceiling WHILE it is still arriving is answered, not reset — the transport `pause()`s (a `destroy()` here killed the reply before a byte of it could be written, which is what a chunked or gzip-inflated overrun used to look like from the client side), writes the envelope with `connection: close`, and only then drops the socket; the two proxy legs answer a parser-level framing fault from the `clientError` code (`HPE_HEADER_OVERFLOW` → 431, else 400, with `connection: close`) and the write is deferred one tick because Bun discards a reply written synchronously inside a `clientError` listener; the header gate refuses an ambiguous `Content-Length` before the body is read and `filterHeaders` never relays one, so the gateway cannot carry a request-smuggling attempt upstream. (e): every listener the gateway owns arms its OWN inbound liveness bounds — `applyInboundLiveness` (`utils/server-liveness.ts`) sets `SERVER_REQUEST_TIMEOUT_MS` (5 min), `SERVER_HEADERS_TIMEOUT_MS` (60 s) and `SERVER_KEEP_ALIVE_TIMEOUT_MS` (5 s) on the native Fastify instance and on both HTTP/1 proxy legs, because those are Node's shipped numbers and **Bun ships none**: leaving them to the runtime made socket liveness a function of which runtime started the process, the same class of defect as the original 413. They are NOT operator knobs — they bound socket hygiene, not what a model may be asked to carry, which is why `client.bodyLimits` is tunable and these are not. The h2 inner listener carries none by design (a multiplexed session may legitimately sit open between streams; its body is still bounded by the transport timer below and its lifetime by the CONNECT keepalive). A server-level clock measures the WHOLE request, so it cannot see a body that stops progressing: `readRequestBody` re-arms `REQUEST_BODY_IDLE_TIMEOUT_MS` on every chunk and answers such a stall with 408 `request_body_timeout` (pause, write the envelope with `connection: close`, then drop the socket) — deliberately not a second 413, because the two verdicts ask the client for opposite fixes (shrink the payload versus resend it unchanged), and with no `Retry-After`, which RFC 9110 §10.2.3 scopes to 503/429. Amended 2026-11-25: the chat admission gate resolves the conversation and allocates the turn on every request. Request capture copies that identity onto archive lines and does not own the resolve; `enabled: false` writes nothing and does not skip it.

## Decision

### 1. One table, two transports, one seam

`SURFACES` (`surfaces/table.ts:8-23`) is the single registry: one entry per inbound face with `routePath / detectSuffix / exec / capture / encodeStream` (and `encodeChunk` where the client protocol is chunk-shaped end to end). The SAME table drives Fastify route registration (`server.ts:1044-1056`) and MITM path detection (`detectSurface` suffix match) — and the rate-limit route table derives from it too (`INFERENCE_ROUTE_PATHS = SURFACES.map`). `dispatchSurface` branches only on `exec`: `chat-pipeline` | `decision-pipeline`. Both transports build a `TransportContext` (`surfaces/types.ts:58-79`): `method/url/headers/clientIp` + the access gate (discriminated: `kind:'key'` on Fastify — validated bearer/x-api-key + per-key modelAccess, guard already wrote the 403; `kind:'exempt'` on MITM — the client connects THROUGH us, trust lives at the CONNECT/TLS layer + bypass list; no gateway key, so captured events carry no apiKey attribution and upstream calls use the registered provider's own credentials) + `captureProcessContext()` (answers `{}` when capture off) + terminal sends (`sendJson` / `beginSse`+`writeSseChunk`+`endSse`) + `isClientGone()` + `logError`. Terminal-send discipline: exactly one terminal send per request, and parse/gate failures emit ZERO capture events (all pre-dispatch on both legs). **Body admission is one policy for both legs, and it lives in one file** (`surfaces/body-admission.ts`; the limits themselves are `config/defaults.ts` constants). `GATEWAY_MAX_BODY_BYTES` (32 MiB) is the `bodyLimit` every surface route registers with AND the cap the MITM transport reads to — Fastify's own 1 MiB default is not a gateway policy and was rejecting ordinary agent contexts on the native leg while the MITM leg admitted 32x more. `Content-Encoding` is honored on both legs (`gzip`/`x-gzip`/`deflate`/`br`): the native leg decodes through a route-level `preParsing` stream so the ceiling applies to the **inflated** body (a compressed bomb is still a 413), the MITM leg decodes its buffer under the same cap; an encoding this gateway cannot decode — `zstd`, or a chain like `gzip, br` — answers **415** with the offending token named, because passing an encoded body to a JSON parser produces a 400 that blames the client's syntax. Rejections answer in the plane's own envelope: a surface route re-emits through `errorBody` (`error.{message,type,code}` — clients parse that shape, and the framework default `{statusCode, error: "Payload Too Large"}`, whose `error` is a reason-phrase string, rendered in the console as an opaque `413 "Payload Too Large"` with no size, no route, no remedy), the admin plane answers `{success:false,message}`. Every refusal logs one structured `body_rejected` warn (`leg`, `path`, `status`, `code`, `capBytes`, wire bytes seen, `contentEncoding`) — a rejection the operator cannot see is a support ticket. **Two tiers, deliberately unequal:** inference 32 MiB (`GATEWAY_MAX_BODY_BYTES`), control plane 8 MiB (`ADMIN_MAX_BODY_BYTES`, set as the Fastify *instance* default so an admin route that forgets to declare a limit inherits a gateway policy instead of 1 MiB — `POST /api/admin/config/raw` is exactly such a route, and its body is a whole `config.yaml`), operator uploads 64 MiB (per-route, `IMPORT_BODY_LIMIT_BYTES` / `PLUGIN_PACKAGE_MAX_BYTES`). **Media type is one policy too**: a body whose `Content-Type` is absent or names a non-JSON media type is refused 415 on BOTH legs before dispatch, naming what the request actually sent (`assertJsonMediaType` / `requestMediaType`) — a 415 that guesses a type would be worse than one that names nothing. A `Content-Length` mismatch is deliberately NOT mapped to an admission code: when the body ends before the declared length, Node and Bun abort the request before any handler runs, so there is no response to shape; the reachable direction (declared shorter than sent) surfaces as `invalid_json_body`.

**Streamed turns take the same discipline, and streaming is TWO independent axes** (`streaming.client.mode` / `streaming.upstream.mode`, both HOT-applied: each axis is read per request and both save handlers re-seed the pipeline gate, so a mode change lands on the next request — the only boot-fixed part is which wires HAVE a streaming executor). They answer different questions — "what shape does the caller get?" and "how is the provider called?" — and neither is derivable from the other: a JSON client can be served over an upstream SSE connection (accumulated), and an SSE client can be served from a buffered upstream call (gateway-rebuilt frames).

- **Client shape.** `allow` (default): the client's typed `stream === true` (C-3 normalization unchanged) selects SSE. `deny`: a `stream: true` ask is answered 400 **before** `orchestrator.process` — zero capture events, same class as a parse-400 or a gate-403. `always`: the gateway answers SSE even for a JSON ask; a surface without `encodeChunk` emits its buffered `encodeStream` frame sequence instead of degrading to JSON.
- **Provider transport.** `stream` (default): the upstream SSE reader runs wherever the wire has one, and a JSON client's response is ACCUMULATED through an accumulate-only relay whose `committed` is permanently false, so retries and failover stay legal (no byte exists to duplicate). Client-observable timing is unchanged — a JSON body still needs the whole generation — and the gateway pays one accumulation buffer (2026-11-18 amendment; see below). `follow`: upstream SSE only when the client is being streamed to, the surface has `encodeChunk` and NO `afterResult` hook (that hook must run before the first byte), the serving wire has a streaming executor (all four built-in Chat/Responses/Anthropic/Gemini HTTP wires, plus plugin wires such as the Qoder gRPC bridge that expose one), the serving attempt is not the schema-assertion cascade's LITE lead (its verdict needs the full content and may re-ask the whole turn on a higher tier — the escalation leg, whose response is final, streams like the direct path), and mock mode is off — the pre-2026-11 default, kept as the conservative rollback. `buffered`: never use upstream SSE — the pre-streaming rollback lever (formerly `streaming.enabled: false`, rewritten by the v2→v3 config migration).
- **Commit point unchanged.** When the client IS being streamed to, the relay forwards upstream frames DURING `orchestrator.process`, and the turn can only end two ways: frames → `: ocr-summary` → `data: [DONE]` → `endSse`, or frames → `endSse` **without `[DONE]`** when execution fails after the first byte (post-commit: no separate JSON response, no retry — ADR-0004 §2). If the Chat encoder rejects signed or encrypted reasoning, send one best-effort `data: {"error": ...}` SSE frame with code `unsupported_parameter` before closing, without a `finish_reason`. Other failures and wires retain their existing behavior. Anthropic and Responses have no `[DONE]`: the same `: ocr-summary` comment follows `message_stop` or `response.completed`. The comment is not an event, so a strict client still ends on the protocol terminator. If the relay is never fed, nothing was written and the buffered `encodeStream`/`encodeJson` path runs byte-identically to before, which is why the fallback is safe rather than a second code path.
- **Stream tags (both directions, so a slow turn is diagnosable).** The trace carries `request.clientStream` (shape actually written — true under `client.mode: always` even when the ask was JSON) and `execution.upstreamStream` (`sse` | `buffered`, the served attempt). The capture archive tags each exchange: `requestStream` (the client's ask on the client leg; the `stream` the gateway actually sent on the upstream leg, incl. vendor URL forms) and `responseStream` (client leg: was the body SSE). The wire carries the outbound tag as `X-OCR-Upstream-Stream`. `ttftMs`/`genMs`/`stalledMs` are measured whenever the provider leg streamed — in accumulate mode they describe the gateway's view, NOT the client's wait, which is the whole generation. The trace also carries the **protocol map** (2026-11-18): `request.inboundWire` (the surface the client addressed — chat / anthropic / responses) and `execution.wireKind` (the outbound wire the served attempt ran on); the two coincide only on a passthrough, and the console renders the pair without request capture enabled.

The X-OCR header set is therefore split by WHEN it is knowable, not by wire: routing facts (`Tier/Layer/Model/Session-*/Request-ID/Thinking-Requested/Variant`) flush with the first byte via `buildChatOcrRoutingHeaders`, while completion facts (`Failover*`, `InPlace-Retries`, `Breaker-State`, `Latency-MS`, `Upstream-Stream`, `TTFT-MS`/`Gen-MS` — the gateway-measured split whose pairing is the output-speed denominator (ADR-0005), absent when the provider leg was buffered — `Thinking-Actual/Degraded`) ride the trailing `: ocr-summary` comment frame (`buildChatOcrSummaryFrame`) — a 200 stream must not assert facts of a turn that has not finished, and HTTP trailers are unreadable to `fetch` clients. Every chat-shaped `streamEnd` writes that comment: chat before `[DONE]`, Anthropic after `message_stop`, Responses after `response.completed` / `response.incomplete` / `response.failed`. The comment is not an event, so the protocol terminator stays the last event a strict client reads; a reader that drains the body uses `X-OCR-Gen-MS` from it as the tok/s denominator. The buffered legs keep sending the whole set as headers; the SET is uniform, the transport differs. A client that disconnects mid-stream does NOT cancel the upstream call: the gateway drains to the usage frame and credentials the turn normally, because an abort that erases metering would let a caller dodge token rate limits by cancelling repeatedly — the turn is still recorded as its real outcome (synthesized 499 on the client leg, ADR-0008 §5).

### 2. Inbound wire aliases — exactly four; Gemini is an upstream wire

`/v1/chat/completions` (OpenAI-compatible), `/v1/messages` (Anthropic-compatible), `/v1/responses` (OpenAI Responses), `/v1/systemone` (decision gateway). The wire alias table is closed — anything else 404s. (Amended 2026-11-05, ADR-0017: the closed table governs DIRECT `/v1` faces; client-gateway plugins may claim whole SNI hosts BEHIND the MITM leg, where their routes are host-scoped and never become table rows.) Gemini `:generateContent` is OUTBOUND provider wire (`providers/google-gemini.ts`; outbound wire set `openai-chat|anthropic-messages|google-gemini|openai-responses|systemone|opencode-proxy`), never an inbound alias. The systemone `detectSuffix '/systemone'` is intentionally WIDER than its routePath so the MITM leg claims upstream native decision traffic (typesafe.ai / bailian) passing through the proxy.

### 3. MITM forward proxy — full capture is the point

Default posture: EVERY HTTPS CONNECT MITMs unless loopback or a rule says otherwise (`forwardProxy.rules`, ADR-0018): SNI peek → `startMitm` → decrypted stream spliced into an inner `http.Server` (h1) or a prior-knowledge h2c `http2` compat server (h2, chosen by the connection preface, never by ALPN alone); gateway claims first (ADR-0026 rev 2: exact claims, then installed wildcard claims, then the built-in universal row, whose `match()` is exactly this surface+POST test) ⇒ the accepting gateway dispatches; otherwise transparent forward — an h1 byte splice (`relay.ts` with backpressure; hop-by-hop header set — connection/keep-alive/TE/trailer/transfer-encoding/upgrade/proxy-* — stripped both directions) or, on the h2 leg, a faithful h2 re-origination upstream (ADR-0017 §3: trailers, bidi, `te: trailers` preserved; h1 fallback when the upstream refuses h2). Request body cap = the configured inference ceiling (`bodyLimitFor('gateway')`, `GATEWAY_MAX_BODY_BYTES` = 32 MiB by default) (413), applied to an `Expect: 100-continue` request from its headers before the body is read — the SAME constant the native routes pass as `bodyLimit`, so neither leg admits what the other would refuse — and malformed JSON (400), an undecodable `Content-Encoding` (415) or a non-JSON/absent `Content-Type` (415) all fail BEFORE capture/dispatch — zero events, answered in the surface envelope on either leg. `DEFAULT_MAX_BODY_BYTES` (16 MB) bounds what the ARCHIVE stores and never participates in admission: one number for both would let an operator's recording preference silently change what the gateway serves. Bare-name disambiguation rides `upstreamHost` = the intercepted request's host (`orchestrator.ts:106-124`; the native leg deliberately does NOT trust Host — anti-spoofing, ADR-0003 §1.5).

**Upgrade / WebSocket relay.** An `Upgrade:` handshake (WebSocket included) is caught on the DECRYPTED stream before the inner server and relayed byte-verbatim — request head (plus any bytes already pipelined behind it) → origin socket, then a raw bidirectional splice (`relayUpgrade`). It cannot ride the runtime's own `node:http` upgrade event: on Bun 1.3.14 the socket handed to that handler swallows every write while the parser keeps running and answers 505 to whatever the client sends next, so a `wss://` connection would die at the handshake. Nothing about the handshake is re-serialized (subprotocols, extensions, cookies — any upgrade protocol), because an upgrade is a single hop. It also cannot ride the ordinary forwarder: `connection` and `upgrade` are hop-by-hop, so `filterHeaders` strips exactly the two headers that ARE the handshake. Upstream TLS omits `servername` for an IP-literal origin (`egress.ts` `upstreamServernameOption`): RFC 6066 forbids an IP in SNI and Node/Bun throw on it, and a synchronous throw raised inside a socket `data` listener used to kill the connection silently — the IP decision therefore lives in one helper, and a refused/failed TLS setup answers the client with a 502 instead of escaping. A client-gateway plugin may OWN a handshake on a host it claims (`handleUpgrade`, ADR-0017): returning `true` transfers the decrypted socket wholesale — the gateway writes the `101` itself and drives the stream — while `false` (or no hook) falls through to the transparent relay. Three boundaries stay open BY CONSTRUCTION and are not bugs to "fix" later: non-TLS `ws://` through the plain proxy port (that leg never decrypts, and the same runtime gap blocks its upgrade event), HTTP/3/QUIC (never proxied at all), and upstream client-certificate (mTLS) targets (the terminator holds no client cert, so the origin's CertificateRequest cannot be answered).

**Bounded per-host terminators.** Every MITM'd host gets one listening `tls.Server` plus one minted leaf cert. Full capture sees every host a client visits, so both caches are LRU-bounded — 256 terminators (`server.ts` `MAX_HOST_TERMINATORS`) and 512 certs (`ca.ts` `MAX_CACHED_CERTS`) — and an evicted terminator is closed listener-only: established connections keep their sockets, and the next CONNECT re-mints from the same CA. Unbounded maps here leak file descriptors in proportion to hosts visited, i.e. the failure appears only after the proxy has been useful for a while.

**Decryption scope and the inbound cap.** Interception scope is the rule table's `ingress` column (ADR-0018): `intercept` decrypts, `passthrough` blind-tunnels, and the unmatched fallback is `intercept` — the posture this ADR describes. A passthrough row still proxies the bytes, they are simply never intercepted, which makes it a DECRYPTION SCOPE and not access control (that axis is proxy auth — an OCR API key as the Basic password, ADR-0017). One resolver answers both legs — the CONNECT/MITM admission and the plain-HTTP absolute-URI intercept step — so they cannot disagree, and the CONNECT ledger note carries the decision, so "why was this host not captured" is answerable from the ledger itself. `forwardProxy.maxConnections` (default 512, clamp 16..8192, hot-applies) caps concurrent PROXIED EXCHANGES — one tunneled or MITM'd socket costs two fds (the accepted socket plus its decrypted loopback peer) — enforced at ADMISSION (CONNECT or a plain-HTTP request) rather than at accept time: Bun's `node:http` exposes no accept-side hook (no `'connection'` event on `http.Server`, and both `server.maxConnections` and `server.timeout` are inert — verified on 1.3.14), so a socket that never sends a byte is bounded only by the listen backlog. A slot releases on `end`, `close` OR `error` because the same runtime emits no `close` on the socket it hands a CONNECT handler. `forwardProxy` auth is API-KEY ONLY — WHO may use the proxy: every CONNECT and plain request presents `Proxy-Authorization: Basic <base64 anyuser:keySecret>` (username ignored; the secret is compared in constant time against the live key list) or it is answered 407 with the `Proxy-Authenticate` challenge; loopback with no usable key keeps auth off (the historical posture) unless `forwardProxy.requireCredential` is on. The pre-API-key `forwardProxy.authToken` is RETIRED — dropped on load like every retired key (ADR-0018 §6) and never translated, so an install that authenticated its loopback proxy with a shared token comes back with proxy auth OFF until it creates a key and turns on `requireCredential`. A non-loopback bind without at least one enabled key is REFUSED at start (`forward-proxy/index.ts` `assertForwardProxyBindSafety`, which deliberately does not reuse `isLoopbackHost`: that helper counts `0.0.0.0` as loopback for MITM cycle-safety, the opposite of what a bind gate needs) — an unauthenticated full-capture proxy reachable from the LAN is the worst available default. Strict mode is opt-in for loopback for exactly one reason: a gateway plugin's bound key (`accountKeyId`, ADR-0017) is a server-side fallback for GUI clients that cannot present a proxy credential, and it must never lend that identity to an unauthenticated process on the same machine — with strict mode on, loopback enforces the same credential as the LAN, and a start with no enabled key is refused instead of degrading to open.

**Strict mode also retires OPEN tunnels.** Admission is per-connection, so enabling `forwardProxy.requireCredential` at runtime closes every tunnel that was admitted without a credential (a 1 s sweep over the tracked sockets) — otherwise the toggle would leave an unauthenticated full-capture tunnel alive until the client hung up. The gateway seam independently stops honouring the bound key for such a tunnel, so identity cannot be borrowed even before the socket dies.

**CONNECT carries identity (ADR-0017).** The ONLY proxy credential is an OCR API key as the Basic password (`Proxy-Authorization: Basic <any>:<keySecret>`, username ignored — key names are not unique), resolved against the live key list in constant time and re-checked at dispatch. A tunnel authenticated that way remembers only `{keyId, name}`; the decrypted requests inherit it, so gateway-routed completions are metered as that key while vendor-native relays remain untouched. Terminators are partitioned per key so two identities never share a decrypted connection; a non-loopback bind requires at least one enabled key, and deleting every key at runtime fails closed (407) rather than opening the listener.

Access log for the non-intercepted remainder (`forward-proxy/access-log.ts`, §4 of the observation ledgers): every NON-intercepted HTTP exchange (plus each CONNECT decision — bypassed / mitm / blind-tunnel) lands in a 300-event memory ring, viewable on the console's **Inbound Log** page (`/admin/proxy-log` — its own page beside the inbound settings, never a tab of it) via `GET /api/admin/proxy-log`. Unlike the other three ledgers the ring IS durably mirrored: events append to daily JSONL files under `<ocrHome>/forward-proxy/access-log/` (`forwardProxy.accessLog.persist`, default true) and replay oldest-first into the ring on startup (the ring's trim evicts earliest-appended rows, so chronological replay keeps the most recent history); day files older than `persistDays` (default 7, clamp 1..365) are swept at startup and daily. Binary bodies persist as raw files under `bodies/<day>/` and are fetched through the ONE neutral body endpoint `GET /api/admin/traffic-body/:token` shared with the plugin traffic feeds (ADR-0017 §5): the row carries an opaque token, the resolved ref is grammar-whitelisted and containment-checked, so no traversal and no storage layout on the wire. The forwarders tee both wire sides into an `AccessTap` while piping; bodies are capped per side at `forwardProxy.accessLog.bodyBytes` (default `DEFAULT_PROXY_ACCESS_LOG_BODY_BYTES` = 1 MiB; 0 = headers-only, never marked truncated) — a body that outgrows the cap SPILLS to a raw body file when persistence is on (the whole body: buffered prefix + the tail streamed straight to disk), so the default costs no captured bytes while the heap stays bounded; with persistence off the tail is dropped and the row is marked truncated. Inflate (`gzip`/`br`/`deflate`) carries its own output ceiling — a capped wire body is not a capped allocation. Headers pass the shared credential deny-list, and `forwardProxy.accessLog.enabled` hot-applies per request (default true). LLM-protocol traffic is never duplicated here — it keeps its richer http-exchange capture in the /traces archive.

OS system-proxy ownership (`forward-proxy/system-proxy.ts`, same Proxy Access page): `POST /api/admin/system-proxy/enable` snapshots the CURRENT OS proxy settings (whatever they point at — including a user's clash/v2ray) to `<ocrHome>/forward-proxy/system-proxy.json`, then points the OS proxy at `127.0.0.1:<forwardProxy.port>` with a loopback + literal-`egress: direct` rule-host override list (win32 registry / darwin networksetup per enabled service / GNOME gsettings; anything else reports `unsupported`). Re-enable is idempotent — an existing snapshot is never overwritten, so the user's original settings cannot be clobbered by a second call. `disable` restores the snapshot verbatim and deletes it; with NO snapshot it is a deliberate no-op (never blind-offs a proxy OCR did not set). The snapshot file doubles as crash detection: present while the OS no longer points at us, the status reads `stale` and the console offers one-click restore.

**The CA path has exactly one spelling — and the CA is machine-wide.** The MITM CA dir resolves through `forward-proxy/ca.ts` `resolveCaDir(forwardProxy.caDir)`; the default is the per-user shared data root + `forward-proxy` (the desktop shell's default `OCR_HOME`), NOT an individual book-set's `<ocrHome>`. A trust anchor is MACHINE state: a second install adopts the CA the operator already imported instead of minting a same-CN twin that clients can select by mistake (`CERT_SIGNATURE_FAILURE`). Book-set isolation still covers the access log and the system-proxy snapshot, which stay under `<ocrHome>/forward-proxy/`. On first resolve the shared dir ADOPTS a legacy per-home `<ocrHome>/forward-proxy` CA by copying it (never regenerating — the imported root must survive the move); `OCR_CA_DIR` pins the default for sandboxed test runs. The same single spelling is shared by the proxy itself, the console PEM download, the CA card (`GET /api/admin/proxy/ca/meta` echoes path / SHA-256 fingerprint / subject / validity, never key material) and the system-proxy trust hint. Two guards ride with it: an existing bundle whose CN differs from the requested one makes `ensureCa` THROW instead of silently returning a different identity, and every CA subject carries a key-derived `OU` so several same-CN roots never share one DN. The Windows CA-trust probe compares the EXACT certificate thumbprint (not the CN), so a stale same-CN root can never be reported as "trusted".

**Trust is reported, never assumed.** The console's Proxy Access card and setup wizard show `GET /api/admin/proxy/ca/trust`: a tri-state answer (`trusted` / `not trusted` / `unknown` — a probe that could not run is NEVER flattened into "not trusted") for the EXACT certificate the proxy signs with. `forward-proxy/ca-trust.ts` probes the platform stores the gateway can read — Windows machine + current-user Root store by thumbprint, macOS `security verify-cert` for the real SSL trust policy, Linux anchor files / merged bundles / NSS databases by certificate BODY — and deliberately does not cover application-private roots (Firefox profiles, Java keystores). The verdict is cached 60 s because the probe spawns platform tools; `?force=1` bypasses the TTL so a re-check immediately after an install cannot replay the pre-install answer. Detection never installs anything: importing the root stays an explicit operator action (elevation / OS consent).

### 4. Request identity

Identity is defined by **ADR-0021**: unqualified ids are the gateway's (`requestId` names one request and is the trace record key; `sessionId` names the conversation), foreign namespaces carry a prefix (`clientRequestId`, `upstreamRequestId`) — a client-minted SESSION alias has no field of its own, it is carried by the routing provenance (`request.clientRef`, ADR-0002), and `exchangeId` pairs one HTTP exchange. The shared boundary adapter (`observability/request-identity.ts`) parses inbound `traceparent` > `x-request-id` > `x-trace-id`/`x-correlation-id`/`request-id` into `clientRequestId` (W3C-validate, never mint, never echo); MITM reads the ORIGINAL client request headers. Outbound traceparent injection is NOT implemented (builder exists for tests only). Captured `clientHeaders` are the safe subset `{userAgent, acceptLanguage, clientRequestId}`; authorization/api-key/cookies are structurally never in the trace record. `X-OCR-Session-ID` names the gateway session; `X-OCR-Trace-ID` no longer exists.

### 5. requestCapture — HTTP-exchange events

Namespace: `requestCapture:` — the retired top-level `capture:` section (rename residue), `classifier.layer2.decisionCapture`, key-level `role`, and the retired `requestCapture.systemone` two-gate subtree are load-STRIPPED and never rewritten back on save; both console save paths hot-apply (`routes/console.ts`). One namespace, one meaning: **request/HTTP exchange logging** (training-data sampling is a different concern, ADR-0001 §5).

Model: `CaptureEvent` — one event per direction per leg; a request produces 2–4 events sharing one `requestId` (each request event pairs with its response via `exchangeId`): client-request / client-response / upstream-request / upstream-response. Every line is stamped `schema: 2` (`CAPTURE_SCHEMA`) and carries the WRITE-TIME turn identity of its request — `turnIndex` (null is a first-class value for prompt-less requests), `isPromptStart`, `turnDecision` — plus `attempt` (1-based within `(requestId, leg)`; the client leg is always 1). The boundary is decided structurally at the admission gate (`capture/turn-boundary.ts`, ADR-0024 §4) and every reader copies it; no reader derives a boundary from prompt text, message counts or resend heuristics. Every event additionally carries `conversationKey` (ADR-0002 §1: sha256(apiKey identity + first user message), content-addressed, absent when unresolvable) so the archive can regroup a conversation across volatile session ids. Header regime (current code): NAMES preserved, credential-shaped VALUES `[REDACTED]` via substring deny-list (authorization/api-key/cookie/token/secret/bearer/…-key/key/auth), query-string auth params redacted too; `requestCapture.redactSecrets` (default true) is ALWAYS ON — a false value is ignored at load/apply time (S-06), so credential-shaped header and query values never persist verbatim; `CaptureRecorder` re-asserts the policy from both constructor and hot-apply. Master `enabled:false` default — OFF is a BYTE-IDENTICAL zero-event posture (pinned by tests), on is conscious opt-in (the `/api/admin/*` auth-exempt reminder applies). Sink: `capture/<YYYY-MM-DD>/<sanitized-sessionId>.jsonl` — the live archive root for schema-2 lines; the version rides on the data (`schema: 2` per line), never on the root name. Schema evolution: the live root moves forward IN PLACE by a registered migrator chain (`capture/migrate/`: one `V{N}ToV{N+1}Migrate` class per hop, one file per class under `migrate/steps/`, registered in `migrate/registry.ts`; the engine resolves a hop by `(from, to)`, builds a fresh instance per file so a step's `begin()` planning state is never shared, calls `begin()` once PER HOP over the shape that hop is about to rewrite (a later hop never plans against the disk shape an earlier hop already replaced), and walks the chain with no gap and no skip — the same one-shot ladder `traces.db` follows with `DB_VERSION`). The boot and hot-apply-enable passes process EVERY file — an upgrading installation shows its history immediately — while the hourly sweep touches only files quiet for ten minutes; each rewrite is whole-file atomic (temp file + rename in the same directory) and re-checks the original right before the swap, so an append that lands mid-pass makes that file back off instead of dropping the new bytes, and a line whose hop is unregistered, skipping or unrepresentable leaves the whole file exactly as it was for the next pass while readers keep rejecting it — never a partially migrated archive. A line that is not parseable JSON is not a reason to abandon the file either: it is carried over byte-for-byte (and counted as `unreadable` in the pass summary) so one rotten row can never cost a reader the thousand good ones beside it. Schema 1 is the unmarked baseline (no `schema` field at all) and `V1ToV2Migrate` is a real step, not a tombstone, covering BOTH historical shapes: lines that already carry the gateway ids are taken as-is (`attempt` rebuilt as the ordinal of each distinct `exchangeId` within `(requestId, leg)`), and lines that predate them — `traceId` + `spanId` only — have the request boundary read off the event sequence, because `traceId` is CONNECTION scope (one trace can hold several sequential client requests) while `spanId` is the exchange identity: a `client request` opens a request, the `upstream` spans it causes belong to it, the matching `client response` closes it, and the requestId is minted deterministically from `(sessionId, spanId, ts)` so a re-run mints the same id (idempotent). A sequence that cannot be closed is repaired into the nearest truth-bearing shape rather than guessed at or set aside: an upstream exchange with no open client request becomes a prompt-less ORPHAN REQUEST of its own (`turnIndex: null`, `NO_TURN` — visible and honestly marked, never folded into a neighbouring turn), a second client request opening over an unfinished one simply becomes the next request (the abandoned one keeps its exchanges and turn, minus a response half), a response matching nothing is attached to the request its span opened earlier in the file or stands as an orphan, and a file that ends mid-request keeps its request. The step therefore never refuses a line the engine hands it: every parseable line comes out readable at the target schema. Turn identity in both shapes comes from the SAME structural rule the admission gate uses (`classifyTurnBoundary`), replayed over the bodies the archive already recorded, in file order with the previous request's message count threaded per session (the recorded `promptMessageCount` / `promptLastUserIdx` pair drives it when the body is no longer readable). The retired vocabulary is dropped: `spanId` becomes the `exchangeId`, `traceId` is superseded by the request identity, `promptMessageCount` / `promptLastUserIdx` → nothing. The engine stamps `migratedFrom: 1` on every line it rewrites, so a reconstructed turn identity is never mistaken for an admission-gate stamp. There is no seal, no quarantine and no parking lot: NOTHING is ever moved out of the live root — an upgrade that parked old captures in a directory the runtime never reads would cost the operator the very history the migration exists to preserve. The live root is the only copy, and every line it holds stays viewable after the pass. (`_backup-20261114-1229/` was a one-off operator copy taken at the cutover; it is not part of the mechanism and no code path produces one.) Retention 7 d / 2048 MB pool / body cap 16 MB (sized so one fully-loaded 2M-token context archives untruncated) / per-session seal 512 MB — an archive that reaches its seal stops appending and gets ONE terminal `archive-overflow` line; that line is metadata, so readers MUST NOT count it as a request. The seal exists because agent loops resend full history on every tool-loop request (O(n²) growth within one turn) and one runaway session must not starve the shared pool; the budget is soft (concurrent appends can overshoot by about one line). The console tail-read window scales with the body cap (8 MB floor / 48 MB ceiling); full history is always available via export, which is uncapped. Read plane (console): `readEvents` is ASYNC — fs.promises window read + yield-paced batched JSON.parse — so an archive read never stalls the gateway event loop; `bodies=none` (the metadata-first console default) strips wire bodies from the parsed events and stamps each response event with a read-time-derived `completionTokens` (last usage occurrence in the body) so per-request tok/s chips survive without the bodies; full bodies return per request via `GET /api/admin/capture/:date/:file/request?id=<requestId>` (an `evt_…` event id is accepted too, since either names it) or a `bodies=full` re-read. The request list pages BACKWARDS within that window: `page=1` is the newest slice, older pages count up from there, and each page is cut at a request start so no page renders a half request (`page`/`totalPages`/`hasOlder`/`hasNewer` come back on the response; out-of-range pages clamp, so the pager self-heals). Because the read window is bounded, the header's exact denominator and the whole-archive turn index come from `GET /api/admin/capture/:date/:file/summary`: it streams client-request metadata only (targeted byte-line scans, never `JSON.parse` on multi-MB bodies), counts requests, and reads the WRITE-TIME `turnIndex` off each line to build the turn index (`CaptureTurnIndexEntry`, keyed by `turnIndex`, cached by file stat; stitched shards sum). The pager counts REQUESTS back from the newest end and its read window GROWS on demand up to a hard ceiling — past that the response clamps the page (the pager self-heals) and deeper history stays export-only, so one click can never allocate a seal-sized buffer. The pager is a FIXED footer of the detail pane (only the request list scrolls), 50 requests per page by default; the conversation lens is exempt — it walks every page itself to reconstruct every turn. Turn navigation rides the same write-time metadata: `isPromptStart` marks the request that opened a turn, and its display-only `promptSummary` stamp (written at capture time, never derived) labels the selector entry, so the console can group the loaded page into turns and narrow the view to one turn without any wire-body parse. Cross-midnight conversations are stitched read-side: `stitched=1` on the events window and the request endpoint merges the per-date shards of one conversation (`readEventsStitched`/`readRequestStitched`; shard discovery via `listSessionsWithSpans` is bounded to cached ≤64 KB head reads and session rows carry `spanDates`); the frontend renders the span as a badge plus per-day dividers. Session rows also carry `protocol` — the inbound surface derived from the FIRST client-request event's request line (`/v1/chat/completions` → chat, `/v1/messages` → anthropic, `/v1/responses` → responses, `/v1/systemone` → systemone; archives without request lines stay undefined = unbadged) — and the preview/prompt extractors treat a System One body's `state` (string or structured JSON, capped) as the user text, so decision-surface sessions get a content title instead of the raw session id. boot + hourly sweeps, ALL I/O fail-open. Client-response body stash capped 1 MB; client disconnects finalize through the transports (synthesized 499) — hang/cancel still leaves a record. A STREAMED upstream leg records the raw `text/event-stream` body of that exchange (in-memory accumulation capped at 256 KB before the recorder's own per-field truncation, `[DONE]` included), so `upstream/response` answers "which frames actually crossed the wire" and a truncated stream is visible AS truncated; the outbound client leg keeps stashing SSE frames per chunk under the 1 MB cap. Streaming emits no extra event kinds — the same request/response pair, with a different body shape. A STREAMED response event additionally carries `firstByteTs` (epoch ms of the first body chunk, stamped at the wire: upstream SSE reader loop / client SSE write; buffered single-shot replies stay stamp-less), and `groupEventsIntoRequests` derives per-leg `ttftMs`/`genMs` from it — the capture plane reports the SAME TTFT/decode-TPS vocabulary as the trace plane (ADR-0005 §8), never a rate synthesized from full latency. The `/v1/systemone` surface itself never captures FinOps or trace rows — capture is exchange events only.

Wire fidelity is independent of IR conversion. The client request event stores the parsed client-protocol envelope (`messages`, `input`, native cache fields and unknown client fields), with only the established directive scrub, credential/header redaction and body caps applied; it never stores the canonical IR snapshot as a substitute. The upstream request event likewise records the actual payload sent by the southbound adapter, and each response event records the bytes/frames returned on that leg. Session identity and routing still use the scrubbed IR snapshot, which is a separate object from the capture body. The chat admission gate scrubs the chain once, then resolves the conversation and allocates the turn on every request it will serve. An empty prompt, an unknown variant, an unusable combo, and a model-policy denial are rejected before that resolve, so they allocate no turn. `enabled: false` writes no events and does not skip the resolve of a request that is served. An archive line's `sessionId` is a copy of that result, held in a private field of the capture context. A value that is not that context writes nothing. An executor that needs the live conversation receives it as its own argument. The `/v1/systemone` archive file is named by the caller's explicit session header, or by the request id when the caller sent none. That surface does not resolve or register a conversation.

Vocabulary (ADR-0024, authoritative): `session ⊃ turn ⊃ request ⊃ exchange ⊃ event`. The request projection the console renders is `CaptureRequestSummary` with an `exchanges[]` list bucketed by `(leg, attempt)` — every failover hop and the Layer-2 decision pair stay visible, one drawer tab per exchange phase; the pre-contract six fixed slots and the `round*` read-plane symbols (`roundNumber`, `totalRounds`, `CaptureRoundIndexEntry`) are deleted. `requestNumber` is the 1-based request ordinal inside the read window (the pager's unit); turn membership is the immutable write-time `turnIndex`, never folded into it and never renumbered. `promptSummary` is stamped at write time on the prompt-start client-request event only (display-only; a continuation never gets one) — the retired read-plane staleness dedupe (`promptMessageCount`/`promptLastUserIdx`) is gone. The recorder stays cross-request stateless (capture is fail-open and restart-transparent); the turn high-water lives in the session-manager snapshot (`v: 3`), not in the recorder.

### 6. System One surface — single-master capture

The retired two-gate tree (`requestCapture.systemone.{enabled, l2DecisionEnabled}` — a surface gate default ON plus a decision-call sub-switch default ON) is load-STRIPPED and never rewritten back on save: both gates defaulted TRUE, so they only ever NARROWED an already-explicit privacy opt-in, at the cost of making the capture card read like System One surface configuration (operator-facing confusion, retired 2026-12). The single `requestCapture.enabled` master (default OFF) now gates every leg — the `/v1/systemone` client pair, the surface's own upstream pair (the native passthrough or the synthesized conversion call, per the resolved wire; no purpose tag), and the Layer-2 decision layer's internal call leg (attached to the OUTER routed request as upstream direction, `purpose:'l2-decision'`, the sole `ExchangePurpose` value; the orchestrator only hands the decision layer a capture ctx while the master is on). Emission is strictly AFTER all 400/403/404/503 gates. Privacy posture when off: `captureProcessContext()` returns `{}`, the surface path is byte-identical to a build without capture.

### 7. The decision gateway (/v1/systemone) — wire-driven, honesty by wording

Model semantics on this surface: named model = that model; tier aliases resolve by PURE POOL PROJECTION to the leading model of the access-filtered pool — 404 unknown/no-pool, 403 denied, 503 unresolvable, NEVER a silent fallback; bare/`auto`/omitted → `systemone.defaultModel`; decision-line rate accounting counts but never locally rejects (the decision layer is a below-request leg). Exactly three response headers (frozen contract): `X-OCR-Model / X-OCR-Systemone-Upstream / X-OCR-Latency-MS`. The SAME executor backs the Layer-2 router decision layer — one implementation, two callers. The console's smart-assign decider (`POST /api/admin/client/:client/smart-assign`, plus the free `GET /api/admin/decider/resolve` probe that shows what a pick resolves to) is a THIRD caller and reuses the SAME alias cascade — physical id, combo leader, tier-alias decision-surface pool leader, bare `auto` → `systemone.defaultModel` — so a name means one thing console-wide; console calls carry no API key, so the access filter is a no-op there, and an unresolvable pick is refused (400) rather than silently substituted.

Two execution limbs, selected by the resolved model's wire (never by config tables):

- **Native passthrough (wire `systemone`)** — the 2026-10-22 amendment. A provider def whose stored protocol id is `systemone` (legacy npm `@ai-sdk/typesafe-ai` or opencode v2 segment `typesafe` are read-only aliases normalized by `providers/protocol.ts` / `opencode/provider-package.ts`) resolves through the shared `wireFor()` to wire `systemone`; the model enters the boot pool with `wire: 'systemone'` and the decision executor calls the vendor's decision endpoint DIRECTLY: `POST {baseUrl}/systemone`, Bearer auth from the provider's credential chain, body = the client's `{model, state, questions, …}` shape with the model id rewritten to `upstreamModel`, response answers passed through verbatim (unknown answer types such as `box` are NOT second-guessed). The chat pool NEVER sees these models (`getCandidateModelsForTier` excludes `wire === 'systemone'` unless the decision-surface opt-in is passed) — a decision protocol cannot answer chat, and routing chat at one would only blame the upstream for the gateway's own mismatch. The vendor wire contract remains: `languageModel` throws `NoSuchModelError`; only the decision model exists, on `POST {baseURL}/systemone` with `{model, state, questions}` and Bearer auth from the credential chain.
- **Protocol conversion (every chat wire)** — one JSON-constrained chat completion carrying all questions; the response's probabilities are then "self-reported estimates, NOT calibrated" (wording lives in the protocol types + reasonCode split, ADR-0001 §4).

`X-OCR-Systemone-Upstream` carries the limb actually taken (`native` / `converted`) — the honesty marker that keeps the two paths distinguishable on the wire. The retired 2026-10-21 `systemoneUpstreams[]` config limb stays retired: the native limb returns as DATA (the defs-file protocol id, ADR-0010), not as a config section.

### 8. Responses continuation state (`responses.persist`, `store`)

The `/v1/responses` chain store is authoritative in-memory (L1 Map); `responses.persist: false` default = byte-for-byte in-memory posture; ON mirrors an append-only JSONL (`<env dataDir>/responses-chain.jsonl`, 0600) replayed at boot (TTL filter 24 h → createdAt order → cap sweep → atomic compaction; boundaries 20 k nodes / 256 KB node / 64 MB file / compact per 1000 appends). Persist turns RESTART AMNESIA into "lost the last unflushed turn" — a chain-using client whose store rolled gets the documented fail-visible 400 (full-resend degradation, prompt preserved); disk failure only ever warns, never fails a request; persist-OFF chain users get a one-per-process warn explaining the exposure.

The wire's `store` flag is HONORED (absent = true, OpenAI parity): `store:false` means the response is not retained — no node is appended in either persistence mode — so naming it as a `previous_response_id` later resolves to nothing and the client gets the same documented resend-full-input 400. The response object echoes the EFFECTIVE flag, so a client that asked not to be stored is never told a chain exists. Request capture is a separate, operator-controlled plane: `store:false` is a protocol-retention instruction, not a capture switch.

Deployment constraint (the standard client-owned-history posture, not a limitation to work around): the chain is PER PROCESS and PER ENVIRONMENT. A second gateway instance, another environment, or a restarted process without `responses.persist` answers an existing id with the same 400, because nothing there holds the history. Chained clients therefore need sticky routing, or `responses.persist: true` over a shared data directory; clients whose first-class path is client-owned history (send the full `input` each turn, `previous_response_id` null, `store:false`) are unaffected by any of this and are the posture the wire is designed around.

Unimplemented-but-load-bearing wire parameters FAIL, never silently degrade (§9's fail-visible-over-silent-loss rule applied to the request surface): `conversation` (Conversations API), `background: true` (no async/polling endpoint) and `truncation: "auto"` (no server-side context trimming) each answer 400 with `error.code = "unsupported_parameter"` naming the parameter. A client cannot detect an ignored parameter — `conversation` in particular would look like a continued session while every turn started blank — so the error is the only honest answer. `text.format` is supported: `json_object` / `json_schema` become canonical structured-output policy and are rendered on targets that support them (an unknown format type still answers 400). `metadata`, `service_tier`, `prompt_cache_key`, `safety_identifier`, `parallel_tool_calls` and `include` are retained in IR. A native Responses upstream receives `include`; a target without a faithful equivalent rejects it instead of accepting-and-ignoring it. Non-fatal: `usage` echoes the cached-input, reasoning and audio token details the upstream actually reported, and omits unknown details rather than inventing zeros.

### 9. Cross-wire invariants on Canonical IR

Every northbound surface parses directly into the vendor-neutral Canonical IR, and every southbound adapter renders that IR into its own protocol (ADR-0033). Chat Completions is one carrier, not the semantic intermediate. The following invariants apply regardless of the inbound/outbound pair:

- **Tool-call pairing.** IR keeps `tool_call` and `tool_result` as typed items, with separate item ids and correlation `callId`s. Every call must have exactly one result before the next non-tool item; duplicate, orphaned and cancelled-call histories are not forwarded unchanged to a strict upstream. `repairToolCallPairing` (`pipeline/tool-pairing.ts`) performs one idempotent repair in the orchestrator after the pre-compression identity snapshot and before compression/rendering. It synthesizes a cancelled result where needed, removes duplicate/orphan results, and returns the original array when no repair is required. Each target adapter then renders the valid IR into its native message/item shape. The rendered correlation id may DIFFER from the canonical one: a carrier with a documented field budget renders it through a deterministic projection, while IR, the session store and the recorded canonical response keep the original (ADR-0033). Pairing is decided on the canonical id, never on the rendered bytes.
- **Reasoning fidelity.** Reasoning is a typed IR item. Response text, summary entries, signatures and encrypted/redacted payloads are distinct; reasoning text is never relabelled as a summary. Chat `reasoning_content`, Anthropic thinking blocks and Responses reasoning items map directly to and from that item. A target that cannot faithfully replay a signature or encrypted payload fails explicitly instead of dropping it.
- **Tools, media and generation controls.** Function/custom/builtin tools, `strict`, `tool_choice`, `parallel_tool_calls`, structured output and sampling controls retain their semantics in IR. Adapters use explicit payload whitelists and a capability gate. Unsupported tool kinds, media sources, annotations, item references or controls produce `400 unsupported_parameter`; they are never blanked, stringified into prompt text or emitted as a different tool shape. Malformed tool argument JSON likewise fails where the target requires an object.
- **Response and stream fidelity.** Responses envelope fields echo the effective request, terminal status preserves `completed` / `incomplete` / `failed`, and incomplete reasons survive conversion. The vendor-neutral stream lifecycle covers item/content start, deltas and completion for text, refusal, reasoning and summaries. Item ids assigned during streaming are reused by completion events and the terminal response. Opaque same-carrier items may round-trip; foreign opaque output fails rather than disappearing from a response.
- **Chat wire version tolerance.** The inbound Chat boundary accepts legacy `functions` / `function_call` / assistant `message.function_call` / `role:"function"` and normalizes them before IR conversion; orphan legacy results remain visible as user content. Outbound responses use the current tool-call shape. `max_tokens` and `max_completion_tokens` are both accepted. The IR preserves the `developer` role; the Chat target adapter folds all instruction/system/developer blocks into ONE `system` message so failover cannot duplicate the prompt, which makes its configured `supportsDeveloperRole` compatibility opt-out inert (all three states emit byte-identical payloads).
- **Prompt and cache integrity.** Prompt normalization only establishes a stable system/developer prefix: it does not trim text, merge messages, rewrite roles or discard structured parts. When a target has one instruction channel, that target's adapter joins text blocks deterministically with `\n\n`; a non-text instruction part it cannot represent is an explicit error. Cache accounting maps cached input from Chat `prompt_tokens_details`, Anthropic `cache_read_input_tokens`, Responses `input_tokens_details` and Gemini `cachedContentTokenCount`, alongside reasoning/audio details where reported. Client cache keys, retention/options and message/part/tool breakpoints have canonical representations. Generic OpenAI-compatible Chat still strips foreign carrier-only cache fields (`stripCarrierExtensions`) because strict servers reject unknown fields; a semantic control with no faithful target mapping fails rather than being silently discarded.
- **One accounting plane, honest streaming.** Buffered and native-relayed responses expose equivalent usage and terminal semantics. All four built-in providers decode native upstream SSE into IR events; an upstream JSON response remains a supported fallback and is expanded through the same canonical lifecycle. Client and upstream streaming are independent, so synthesized client SSE from a buffered upstream is never labelled native provider streaming. Relayed upstream usage remains intact, while synthesized SSE emits the same cached/reasoning/audio usage fields as JSON.

Conversion and streaming work is linear in input/output size and bounded by the existing body, accumulation and archive caps. `backend/tests/ir/ir-conformance.test.ts` pins cross-carrier fidelity, explicit failures, lifecycle/id stability and bounded-work cases; `backend/tests/ir/cache-integrity.test.ts` pins the financial fields.

## Consequences

- Adding an inbound face = one table row; both transports inherit dispatch, header, capture and rate-limit behavior — per-leg drift is structurally impossible (the header module's comment records the old drift as the reason it exists).
- Capture answers "what crossed the wire", traces answer "what decided and executed", datasets answer "what should the models learn" — three planes, three namespaces, no key implies another.
- Privacy postures are default-off/byte-identical and test-pinned, opt-in is two-level and honest about exposure.

## Amendment — `streaming.upstream` defaults to `stream` (2026-11-18)

The provider-leg default flips from `follow` to `stream`. Rationale: `follow` left every JSON-client
turn (IDE agents posting chat/completions one-shot) on the buffered leg, so `firstChunkAt` never
existed and the console's TTFT P50/P95, decode-TPS and stall-ratio columns rendered "—" for exactly
the traffic that most needed them. `stream` opens the upstream SSE reader wherever the wire has one
and accumulates for JSON callers — client-observable timing is unchanged (a JSON body still needs
the whole generation), the gateway pays one accumulation buffer, and the `UPSTREAM_SINK_RELAY`'s
`committed: false` keeps in-place retries and failover legal. `follow` remains as the conservative
rollback; `buffered` keeps its meaning. Capability still bounds every mode: wires without a
streaming executor and the schema-cascade lite lead stay buffered regardless.

The same amendment adds the protocol map to the trace plane: `request.inboundWire` (the surface the
client addressed: chat / anthropic / responses) and `execution.wireKind` (the served attempt's
outbound wire). Capture no longer needs to be enabled for the console to show which protocol pair a
turn ran on.
