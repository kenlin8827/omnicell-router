# ADR-0003: Model Addressing and Tier Membership — One Resolution Ladder, One Membership Authority

## Status

Implemented — 2026-10-15 (facts-side corpus rewrite). Scope: what the request `model:` field may name and how that name resolves; who decides pool membership; combos; variants; per-key model policy; the effort vocabulary. Conversation consequences of membership edits = ADR-0002; pool execution semantics = ADR-0004/0005.

## Decision

### 1. The addressing ladder (one name, one winner)

Resolution order, exact (chat path `orchestrator.ts:348-467`; decision surface mirrors it `surfaces/decision-pipeline.ts:54-137`):

1. Trim once; `request.model` verbatim on the wire (surface contract — forwarded bytes are never rewritten).
2. `auto-lite|plus|pro|ultra` virtual ids → `force_tier` (Layer 0, ADR-0001). These ids are RESERVED — registrable by neither models nor combos (`RESERVED_COMBO_IDS`, `registry.ts:695`).
3. Exact registered id → transparent pass-through: pin that model and force its tier (`:364-373`).
4. Variant sibling `base-variant` / `base#variant` → route to BASE, pin the variant's `reasoningEffort` over any client-sent effort (`ModelVariant = {id, reasoningEffort}`; `:375-387`). A real registered id always beats a sibling; a combo beats a variant ref; `#` with no matching variant → **404 loud, never silently auto-routed** (`:388-398`).
5. Bare upstream name (no provider prefix — how clients name a model the way its catalog does): ALL hits returned, ordered cheapest-input then id (`getModelsByUpstreamName`); the MITM leg additionally narrows by intercepted host (`upstreamHost` from the client request's host — native leg deliberately excluded, anti-spoofing; `:106-124,415-418`). A bare hit NEVER claims a name that is a live combo id (`:425`) — the combo is the gateway's own advertised meaning for that name; the same-named physical models stay reachable by full provider-prefixed id.
6. Combo id (checked after the exact-id and variant branches, before the classifier — and it outranks a bare-name hit): the member list IS the candidate pool, classifier/session-ratchet/schema-escalation all bypassed; a combo with zero registered members **fails fast** — never silently demoted to `auto` (invisible billing drift) (`:439-467`). Pre-execution placeholder resolution in the pipeline (effort machinery) must not consult the tier pool for combo or explicitly-named requests — a pool-less operator world (no tier rule claims any model) keeps both paths callable (`:584-591, 705-722` — the session resolver and the placeholder).
7. Anything else unregistered → the classifier decides. This IS intelligent routing (e.g. a native `claude-opus-*` name after an in-client model switch).

Vocabulary fact: the resolved physical record is `ModelRegistration` (id + provider + wire + derived home tier + pricing…, `config/types.ts:15-95`); `ComboModelRef {id, weight?}` is the unresolved config handle (`:110`); the `modelRef` WORDING names the gateway-visible id namespace = auto alias ∪ combo id ∪ registered id ∪ variant sibling id (`:131-148`) — the four kinds the console catalog tags each row with (`kind: 'auto'|'combo'|'model'|'variant'`, `/api/admin/gateway-models`; each row also carries `tiers`, the model's FULL membership set — no single fixed tier is reported). The historical glossary's `ModelRef`/`ModelIdentity` TYPE NAMES were never adopted in code — do not resurrect them; `AGENTS.md` now points here.

### 2. Tier membership — the committed member list is the ONLY source, projected PER TIER

`tiers.<tier>.members` decides pools (`config/types.ts:149-153`). Determinism beats zero-maintenance: a curated pool with no hidden heuristics; new models NOT auto-joining is a feature. The classifier survives as the **suggestion engine only** (boot pre-label, console preview/check; `match:` config @deprecated-suggestion, `:183-198`).

- `TierMemberRule = {pattern, weight?≥1, effortMap?}`; pattern semantics: `*`/`?` case-insensitive glob, **no wildcard = substring**, full id = exact pin (`utils/glob.ts:7-16`).
- **Membership is a per-tier projection** (`claimInTier`, `member-match.ts`): every rule in tier T's list independently claims what it matches, so a model — or a combo's expanded members — MAY join several tiers at once (overlapping rules are legal by contract and NOT warned at save time). Each tier's chain order (= that tier's rule index), weight and inline `effortMap` come from THAT tier's own claiming rule, so the same model can rank — and translate effort — differently per pool. `matchingTiers` returns the full membership set (the catalog's `tiers` array, tier-expanded model-access checks).
- The registry keeps ONE committed member view (`committedMembers`, set by `reclassifyTiers` — the only commit; initialized from the boot config): every runtime pool read (`getCandidateModelsForTier`, weights, `effortMapFor`, `tiersOf`, live previews without an override) projects THAT snapshot over the model universe (`buildTierPoolEntries`). Previews with a draft override re-derive from the draft instead.
- **Home tier (derived view)**: `m.tier` = first claim in tier order lite→plus→pro→ultra (`claimModel`), with that claim's priority/list-leader flag and effortMap stored on the registration. It exists ONLY for consumers that need a single tier value — pinned-model force_tier, tier-keyed reporting (`tierUsed` falls back to it, otherwise the serving pool's tier is reported), model-access tier expansion and the bare-auto widened-pool proximity sort. POOL MEMBERSHIP NEVER READS IT.
- Chain order = per-tier rule data: priority = that tier's claim index, the list leader leads the tier (`buildTierPoolEntries`: weight desc, then index; `pickPrimary` for weighted/RR) — representatives (`tierDefaults`, the empty-pool fallback chain) are the per-tier pool heads, recomputed on every commit.
- **No runtime auto-seed, no shipped member defaults** (the historical seed path is gone): `DEFAULT_CONFIG.tiers` is four EMPTY tier shells — a brand-new config.yaml starts pool-less and `auto` cannot route until the operator adds members on the /tiers page; an explicit `tiers: {}` is respected as "no pools"; any config with no `members` key anywhere keeps pools empty with a boot warning (`member-match.ts:28-35`; the YAML field comment "no runtime auto-seeding" lives, in Chinese, only in `config/index.ts`).
- `unclassified` is a fourth-state MARKER, not a tier widening (`types/router.ts:9-21`): claimed by NO tier's list, joins no pool, cannot become a tier representative, surfaced in a console "unpooled" view with one-click join.
- Two-axis liveness: the BOOT snapshot owns the model universe (providers/credentials/wire); membership+priority+effortMap are FILE-DERIVED live projections — commit-on-save `applyTierConfigNow` (+ `applyCombos`) on both console save paths, with a 2 s lazy replay as the hand-edited-YAML safety net (`registry.ts:375-425`, `routes/console.ts:1076-1077,1100-1101`).
- Hand-configured models (no captured `tierMatch`) are never reclassified — their explicit tier is permanent and is exactly how they join pools (member rules move them not; a matching rule in that tier may still supply weight). `tiersOf` exposes exactly their explicit tier.
- Global denylist `tiers.exclude` is the ONLY pool veto left — unconditional, "it outranks even an explicit pin" (`registry.ts:271-281`); per-tier `match.exclude/excludeTiers` are classification-gate vetoes on the suggestion path only.
- Combo indirection: a member rule `pattern: 'combo:<id>'` is a DECLARED reference, not a glob — every commit/read point (boot claim, `applyTierConfigNow`, the 2 s lazy replay, `resolveTierPool` previews, the save check) expands it in place via `expandComboRefs` into the combo's registered members: config order preserved (the ref's list position decides chain order), per-member weight carried, the ref's `effortMap` applied block-wide, duplicates and unregistered ids dropped, exact-id claims from earlier rules deduped, and every expanded member is an EXACT pin (`exact: true` — a member's full id must never substring-claim longer sibling ids like `p/v4-pro`). Pools stay physical-model lists — the request path never resolves a ref. A combo may be referenced by ANY number of tiers — each tier's pool expands independently. This is the one sanctioned auto-follow channel: later combo edits flow into every referencing tier at the next commit because the operator opted in per ref; a dead ref (unknown / reserved / disabled / shadowed / zero registered members) expands to nothing and surfaces as a `deadCombo` save-check warning (boot warns too). The ref's own `weight` field is inert — weights live on the combo's member entries.

### 3. Combos

`ComboConfig = {id, disabled?, selection?, models:(string|ComboModelRef)[], note?}` — `selection` decides the LEADER only; failover always walks config order; no cross-tier escalation (the composition is the contract); attempt-cap = chain length (ADR-0005). Tier member lists may reference combos via `combo:<id>` rules (§2) — the composition stays self-owned; the ref only mirrors membership at commit points. `disabled: true` is the operator takedown: the combo stays registered so the request path can tell "disabled" apart from "unknown name", but it is hidden from every catalog (`/v1/models` list and detail 404, console model picker) and naming it in a request fails fast with 404 — the same no-silent-demotion contract as the empty-member case, never classifier-routed (`orchestrator.ts:442-453`). `resolveCombo` re-resolves per call: config order preserved, unregistered ids dropped, duplicates collapsed to first — late registrations join naturally (`registry.ts:737-752`). Id namespace collisions are one-way and loud: a combo over an existing model id is ignored with a warn; a model registered over a combo shadows it (warn + hidden from `/v1/models`) (`:698-724`, `:161-163`). The `combos` list order is the console display order — reorderable from the UI, saved back verbatim.

### 4. Per-key model access

`apiKeys[].modelAccess = {mode: 'allow'|'deny', models: string[]}` — entries are exact ids, `*`-wildcards, or TIER-VIRTUAL entries `auto-*` (whole-tier rules); absent = unrestricted (`auth/model-access.ts`). Enforced at four layers so no path skips it: surface entry guard (reduces indirections before the pipeline: variant→base, combo→EVERY member, auto*→tier, `checkRequestedModel` :103-141), orchestrator defense-in-depth for explicit models (:452-467, 403), the execution choke point filtering every candidate (`executeCandidatePool`, ADR-0005) incl. escalation targets, and `/v1/models` + detail listing (variant judged via its base; combo listed only if every member is allowed). Bare `auto` under a policy WIDENS to the cross-tier allowed pool (chosen tier first, then proximity) instead of 403 — "auto" promises SOME allowed model, not a specific tier.

### 5. Effort vocabulary

`EFFORT_LADDER = none|low|medium|high|xhigh|max` — `indexOf` IS the rank (`types/router.ts:31-52`). `'none'` is a REAL ladder value a client may send, distinct from an omitted field; the "5-level + none-toggle" framing is stale (one vendor exception: the System One enum has no `none` — legacy `true` maps to the five non-none levels there). Honesty rules (`pickModelForEffort`, `registry.ts:484-544`): never upgrade above the ask (translate → capability-clamp → downgrade-or-nothing); an over-spec pool (everything supports MORE than asked) is not a match — route elsewhere rather than silently drop to none; cross-tier fallback allowed, descending order, actual model reported; `degraded` = served-rank < asked-rank (surfaced via `X-OCR-Thinking-*`, ADR-0004). Member rules' inline `effortMap` (`map?.[ask] ?? ask`) runs BEFORE the capability clamp at all four sites (selection, pinned-model path, per-candidate copy, post-failover recompute) — and the translation applied is the SERVING pool's claiming rule (a multi-tier member translates per pool); `none→real` mappings engage even omitted-effort requests. `defaultEffort` pins only when the client omitted the field — explicit values, `none` included, always win.

## Consequences

- Membership, order and thinking translation are 100% reviewable in one config surface; churn is visible (unpooled/orphan views, save-time orphan + `deadCombo` warnings), not silently absorbed. Cross-tier overlap is legal and silent BY DESIGN — each tier's card on /tiers shows the projection its own rules produce. Combo refs are reviewable at two levels — the ref in config.yaml, the expansion in every pool preview / save check; nothing expands inside the request path.
- Naming honesty: no type claims an `Identity`/`Ref` contract the code never shipped; the ladder in this record IS the resolution contract.
- Tests: `tier-membership`, `tier-combo-members`, `tier-pools*`, `combos`, `variants`, `model-access`, `tier-match` (suggestion path).
