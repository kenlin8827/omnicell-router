# ADR-0017: Client-Gateway Plugins — Inbound Native-Protocol Wire Ownership Behind the MITM Leg

## Status

Implemented — 2026-11-05.

## Context

Two extension axes were already named but only one existed:

- The plugin manifest's `type` field is the declared extension axis (`plugins/types.ts`), with exactly one type, `'model-service'` — outbound vendor-protocol knowledge (native transports, credential chains, vendored vendor binaries) shipped as user-installed packages.
- ADR-0008's inbound surface table is CLOSED: four wire aliases, everything else 404s. Vendor clients whose protocol is neither OpenAI nor Anthropic shaped (Cursor: ConnectRPC + protobuf over HTTP/2 to `api2.cursor.sh`, no configurable endpoint) had no lawful inbound path.

Cursor cannot be pointed at a custom endpoint by config — its AI traffic is hardcoded to its own API hosts. The only integration topology is TLS interception: point the client at the inbound forward proxy (ADR-0008 §3) and answer/relay the decrypted traffic. That is vendor-protocol knowledge in exactly the sense `plugins/types.ts` already reserves for plugins: the vendored .proto sets a later phase would need (phase 2 pins them to the validated Cursor build, §4), a frame codec, version-drift extraction tooling. It must not live in core.

## Decision

### 1. Second plugin type: `'client-gateway'`

A client-gateway plugin CLAIMS whole SNI hosts on the inbound forward proxy and owns the decrypted traffic of those hosts. The module exports `createPlugin(host: ClientGatewayHost): ClientGatewayPlugin`:

- `hosts: readonly string[]` — the claimed SNI hosts (e.g. `api2.cursor.sh`).
- `match(info)` / `handle(req, res)` — per-request admission and full lifecycle. The gateway sees node-http req/res on the h1 leg and the http2 compatibility API (same shape) on the h2 leg.
- `ClientGatewayHost` SDK (self-contained, same rule as the model-service host SDK — packaged plugins never import backend paths): `chat(body, sink, signal)` runs ONE canonical OpenAI-shaped completion through the SAME `dispatchSurface` pipeline as `/v1/chat/completions` (model resolution, tiers, breakers, captures all apply), `catalog()` exposes the routing surface for AvailableModels-style fabrication, `ocrHome()` for artifact state.

The plugin registry (`plugins/gateways.ts`) is module-level, rebuilt atomically on every plugin-host load cycle (stage → commit mirrors the model-service registry swap), and disable/uninstall hot-unplug immediately. **Host scoping is enforced by the registry, never trusted to the plugin**: `findGateway` gates on `:authority` (h2 compat) / `host` (h1), port stripped, case-insensitive, before the plugin's `match()` is consulted.

### 2. Gateway routes never join the ADR-0008 surface table

The SURFACES table stays closed for DIRECT `/v1` faces. Gateway routes are HOST-SCOPED and exist only behind the MITM leg — a host claim is opt-in by plugin installation (install IS the authorization, unchanged trust model), and an unrecognized path on a claimed host either is relayed by the gateway itself or falls through to transparent forward. This is the lawful home for the fourth Cursor wire: not a fifth table row.

### 3. Forward-proxy h2 leg — transport-complete, not plugin-gated

Cursor's streaming endpoints force HTTP/2 (an h1 client is rejected with 464); the forward proxy's per-host TLS terminators were h1-only (Bun has no server-side SNICallback, hence the existing per-host terminator pattern). h2 is also the base transport of gRPC/Connect traffic generally, so the leg is NOT a vendor feature: it belongs to the proxy, and the plugin only owns vendor SEMANTICS on the hosts it claims.

- EVERY host advertises both protocols; the ORDER differs. Bun honours the SERVER's preference (verified: server `['http/1.1','h2']` + client `['h2','http/1.1']` negotiates `http/1.1`), so an unclaimed host offers `['http/1.1','h2']` — dual-offer clients (curl, browsers, most SDKs) keep the h1 path the surfaces pipeline knows, ZERO regression, while h2-only clients get h2 instead of a broken downgrade — and a gateway-claimed host offers `['h2','http/1.1']` because the plugin speaks the vendor's h2 wire even to dual-offer clients. The terminator cache is keyed by host+port+mode+CALLER KEY, so a runtime plugin install flips the offer on the next CONNECT and two proxy credentials never share a decrypted terminator.
- Routing to the inner leg is decided on the FIRST DECRYPTED CHUNK: negotiated ALPN is only a hint (Bun does not reliably surface `alpnProtocol` server-side at callback time); the h2 connection preface (`PRI * HTTP/2.0`) is the authority. h2 bytes splice to a prior-knowledge h2c inner loopback (`http2.createServer`, compat `request` API), h1 bytes keep the existing inner. Both inners run the SAME intercept chain, and the h2 fall-through accepts `:authority` where h1 uses `host`.
- The transparent forward RE-ORIGINATES the protocol it accepted: the h2 leg relays upstream over h2 (`forward-proxy/h2-forward.ts` — pooled sessions, `:authority` rebuilt from the dial target, hop-by-hop stripped but `te: trailers` KEPT because gRPC requires it end-to-end, response trailers forwarded via `addTrailers`, bidi bodies with backpressure, cancel on client disconnect). An upstream that will not speak h2 hands the exchange back to the h1 forwarder BEFORE anything reaches the client — including the body bytes already captured, which the h1 leg writes first (Bun's h2 compat IncomingMessage drops chunks emitted while nobody listens, so the head of the body must be captured synchronously).
- Consequence: with NO plugin installed, a gRPC/Connect client is transparently proxied — full HTTP/2 semantics, full access-log capture — instead of being downgraded into a 464. Vendor semantics (Cursor's Connect routes, model catalog) still require the plugin; only the transport is core.
- GATEWAY RELAYS USE THE SAME LEG: a client gateway relays its claimed hosts through the host SDK's `relayUpstream`, which runs exactly these forwarders with the ADR-0018 ADMISSION gate (`reject` → 403 before any dial, `{ rejected: true }`), the LIVE rule-table egress, the ADR-0019 upstream trust and the h2/h1 fallback. The origin SCHEME is the caller's declaration, not a constant — `opts.secure` (default `true` = TLS, `false` = plaintext origin) — and declaring a plaintext origin bypasses NOTHING else: the admission gate and the rule-table egress apply exactly as on the TLS leg (a plaintext origin simply has no certificate to trust), and the h2 leg is TLS-only, so a plaintext origin is served by the h1 leg. A plugin never dials an origin itself — a raw `http2.connect`/`https.request` would silently bypass all of them.

- A gateway that must read the first body frame to route (model selection) hands those consumed bytes back through `relayUpstream`'s `preface`; both the h2 and h1 legs write them before the live stream, so a peeked request loses nothing and is not replayed twice.

### 4. Reference plugin: `cursor-gateway`

The dev plugin tree carries the phased reference implementation (`plugins/cursor-gateway/`, its own repository; untracked here):

- **Phase 1 (shipped, 0.1.0)** — OBSERVE. Claim the four Cursor authorities and relay every decrypted exchange through the core host SDK (`relayUpstream`): byte-verbatim upstream, both directions captured to a day-JSONL feed, Connect frames decoded at READ time by the dissector. Cursor keeps talking to its real backend; capture never mutates traffic.
- **Phase 2+ (shipped in the dev plugin)** — OWN. Decode and answer the three inference wires (`agent.v1.AgentService/Run`, `aiserver.v1.InferenceService/RunInference`, legacy `ChatService/StreamUnifiedChat…`), merge or replace the model catalog, and route requested ids: with `catalogReplace` on, the catalog IS the OCR list, so every request answers locally (an unlisted leftover such as `auto` resolves to the configured default instead of contradicting the advertised list); otherwise OCR-namespace ids go through `host.chat` and every other id relays byte-verbatim to Cursor. Client MCP tool definitions ride the agent wire as extra function specs. An operator-only `mockGetMe` switch (`mockEmail` overrides the address) answers `aiserver.v1.DashboardService/GetMe` locally with a synthetic identity so the intercept path can be exercised without a live Cursor session; every other account/dashboard RPC still relays. A second test-only switch, `mockPlan`, rewrites `/auth/full_stripe_profile`'s membership fields on the way back so the client's picker renders injected entries on a free account — the upstream profile is untouched and Cursor's server-side entitlement still applies.
- Wire codec: Connect frame `[1B flags][4B BE length][payload]`, 0x01 gzip, EndStream JSON at `0x02` (Connect standard) or `0x80` (Cursor legacy marker) — schema-less preview in phase 1; phase 2 vendors protos pinned to the validated Cursor build and re-runs the extractor on a client upgrade.

**Second reference: `qoder-gateway`** (`plugins/qoder-gateway/`, own repository; untracked here). Qoder cannot be pointed at a custom endpoint, so the plugin claims the vendor hosts for BOTH editions — international (`api2-v2.qoder.sh` chat, `api1..3`/`center` catalog and control, `openapi`, `qts2`) and China (`gateway.qoder.com.cn`, `openapi.qoder.com.cn`) — while login hosts stay unclaimed and pass through. It owns the two gRPC inference RPCs `model.chat.ChatService/ChatCompletion[Stream]` (decoded with the CLI-vendored `chat.proto` and routed through `host.chat` only when the model is in the OCR namespace — `ocr/<ref>`, a bare tier alias, or `forceModel`; EVERY official key (`auto`, `qlite`, …) plus any `custom_model` (BYOK) request relays byte-verbatim with its `preface`) AND the HTTP SSE `.../agent_chat_generation` surface (COSY-decrypted into an OpenAI-shaped body; undecodable bodies relay with their preface; the SSE payload carries no BYOK marker, so the gRPC `custom_model` guard has no SSE counterpart yet). `catalogReplace` inverts the gRPC default: the advertised list is the OCR list, so every non-BYOK request answers inside the gateway and a leftover official key resolves to the configured default. The model catalog is merged from the upstream scene map (COSY-decrypted with the vendored `qoder-auth.wasm`) or replaced; the merged reply is plaintext because the client's parser falls back to raw text when decryption fails, and the same merged list is seeded into the client's encrypted `catalog-v<N>` cache because the desktop daemon often never asks (append seeding prunes `ocr/*` rows the current registry no longer advertises; seeding is disabled when `interceptChat` is off). Wire codec: standard gRPC `[1B compressed][4B BE length][payload]` with gzip flag 1 and `grpc-status` in HTTP/2 trailers; gateway 401/403/429/5xx map to UNAUTHENTICATED/PERMISSION_DENIED/RESOURCE_EXHAUSTED/UNAVAILABLE and `retry-after` rides the trailers. The `qoder` client adapter ships the launcher env for all three legs: `--proxy-server` (Chromium), lowercase `http_proxy`/`https_proxy` (undici fetch) and `grpc_proxy` (grpc-js consults it first); the CLI launcher adds `NODE_EXTRA_CA_CERTS`/`--use-system-ca`, while the desktop launcher disables TLS verification for that process (`NODE_TLS_REJECT_UNAUTHORIZED=0`) because its daemon ignores every CA store except the compiled-in one. Under `forwardProxy.requireCredential` the console passes the bound key into the launcher URL (`http://ocr:<key>@127.0.0.1:<port>`) so the Node/gRPC legs authenticate without a prompt; launchers written with a credential are owner-only (0700).

**Key binding on the in-process leg.** The ONLY proxy credential is an OCR key as the Basic password (`Proxy-Authorization: Basic <any>:<keySecret>`, username ignored — key names are not unique), captured at CONNECT, validated in constant time against the live config, and inherited by every decrypted request on that connection — terminators are partitioned per key so identities never share one. OCR-routed completions (`host.chat`) REQUIRE that identity; the plugin's console-picked `accountKeyId` is the fallback, and with neither the turn is REFUSED (401) — proxy admission is transport, model usage is keyed. With a key the core re-checks it against the live config at dispatch, consumes its inbound `limits` (429 + `Retry-After`), applies its `modelAccess` (403), and attributes usage/capture to it. Vendor-native requests relay byte-verbatim and never enter this seam (no gateway key exists on that wire), so passthrough keeps working without any key. The console card requires a key before it saves the model surface. Reason: OCR-routed turns are the gateway's own inference and must not escape the per-key accounting the native surfaces enforce. `forwardProxy.requireCredential` (default off, hot-applies) closes the loopback loophole: every connection must then present a key, so the bound-key fallback can never lend an unauthenticated local process its identity — non-loopback binds already enforce this unconditionally, so the fallback is never reachable remotely.

- **Loop guard.** OCR's own `qoder` provider dials the same upstream hosts. Provider egress must stay direct (or use an external proxy): pointing `forwardProxy.proxy.url`, or the backend process's `https_proxy` / `grpc_proxy`, at OCR's own inbound proxy makes the gateway intercept OCR's outbound dial and recurse — the admission gate cannot tell the two apart.

### 5. Traffic observation — capture is full-fidelity, display is windowed

A gateway that wants its traffic visible registers a **dissector**, never a view. The Wireshark model, split by phase:

- **Capture (plugin, write path)** — the plugin streams every decrypted chunk straight to a sidecar file `<ocrHome>/plugins/traffic/<id>/bodies/<YYYYMMDD>/<exchangeId>-<side>.bin` and appends ONE metadata line to the day JSONL (headers, byte counts, status, leg, file refs). Nothing is buffered in memory: a long `StreamChat` costs O(chunk), not O(body). Bodies are **never truncated for storage** — the sole ceiling is a runaway guard (64 MiB per side) that stops the write and sets an honest `truncated` flag. Bodies older than 7 day-directories are pruned on the plugin's own write path.
- **Decode (plugin, read path)** — the plugin's `dissect(exchange)` is called by the backend at READ time with the captured bytes, and returns named protocol layers. Protocol knowledge therefore stays with the plugin that owns the wire; the console renders layers it has never heard of.
- **Display (core route, read path)** — the route reads a fixed WINDOW per side (32 KiB for the dissector, 1 KiB for the inline hex preview) and ships byte counts + file refs, never payloads. `/api/admin/traffic-body/:token` streams the whole capture for download — the SAME neutral endpoint the proxy log uses, so the console never learns which subsystem stored the bytes; full fidelity is one click away and the browser's DOM never receives a multi-megabyte body.
- **One timeline, one filter set** — dissected rows join the existing proxy access-log table (no separate tab, no separate view). Columns classify transport, not vendor: type (`http` / `connect`), protocol (`h1` / `h2` / `ws` / connect-rpc), host, method, path, status, duration, ↑/↓ body bytes.
- **One drawer, one decoder registry** — every row (proxy or gateway) is rendered by the SAME detail component from a normalized side model (headers, bytes, layers, download ref); the row kind only builds the model. A body is bytes plus a list of decoders that claim them: `hex` is the FLOOR decoder (Wireshark's `data` — always applicable, the fallback), with `text` / `json` / `image` / `pdf` built in and each plugin dissector layer ranked above them. The default view is the highest-ranked applicable decoder, so protocol knowledge wins over hex with no ordering logic in the UI, and a new format is one registry entry — never a new branch. Layer output is SIDE-TAGGED (`req` / `res`) by the dissector: an empty response body must never appear decoded.

Consequence: the console never learns a vendor protocol, and a plugin that declares no dissector simply does not appear. Retention, feed layout and the tail cap belong to the core route; byte ownership belongs to the plugin.

### 6. Console ownership

`/admin/clients` gains `cursor-proxy` and `qoder-proxy` as proxy-access clients (`SupportedClient`, `CursorProxyClientAdapter`, `QoderProxyClientAdapter`). Setup cannot write a vendor config file — it (a) requires `forwardProxy.enabled`, (b) writes `cursor-launcher.cmd|.sh|.command` (plus `cursor-agent-launcher.*` when the CLI is installed) and the Qoder desktop/CLI launchers, setting `--proxy-server` for Chromium legs and lowercase `http(s)_proxy`/`grpc_proxy` + `NODE_EXTRA_CA_CERTS` + `NO_PROXY` for the Node/gRPC legs. Phase 1 publishes no model advertisement: the plugin's model catalog arrives with the gateway plugin. The per-app launcher is deliberate: no OS-proxy takeover (which would fight Clash/v2ray for the same registry keys) and no kernel redirector. CA trust stays EXACTLY the forward-proxy CA (no new trust material); installation remains an explicit operator action. The status probe is per-platform and evidence-based — Windows Root stores via `certutil`, macOS `security verify-cert` against the SSL policy, Linux anchor directories + the merged bundle + the NSS databases Chromium/Electron actually read — and reports `unknown` when a probe cannot run instead of guessing. Launch injection is process-start only: Dock / Start-menu / `.desktop` launches bypass the launcher, and an already-running single instance swallows a later launcher invocation. The macOS `.command` starts Cursor detached (`nohup … &`) so closing the Terminal window it was double-clicked from does not take Cursor down; the Linux `.sh` keeps `exec` because it IS the terminal session. Teardown removes ONLY the launchers this adapter owns and never the CA, never the client's own files; setup removes a stale agent launcher when the CLI is gone. Status echoes BOTH launcher paths (`configPath` plus the CLI launcher in `artifacts` when the CLI is installed or a launcher file from an earlier setup still exists — `artifacts` is absent otherwise), so the console card lists every launcher setup owns instead of only the IDE one. `ocr cursor` / `ocr cursor-agent` / `ocr qoder` / `ocr qoder-cli` are passthrough verbs: they execute the managed launcher (stdio and the LAUNCHER's exit code forwarded — `128+signum` for a signal) rather than re-deriving the env, so a CLI launch and a double-click share one contract. The IDE launchers on Windows/macOS deliberately detach (`start`/`nohup`), so there the code belongs to the launcher and `--help`/`--version` output to the app it starts rather than to `ocr …` — the CLI says so instead of exiting 0 in silence; the Linux `.sh` and both agent launchers stay attached and forward the real code.

**Setup never gates on that state.** A successful hook returns advisories alongside the write —
`ca_not_trusted` / `ca_trust_unknown` / `proxy_not_running` (shared builder, `cli/clients/base.ts`
`collectHookWarnings`) — and re-probes the CA with the TTL cache bypassed, so a cached pre-install
`trusted` cannot silence the warning. The CLI prints them; the console raises a warning toast and
refreshes its CA-trust chip. No launcher is withheld because the root is not imported yet: the
wizard that installs it lives on another page, and blocking would be a dead end.

Plugins are also exportable from the same page: `GET /api/admin/plugins/:id/package` returns the installed zip verbatim for a packaged plugin, and for a dev-tree plugin it BUNDLES the entry (third-party imports inlined) and zips it with the SAME deterministic packer `plugins:build` uses — the download is installable and byte-identical to the build output.

Packages are always **self-contained**: the released host is a `bun build --compile` binary, and compiled executables resolve bare specifiers only from the embedded snapshot — never from `node_modules` on disk. A source-only package is therefore refused at load with a repack instruction; dependency resolution belongs to packaging time (author/CI), never to plugin install time. `plugin.json` carries **no** dependency list: an in-tree plugin declares npm packages in the host repo's workspace `package.json` (the bundler resolves them from the repo's `node_modules`), and an out-of-tree author ships the bundled `index.js` directly — the only install-time contract is that the entry resolves with zero external packages. The bundle is built for the **Node** target, not Bun, because BOTH host runtimes must run the same artifact: the compiled sidecar and `node backend/dist/index.js` (README: Bun or Node >= 18). A `bun` target emits `import.meta.require` for CJS interop inside inlined dependencies — a Bun-only API that made a package load in the sidecar and throw `__require is not a function` on the Node entry point — so CJS interop is emitted as `createRequire` and a bundle still carrying `import.meta.require` is REFUSED at pack time. Each package also carries a `package.json` holding `{"type":"module"}` (a source `package.json` is replaced, never shipped): the entry is ESM, and a bare `.js` file is only ESM by default from Node 20.19 / 22.7 on, when syntax detection arrived — the Node 18 releases the README still supports would otherwise parse `export` as CommonJS.

Official and third-party packages share ONE loader and ONE package format. Precedence is deterministic: source tree (read ONLY when `OCR_PLUGIN_SRC_DIR` names one — `bun run dev` names `plugins` for its own backend child, since that is the command a plugin is edited under; no other entry point reads a checkout, so an installed or standalone gateway lists what is INSTALLED and install/uninstall stays testable rather than hidden behind phantom rows; opt out of even the dev default with an empty `OCR_PLUGIN_SRC_DIR=`) > `<pluginsRoot>/bundled/*.zip` (shipped with the app) > `<pluginsRoot>/*.zip` (operator-installed), with sorted file names inside each root; the HIGHEST-precedence copy of an id owns it — a duplicate is warned and the lower copy ignored, and a copy that FAILS to load still owns the id (one console row per id, one target for disable/uninstall), so nothing is ever resolved by `readdir` order. Package FILE NAMES are free-form in every root: each ownership question — does the app ship this id, is this install an override, is this uninstall a tombstone — is answered by the MANIFEST id, never by guessing `<id>.zip`. `bundled/` is the app-owned tier: an install that would shadow one is refused, `ocr-*` ids are reserved for them and are refused at install (not merely at load), and uninstalling one writes a tombstone in `disabled.json` instead of deleting a file the app owns. Uninstall removes the package, the unpacked copy, the ledger entry, the preset providers the plugin REGISTERED (deleted only while the defs file still matches what the plugin wrote — an operator edit makes it operator-owned and survives) and the disabled-ledger row; it deletes `<pluginsRoot>/config/<id>.json` too — the operator's plugin settings — so uninstall is a CLEAN SWEEP: package, unpacked copy, ledger row, registered preset providers, settings artifact, and the empty `plugins/config/` directory if that was the last one. Settings do not need to survive, because an UPGRADE is not uninstall → install: it is a plain install OVER the existing id, which re-extracts the package (fresh mtimes, so the module cache is busted — no restart needed), leaves the settings artifact and the operator's provider defs untouched, reconciles the presets it declares — a preset the NEW version dropped is retired from `providers.json` (unless the operator edited that def, which makes it operator-owned), so an upgrade leaves no provider behind from a version that no longer exists — and takes a disabled plugin back to enabled (installing expresses intent to use). The unpacked tree is REBUILT, never merged: an asset the new version dropped disappears with the rest of the old tree. A package that ships WITH the app is the one uninstall that is a reversible tombstone instead — its file belongs to the app, so re-enabling it must not have thrown the settings away. Nothing in the current build pipeline populates the tier — the product question "do plugins ship with the app?" is open — so it is filled by a release that decides to ship packages, or by an operator who places one there deliberately; the guards apply to whatever is actually present, and `bun run plugins:build` writes an installable artifact to `<repo>/.plugin-dist/` — a repository build output, never the app-owned tier and never the runtime root: a package reaches an install through the console's upload, not through a build step writing into `OCR_HOME`. Reload is layered, and the boundary is the module cache: `POST <prefix>/plugins/reload` re-imports from disk in-process, which is enough for `plugin.json` (schema, presets, display) and for an edit to the plugin's ENTRY file — each import is cache-busted with the entry's mtime, and the specifier is a PATH rather than a `file://` URL because Bun keys a file-URL module on the URL alone and ignores the query, which served the previous module on Windows until a restart. An edit to an imported SUBMODULE cannot be busted from outside: its resolved URL carries no query, so the module cache keeps it. That is the watcher's job — `bun run dev` already runs the backend under `bun --watch`, which restarts the process on any change under the loaded graph and rebuilds it from scratch. A package that cannot load is DISCARDED so it never re-fails every boot — and when it was uploaded as an UPGRADE, the version that was running is restored first, so a bad upload is a no-op (422 + the previous package back, its settings intact) instead of a lost plugin. A refused install writes NOTHING — it is decided before any artifact or ledger is touched. `plugin.json.apiVersion` declares the plugin contract version and MUST EQUAL `SUPPORTED_PLUGIN_API`: v1 is the FIRST plugin mechanism and promises no legacy or forward compatibility, so any other value — or a missing field — is an illegal package, rejected at install before anything touches disk and again at load; adding a capability to the host SDK (e.g. `pluginDir()`) is additive and does NOT bump `apiVersion` — only removing or changing a contract does. `plugin.json.id` is a lowercase slug (`a-z`, `0-9`, `-`, starting alphanumeric) because it IS a directory name — `<pluginsRoot>/unpacked/<id>/` and the canonical install target `<pluginsRoot>/<id>.zip`, while a package placed in either root by hand keeps whatever file name it has — so the manifest validator rejects anything path-shaped before a package can steer those paths, and casing cannot slip past the `ocr-` reservation on a case-insensitive filesystem. Also: a package whose manifest is unreadable only surfaces as a row when its FILE NAME is itself a slug — an id is a path component, so an unidentifiable file with an arbitrary name is warned about and ignored rather than fed to the unpacker. Because a package is a single flattened entry, shipped data files resolve from `host.pluginDir()` (the plugin's load root) and NEVER from an inner source module's `import.meta.url` — that parent stops pointing inside the package once the sources are bundled, which silently degrades a prompt and hard-fails a proto corpus.

### 7. Plugin-level configuration

Plugins may declare operator-facing parameters, and the console renders the settings form generically from that declaration. Three sources, strictly separated:

- **Declaration** — `plugin.json` `configSchema`: a flat array of `{key, type, default?, min?, max?, values?, enumLabels?, control?, section?, visibleWhen?, title?, desc?}` where `type ∈ string|number|boolean|string[]|enum`, plus an optional `configSections` grouping. `title`, `desc` and `enumLabels` follow the manifest locale-map convention (a plain string or a BCP-47 keyed map of strings); `enumLabels` maps a declared `values` entry to the text an operator sees, because a machine value (`follow`) is not a label. `visibleWhen` is a DISPLAY-ONLY predicate — `{key, equals?|in?}` over exactly one sibling enum/boolean field. `control` selects a widget from a CLOSED console vocabulary (`text` | `textarea` | `model` | `models` | `segmented` | `apiKey`) and must be able to drive the field's type (`model` a `string`, `models` a `string[]`, `segmented` an `enum`, `apiKey` a `string` — the joined-button shape the console itself uses for its mode switches, so a 3-way plugin option like none / custom / follow is not forced into a dropdown); the widget changes only how the value is EDITED — storage, validation and merge stay type-driven, so a `model` value is still a plain string in the artifact. Adding a widget is a console capability (registry + renderer + this ADR), never something a plugin can invent or compose. `configSections: [{id, title?, advanced?}]` groups the fields, declared ONCE and referenced by `field.section` (a per-field title would be a drift twin); a section id that nothing declares, or a field naming an unknown id, fails at install, and a section whose fields are all hidden by `visibleWhen` renders no heading. `advanced` starts a section collapsed — the values inside survive, exactly like a hidden field. That is the whole surface: no expressions, no layout, no ordering, no tabs, no plugin-supplied UI code (which would run with admin credentials in the console). Grouping is where the vocabulary STOPS: a form that outgrows sections is a first-party console page, not a richer protocol. Fields arrange as declared-section order then schema order, ungrouped fields first. Arrangement stays console-owned; a plugin names a condition and, when the default widget is wrong for the data, one control from that vocabulary. A field hidden by `visibleWhen` is NOT cleared or skipped — it keeps its value and is still validated and merged, so switching a mode back never loses operator input. Primitives only; there is deliberately no JSON-Schema engine or layout DSL — that would invite arbitrary UI complexity into the plugin protocol. A malformed schema fails the package loudly at install/load (the author-facing API must not degrade silently): unknown or type-incompatible `control`s, sections that no field references, fields naming an undeclared section, unknown `visibleWhen` targets, targets with no discrete values, values the target can never hold, and cyclic visibility chains are all install-time errors.
- **Storage** — `<pluginsRoot()>/config/<id>.json` holds only the operator's effective (non-default) values. Plugin parameters NEVER enter `config.yaml` (ADR-0016: frozen schema; plugin lifecycle state lives with the plugin artifacts, disabled.json / registrations.json precedent).
- **Merge** — the host validates stored values field-by-field (unknown keys dropped; wrong-typed/out-of-range values fall back to the default with a warning; a bad artifact never crashes a load) and hands the merged object to the plugin through its host SDK `config()`. `''` is a valid `string`: a blank default round-trips unchanged. Call-time lookup: always current after a console save. The merged result is cached per plugin id; every plugin reload invalidates the cache so hand-edited artifacts are picked up.

Console: `GET /api/admin/plugins/:id/config` returns `{schema, values}`, `PUT` validates + persists + fires the plugin's optional `onConfigChange(config)` (a failing hook never rolls back a persisted save; the merged values reach the plugin via `config()` regardless). A plugin without a schema exposes nothing and rejects writes — there is no free-form parameter bag.

`cursor-gateway` uses the mechanism for its whole operator surface: capture (`logFrames`, `previewBytes`), the model catalog (`model` writes Cursor's default-model RPC, `forceModel`, `modelListMode` with `models`/`accountKeyId`, `catalogReplace`), the agent loop (`maxTurns`, `toolTimeoutMs`, `heartbeatMs`, `maxResultChars`, `contextMaxChars`, `systemPrompt`), interception scope (`interceptAgent` / `interceptDesktop` / `interceptLegacy` plus the legacy knobs behind the third) and the synthetic `GetMe` answer (`mockGetMe` / `mockEmail` / `mockPlan`). The Client Hub card edits the model-catalog subset of that schema; the Plugins page drawer renders the rest.

## Consequences

- Vendor inbound protocols become pluggable without core growth; the proto corpus and its drift tooling live with the plugin that needs them (install = authorization) once phase 2 vendors them (§4). The TRANSPORT is the other half and it does not move: h2 re-origination is core (§3) and is exposed to gateways as `relayUpstream` (ADR-0018 admission gate + rule-table egress + upstream TLS + h2/h1 fallback), so a plugin author only ever writes semantics or observation — and an operator who installs nothing still gets a working, fully logged h2/gRPC passthrough.
- A gateway relay can never silently bypass forward-proxy policy: `relayUpstream` is the only dial path, and it applies the ADR-0018 admission gate, the live rule-table egress and ADR-0019 trust. A plugin dialing an origin itself is a defect, not an optimization.
- One more TransportContext implementation exists (the callback-sink gateway seam) — the terminal-send discipline is now proven by three implementations, and plugin completions are indistinguishable from native-leg completions to routing/breakers/captures.
- The Bun http2 server-side quirk (unreliable `alpnProtocol` at terminator callback time) is encoded as the preface-sniff rule — do not "simplify" back to ALPN-only routing. Same family of quirks, same rule: ALPN ORDER is a server-preference decision (verified, not assumed), and the h2 compat IncomingMessage drops chunks emitted while nobody listens — so an h2 body's head must be captured synchronously, before the first await.
- Boundaries: Tab completion, codebase indexing and login traffic are NOT intercepted (non-claimed hosts / relayed paths — Cursor keeps working against its real backend for those); the gateway carries no `x-cursor-checksum` obligations (it is the server, not the client); personal use, own machine, own account.
- No new config.yaml section: gateway lifecycle state lives with the plugin artifacts (disabled.json / registrations.json precedent, ADR-0016 posture untouched); operator-set plugin values live in `<pluginsRoot()>/config/<id>.json`, never in schema.
